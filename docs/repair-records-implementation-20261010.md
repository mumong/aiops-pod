# 修复节点独立规划与诊断交接

## 已确认设计

- 诊断只生成报告，不生成可执行修复计划。
- 用户点击报告入口时携带诊断 run_id；修复节点基于明确的历史报告、分组证据摘录及引用自主补查和规划。
- 记录保存在现有 reports PVC，绑定原有浏览器 owner 身份；不引入新数据库，不跨 owner 读取。
- 生成方案后直接进入已有 review/auto 流程；人工模式在具体动作前批准，自动模式通过既有安全策略后执行。不另设“选择执行”步骤。
- 对话修改产生新 run_id/方案版本，旧待审批方案失效；执行命令期间拒绝替换，已执行结果必须保留。
- 三类核心场景只通过 Runbook、可信参数与测试用例增强，不实现故障专用执行分支。

## 实现边界

- `remediation/records.py`：owner 归属、不可覆盖记录、原子写入、执行与替代互斥、会话最新记录索引。后端内存丢失后可以恢复诊断/方案上下文，不恢复或自动重放写操作。
- 通用证据摘录跨分组轮流分配 64,000 字符预算，单项最多 4,000 字符，保留原文引用及明确截断标识。它是有损模型输入，不把预览假称全量证据。
- 修复规划新增逐对象状态及配置变更、验证条件。缺少可靠外部信息时不强行生成动作。
- 旧报告未写入新记录时不能仅凭公开 run_id 导入，需重新诊断；防止绕过归属校验。
- 安全黑名单及审批/自动配置沿用既有实现；本轮不承诺通用恢复判定闭环，执行完成仍须结合实际状态验证。
