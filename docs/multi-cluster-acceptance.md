状态：开发前制定（2026-10-21）；2026-10-22 根据 run `e43e8298` 的教训，补充了衔接处检查、误报检查和意图准确率统计（§2 的 L1b / L3b、§3、§4.8、§4.9）。当前设计见 [多集群设计](multi-cluster-design.md)，开发过程记录见 [specs/008-multi-cluster](../specs/008-multi-cluster/spec.md)。

## 2. 测试分层

| 层 | 内容 | 是否依赖 LLM | 通过标准 |
|---|---|---|---|
| L0 单元测试 | 注册表、别名解析、后端档案选择、`extra_label` 拼装、事件文本解析、垫片参数检查、签名校验、注入规则 | 否 | 全部通过；现有测试全部通过 |
| L1 契约测试 | xnet 隧道、VictoriaMetrics/VictoriaLogs 接口、新旧后端常用指标是否都存在 | 否 | 全部通过 |
| L1b 衔接处契约 | MCP 在各集群上的真实输出，交给 AIOps 自己的观测解析器校验 | 否 | **100% 通过** |
| L2 工具级测试 | 脚本直接调用 MCP 工具和 runner，不经过模型 | 否 | **100% 通过**（行为确定） |
| L3 端到端测试 | 网页或 `/ask` 接口提问，完整走工作流 | 是 | 范围类断言 100%；诊断质量见 §5 |
| L3b 事件流与前端 | 端到端运行的 SSE 事件流满足 UI 依赖的规则；再交给前端同一份事件处理逻辑回放，检查卡片的最终状态 | 是 | 规则 100% |
| L4 故障测试 | 边缘 runner 停止或重启、隧道断线（用测试用的假隧道模拟） | 部分 | 全部通过 |
| L5 回归测试 | 现有环境 10.2.0.48 的全部验收 | 是 | 结果与改动前一致 |

范围类断言（集群是否正确、有没有串集群、有没有调用不该调用的工具）由工程代码保证，所以要求 100%。诊断结论的正确率受模型影响，按 §5 单独评估。

**为什么补 L1b、L3b 和误报检查**：run `e43e8298` 暴露的几个问题，各仓库自己的测试都是绿的。

- 定位事件被改记到别的阶段：单元测试用假函数代替真实定位，没有事件；验收只看最终报告。
- MCP 日志结果不符合 AIOps 契约：MCP 的单元测试断言的正是那个错误字段。
- "子集群"被展开成含中心的全部集群：标准答案本身写错了。
- xnet 主备副本被报成异常：验收只看"找到了没有"，不看"多报了没有"。

因此衔接处必须用对方的真实代码检查；误报要有清单。范围按意图交给模型判断（Boss 2026-10-22：尽量识别准确，容易误解的说法可以接受），意图样例只用来统计准确率，不作为验收关卡。

## 3. 验收脚本（随各阶段开发，先于功能代码）

放在 `robusta/scripts/acceptance/multicluster/`：

| 脚本 | 作用 | 首次需要的阶段 |
|---|---|---|
| `env_check.py` | 环境基线：三个集群在线、xnet 隧道可用、VM/VLogs 有数据、已知噪声清单；输出 `xnet`、`monitor` 命名空间的对象快照（X1 用） | P0 |
| `contract_xnet.py` | A15：`/proxy` 可用、不带证书被拒、Node 名与 UUID 可以互相转换、`cluster` 标签与 Node 名一致 | P0 |
| `contract_backends.py` | VM 的 `extra_label` 生效；VLogs 能按集群查询事件；常用指标在新旧两套后端上都存在 | P1 |
| `tools_direct.py` | L2：逐个调用 MCP 工具和 runner 接口并断言结果 | P0 起逐步扩充 |
| `e2e_ask.py` | L3：用 `/ask` 提问，从运行报告中取出路由范围、工具调用的集群参数和结论，并做断言 | P2 |
| `contract_mcp_aiops.py` | L1b：在 MCP Pod 里对三个集群调用日志（有事件 / 无事件）、指标、链路、拓扑、Pod 生命周期工具，再用本仓库的 `ObservationProcessor` 解析；出现 `parse_failed` 等即失败 | 2026-10-22 补 |
| `e2e_ask.py --phase p5` | L3b 与误报：事件流规则、前端回放（调用 `frountind/scripts/replay-sse.mjs`）、声明对象与虚拟节点不得列为异常（清单在 `mc_common.DECLARED_NORMAL`、`CLUSTER_NODES`） | 2026-10-22 补 |
| `e2e_ask.py --phase intent` + `intent_cases.json` | 统计路由按意图判断范围的准确率（HIT / MISS）；只作观察，不作为关卡 | 2026-10-22 补 |
| 故障注入（无单独脚本） | L4：`tools_direct.py` / `e2e_ask.py --phase p4` 内把 runner 副本数设为 0 并在 `finally` 中恢复；隧道断线和模型断线在单元 / 集成测试中模拟（`tests/unit/multicluster/`：假隧道、`test_model_disconnect_is_retried_once_per_cluster`）。只操作我们自己的组件，不加防火墙 | P3 |
| `runtime_dependency_check.py` | X3：检查中心 AIOps 和 MCP 的镜像、ConfigMap、Secret、环境变量中没有边缘 kubeconfig 和边缘 API Server 地址 | P0 |
| `snapshot_diff.py` | X1：比较前后两次快照 | P0 |

每个脚本输出 `PASS` 或 `FAIL`、用例编号，以及证据（运行 ID、任务 ID、请求耗时）。

**归属限制**：`e2e_ask.py` 按"提问前后新增的日志"判断这次运行调用了哪些集群、命中了哪些 runner，因为 MCP 日志不带 run_id。如果这段时间里有别人也在使用环境，他们的调用会混进来。

- 脚本会从 AIOps 日志检测同期开始的其他运行（`concurrent_runs`）。
- 有并发运行时，"串集群"类断言不通过会标为 `INCONCLUSIVE`（不算通过），需要在无人使用时重跑。
- 其他运行只会多出调用，不会让本次的调用消失，所以 PASS 仍然有效。

2026-10-22 的 P5-1 首次运行就是这样被另一次快速查询（`7d9e05cc`）误判为 FAIL 的。

**为什么补召回检查（run `51d58579`）**：之前的 P5 只检查"范围对不对、有没有误报、事件流和卡片对不对"，没有检查"每个真实故障都被诊断出来"。结果 edge-88 的两个故障被模型判为"测试场景"后从报告里消失，edge-89 的 c09 被漏掉，这几项都通过了。现在 P5-1 按测试当时的真实故障逐一核对召回，并通过前端回放确认分析正文看得见。

只操作我们自己的组件（runner），由脚本在结束时自动恢复。隧道断线类场景在集成测试中用假隧道模拟。

| # | 操作 | 预期 |

## 5. 诊断质量的评估方式

范围类断言之外，诊断结论的正确率受模型影响，不作为硬性门槛，而是与现有环境对比：

- 同一个 case，在现有环境（旧后端，有容器日志和链路）和新环境（新后端，只有事件）各诊断 3 次。
- 记录：根因是否正确、是否承认数据缺失、是否有编造的证据、耗时、工具调用次数。
- 判定：新环境的根因正确率**不低于现有环境减去一个合理的差值**。差值来自容器日志和链路的缺失，P1 结束时由 Boss 确认。**编造证据的次数必须为 0**。
- 结果记录在本文档 §7。

## 6. 测试环境操作规范

- 只在 `aiops`、`mcp` 命名空间和 case 命名空间里部署和删除资源；不碰 `xnet`、`monitor`、`kube-system`。
- 每个阶段结束后清理 case（`make case-clean`）和临时 Pod，确认 runner 副本数已恢复。
- 不在测试主机上添加防火墙规则。
- 正在执行修复、审批或验收时不发版（与现有约定一致）。
- 对 xnet 或可观测组件的任何运维操作（如 P3-2 的重启），都要先经过 Boss 确认。
