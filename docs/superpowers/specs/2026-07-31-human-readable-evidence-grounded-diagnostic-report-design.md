# 面向人的证据型诊断报告设计

**日期**：2026-07-31

**状态**：已获用户批准

**范围**：Robusta `/ask` 诊断报告的 Prompt、确定性正文渲染和机器附录

## 1. 背景与目标

当前报告已经具备 Fact Ledger、证据引用和机器可核验附录，但正文偏向机器合同展示：
诊断概览包含内部权威性声明，现象描述强调模型内容被移除，可观测性表还可能在附录已有
Logging 或 Tracing 证据时显示“未获取到”。这些内容有利于实现审计，却降低了人类读者对结论的
理解和信任。

本次改动将报告拆成两个明确层次：

1. 上半部分是面向人的诊断正文。它直接回答问题，用自然语言解释证据、因果关系和下一步，
   并用 Markdown 粗体突出关键状态、实体、指标与错误。
2. 底部保留机器可核验附录。它继续承载 Fact ID、evidence ref、结构化事实和安全合同，供审计、
   回放与自动验收使用。

真实性边界不变：精确值、状态、可用性、内部机制和因果关系只能来自通过校验的 FactRecord 或
来源可核验的最终 observation；模型不得补算或猜测。没有 typed remediation policy 时仍必须输出
`manual_only`、`requires_human_approval=true` 和 `actions=[]`。

## 2. 通用性约束

报告实现不得按 OOM、CrashLoopBackOff、ConfigError、ImagePullBackOff、Pending、调度失败或其他
具体故障类型分支。生产代码和 Prompt 都不得包含“识别到某故障名就套某一结论、因果链或修复建议”
的规则。

确定性代码只能依据通用合同处理内容：

- 证据维度，例如 Kubernetes、Metrics、Logging、Tracing、Topology；
- 已校验事实的类型、状态、时间、实体、来源、值和 evidence refs；
- 根因分析器明确选出的 supporting facts 与因果边；
- 证据覆盖状态和 typed remediation policy。

模型负责把上述通用输入组织成可读语言。新增 Pod 异常场景应通过新增真实事实和模型解释自然获得
支持，而不是修改报告渲染器增加场景专用代码。

通用性门禁将扫描生产代码中的故障专用条件，并使用至少三类不同异常夹具验证同一渲染路径。

## 3. 方案选择

### 方案 A：只修改 Prompt

改动最小，但现有 `conclusion_formatter.py` 会在模型输出之后确定性替换诊断概览、现象描述、
可观测性表和附录。只改 Prompt 无法稳定解决正文被重新数据化的问题。

### 方案 B：同时修改 Prompt 与正文渲染器（采用）

Prompt 定义人类可读结构和 AI 总结职责；确定性渲染器保证证据聚合、引用、安全合同及最终兜底。
该方案能同时保证可读性、真实性和输出稳定性。

### 方案 C：只修改确定性渲染器

输出稳定，但只能机械拼接事实，难以形成自然的证据解释和因果叙述，无法满足“有 AI 总结而不是
陈列数据”的目标。

## 4. 报告信息架构

正文按以下顺序输出：

1. **诊断概览**：直接给出问题层级、诊断结论、置信度和影响对象；不展示内部证据合同声明。
2. **现象描述**：复述用户问题并概括真实观测到的关键现象和实体。
3. **关键证据**：按读者价值选择证据，展示真实信号、来源和它说明的含义；不堆叠 JSON、Fact ID
   或内部 entity ID。
4. **可观测性摘要**：按维度聚合全部可展示的已验证证据，而不是只使用 RCA supporting facts。
5. **证据关联与因果链**：只连接根因分析器已经验证的 supporting facts 和因果边，不把背景证据
   升级为根因。
6. **根因结论**：用一段明确、自信、直接的自然语言回答问题，并突出关键值。
7. **修复建议**：只展示 typed policy 允许的动作；没有 policy 时给出人工确认方向，不生成危险写命令。
8. **验证步骤**：使用只读或 policy 允许的验证方法说明如何确认恢复。
9. **注意事项**：仅保留与当前结论和后续观察有关的行动信息，不重复内部合同警告。
10. **机器可核验附录**：保持结构化事实、引用、限制和 remediation JSON 的审计能力。

正文不再输出以下内部话术或同义变体：

- “权威结论仅由 validated FactRecords 及其引用确定”；
- “未验证的模型叙述不构成精确值、可用性、内部机制或因果关系证据”；
- “当前可核验现象仅见……”；
- “本节不保留模型生成的……” 。

这些约束仍由代码执行，但不向最终读者解释内部实现。

## 5. 可观测性证据聚合

### 5.1 输入范围

正文聚合器读取本轮最终、已归档且来源可核验的 observability projection。canonical Fact Ledger 优先；
只有满足现有 trusted fallback 规则的 legacy facts 才能进入正文。被 RCA 选为 supporting fact 不是
展示 Logging 或 Tracing 信号的前提。

聚合顺序如下：

1. 按证据身份去重并保留最终成功 observation，避免首次失败覆盖后续成功重试；
2. 按 dimension 分组；
3. 为每个维度选择少量最有信息量的真实信号；
4. 将事实值与来源交给 AI 生成一句解释；
5. 用确定性校验器确认摘要中的精确值和引用仍有来源。

### 5.2 Logging

Logging 是证据维度，不等同于 ES/Filebeat 单一来源。ES 查询为空但 Kubernetes previous-container logs
包含真实日志时，正文必须展示该日志信号，并明确来源为 Kubernetes previous logs。ES 的空结果可作为
来源状态保留在附录，不得让整个 Logging 维度显示“未获取到”。

### 5.3 Tracing

Tracing 同样不绑定单一 provider。DeepFlow flow、Tempo trace/span 或成功查询返回的来源可核验追踪
信号只要存在，正文就至少展示一个有意义的请求、路径、状态、时延或关联实体。Tempo 未返回完整 trace
不能覆盖已经存在的 DeepFlow 信号，也不能把整个维度改写为“未获取到”。

### 5.4 真正为空的维度

若本轮查询成功但没有匹配记录，正文使用中性且准确的表达，例如“查询完成，当前时间窗口内未发现
匹配记录”。若来源调用失败，则只在相关证据段说明该来源状态和可执行的补采集方向，不在诊断概览
堆叠负面限制声明。任何情况下都不得伪造数据填充表格。

## 6. Prompt 与确定性组件边界

### `app/core/prompts.py`

`CONCLUSION_FORMATTER_PROMPT` 定义正文结构、语言风格、证据解释规则、Markdown 粗体要求及禁止泄漏
内部合同的要求。它不包含具体故障场景的示例结论或专用修复命令，避免小模型模仿单一异常模板。

### `conclusion_formatter.py`

确定性逻辑拆分为职责清晰的通用步骤：

- 从最终 observability projection 建立按维度聚合的可展示证据视图；
- 验证模型正文中的精确声明和证据引用；
- 当模型遗漏已有维度证据时，用通用摘要兜底补齐；
- 删除内部合同措辞和机器数据泄漏；
- 追加不被人类正文改写影响的机器可核验附录；
- 保持 remediation 安全合同。

兜底摘要从事实的通用字段生成，不识别故障名称。它可以陈述“实体 + 观测值/状态 + 来源”，但不得
自行生成根因或场景专用修复建议。

## 7. 数据流与失败处理

```text
validated facts / trusted final observations
                  |
                  v
        通用维度聚合与去重
                  |
                  +------> 机器可核验附录（完整、确定性）
                  |
                  v
       AI 生成人类可读正文与解释
                  |
                  v
       精确声明与引用的确定性校验
                  |
                  v
       通用缺失维度兜底 + 安全合同
                  |
                  v
              最终双层报告
```

若模型调用失败，系统使用通用事实摘要生成可读但较简洁的正文，并继续追加完整附录。若模型生成无来源
精确值，校验器删除或替换该声明。若维度存在多个 provider 且部分失败，成功证据优先展示，失败状态
留在附录；只有所有来源均没有可展示证据时才使用中性空结果或失败说明。

## 8. 测试与验收

实施必须测试先行，并至少覆盖：

1. 正文不包含四类内部合同负面话术；
2. 附录存在 Logging 或 Tracing 事实时，正文对应维度不会显示“未获取到”或“未返回可用数据”；
3. ES 为空、Kubernetes previous logs 非空时，Logging 展示真实日志信号和正确来源；
4. DeepFlow 有 flow、Tempo 为空或只有部分数据时，Tracing 展示真实 DeepFlow 信号；
5. 正文包含 AI 证据解释，并以 Markdown 粗体突出关键指标、状态、错误和实体；
6. 正文不泄漏大段 JSON、Fact ID 或内部 entity ID，附录仍完整保留；
7. 背景 Logging/Tracing 证据可以展示，但不会自动进入根因因果链；
8. `manual_only`、`requires_human_approval=true`、`actions=[]` 安全合同保持不变；
9. 模型失败时通用兜底正文仍可读且不编造；
10. 使用资源异常、配置异常、镜像/调度异常等至少三类不同夹具走同一渲染路径；生产代码不存在按
    OOM 或其他具体故障名称选择报告分支的逻辑；
11. 用真实 A006 归档回放，确认 Logging fallback、Tracing 信号、正文可读性和机器附录同时成立。

## 9. 非目标

- 不改变四节点工作流拓扑；
- 不改变 Fact Ledger schema 或来源侧查询协议；
- 不为任何具体 Pod 异常新增专用诊断代码；
- 不在没有 typed policy 时生成或执行 Kubernetes 写操作；
- 不删除机器可核验附录；
- 不把未验证的 raw observation 直接提升为精确结论。

## 10. 完成标准

只有在 Prompt、确定性渲染、单元测试、A006 回放和用户文档共同证明以下结果时才算完成：正文直接、
自信、可读；已有真实 Logging/Tracing 信号不会被显示为空；关键值被突出；根因仍完全来源可追溯；
机器附录和 remediation 安全边界不退化；新增异常场景无需添加故障专用渲染代码。
