# 工作流上下文流转说明

本文只描述当前代码的真实行为，不描述旧方案和理想方案。

当前 `/ask` 主链已经收紧为：

- 保留 4 节点：`layer -> evidence -> rca -> conclusion`
- 第一个节点不再优先做“广义分层巡检”
- 而是优先识别“当前异常 Pod 的状态关键字”，并归一化异常类型（L0-L4 层级映射已移除，layer 只判定 HEALTHY/ABNORMAL）

主线只暴露 5 个 Pod 异常 runbook：

- `l0-volume-limit`
- `l1-taint-node`
- `l2-oomkilled`
- `l3-imagepull-failed`
- `l4-config-bootstrap-fail`

`private-k8s-health-reference`、`private-k8s-query-promql-reference`、`l4-dependency-503` 仍保留文件，但不再出现在运行时 catalog 里，不作为 `/ask` 主链默认上下文。

另外，`fetch_runbook` 当前还有一层运行时 allowlist：

- `/ask` 主链允许的主线 runbook 仍然是上面 5 个
- 额外只保留 `private-k8s-query-promql-reference` 供 `/query` direct 使用
- `private-k8s-health-reference` 和 `l4-dependency-503` 即使模型猜到文件名，也会被拒绝


## 1. 两条链路

### 1.1 `/ask`

固定走完整诊断链：

```text
question
  -> layer
  -> evidence
  -> rca
  -> conclusion
```

### 1.2 `/query`

固定走 direct query：

```text
question
  -> layer(query direct)
  -> conclusion(render)
```

`/query` 不走 evidence 和 RCA。


## 2. `/ask` 的当前上下文主线

### 2.1 layer

`layer` 节点看到的内容由三部分组成：

1. `system prompt`
2. `user question`
3. 工具 schema

其中 `system prompt` 的固定组成是：

- 运行时 runbook catalog
- `LAYER_CLASSIFIER_PROMPT`
- remediation policy
- language policy

这里的关键变化是：

- catalog 里只剩 5 个 Pod 异常主线 runbook
- prompt 明确要求先给出 `primary_pod`
- prompt 明确要求给出 `pod_status_keyword`
- prompt 明确要求给出 `pod_abnormal_type`

因此 layer 的职责现在是：

1. 用最少工具锁定当前仍异常的 Pod
2. 识别状态关键字，例如 `Pending / CrashLoopBackOff / ImagePullBackOff / OOMKilled / Evicted`
3. 识别异常类型，例如 `OOMKilled / ConfigBootstrapFail`
4. 归一化 `pod_abnormal_type`（不再映射 L0-L4）

layer 的结构化输出除了原来的 `layer/layers/confidence/reasoning`，还新增：

- `primary_pod`
- `abnormal_pods`
- `pod_status_keyword`
- `pod_abnormal_type`


### 2.2 evidence

evidence 不再把上游大段文本继续塞进 `system prompt`。

当前 evidence 的上下文拆分是：

1. `system prompt`
   - `EVIDENCE_COLLECTOR_PROMPT`
   - remediation policy
   - language policy
   - 运行时 runbook catalog
2. `user message`
   - 原始问题
   - `layer_handoff`
   - archive 入口路径
   - evidence 节点自己的硬约束
3. 工具 schema

也就是说，上游业务上下文现在主要走 `user message`，不是走 system prompt。

evidence 的 `user message` 会明确告诉模型：

- 上游的 `primary_pod` 是谁
- 当前的 `pod_status_keyword` 是什么
- 当前的 `pod_abnormal_type` 是什么
- 必须先围绕这个 Pod 做证据验证
- 如果要读取落盘文件，必须调用 `read_context_archive`

这一步的设计目标很直接：

- 保留“LLM 自己决定调什么工具”
- 但把目标对象钉死，降低小模型漂移


### 2.3 rca

RCA 默认走 lite 模式，不带工具。

它看到的不是 layer 全量文本，而是 compact context：

- `layer_handoff`
- `evidence_items`
- `evidence_facts`
- `evidence_conflicts`
- `missing_evidence`
- 从 `evidence_analysis` 提取出的工具摘要

所以 RCA 看到的是“已经验证过的事实”，不是一整包历史工具全文。


### 2.4 conclusion

conclusion 默认也不再消费 `layer_full_analysis`。

它优先读取：

- `layer_handoff`
- `evidence_analysis`
- `rca_analysis`
- `thinking_events` 中的工具真实输出（`tool_result` 的完整 `result`，作为报告的核心数据段）

也就是：

- layer 负责“问题对象钉住”
- evidence 负责“事实采集”
- rca 负责“因果收敛”
- conclusion 只负责“组织输出”

## 4. `layer_handoff` 现在长什么样

`layer_handoff` 是 `/ask` 主链最关键的交接对象。

当前典型结构：

```json
{
  "diagnosis_scope": "current_state_only",
  "layer": "L2",
  "layers": ["L2"],
  "confidence": 0.91,
  "primary_problem": "Pod memhog OOMKilled",
  "primary_pod": {
    "name": "memhog-7b4c8f5d7d-abcde",
    "namespace": "aiops-e2e"
  },
  "abnormal_pods": [
    {
      "name": "memhog-7b4c8f5d7d-abcde",
      "namespace": "aiops-e2e",
      "status": "CrashLoopBackOff"
    }
  ],
  "pod_status_keyword": "CrashLoopBackOff",
  "pod_abnormal_type": "OOMKilled",
  "active_entities": [
    {"type": "Pod", "name": "memhog-7b4c8f5d7d-abcde", "namespace": "aiops-e2e"},
    {"type": "Namespace", "name": "aiops-e2e"}
  ],
  "active_signals": [
    {
      "source": "kubectl_describe",
      "signal": "Last State: OOMKilled, Exit Code: 137",
      "raw_ref": ".../001-layer-kubectl_describe.raw.txt",
      "summary_ref": ".../001-layer-kubectl_describe.summary.txt"
    }
  ],
  "possible_scenarios": [
    {"scenario": "OOMKilled", "probability": "高", "reason": "Exit Code 137"}
  ],
  "matched_runbooks": ["l2-oomkilled"],
  "must_verify": [
    "优先围绕 primary_pod 验证它为什么进入当前 pod_status_keyword / pod_abnormal_type",
    "确认 active_entities 中的对象当前仍存在于指定 namespace",
    "确认 active_signals 仍能被真实工具结果验证"
  ],
  "do_not_change": [
    "不要把 primary_pod 替换成其他 Pod，除非真实工具结果证明上游对象不存在或已恢复",
    "不要把历史 event 当成当前故障",
    "不要把计划或工具名当成证据，必须基于 tool_result"
  ]
}
```

这个对象的目标不是“完整”，而是“可行动”：

- 足够短
- 足够硬
- 能直接驱动 evidence 节点做下一步


## 5. 归档文件怎么配合上下文治理

归档根目录见：

- [archive.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/context/archive.py)

典型结构：

```text
<context_archive_root>/<run_id>/
  budget/
    layer.json
    evidence.json
    rca.json
    conclusion.json
  handoff/
    layer-to-evidence.json
    evidence-to-rca.json
    rca-to-conclusion.json
  layer/
    full_analysis.md
    handoff.json
  node_inputs/
    evidence.input.json
    rca.input.json
    conclusion.input.json
  node_outputs/
    layer.output.json
    evidence.output.json
    rca.output.json
    conclusion.output.json
  tools/
    001-layer-kubectl_describe.raw.txt
    001-layer-kubectl_describe.structured.json
    001-layer-kubectl_describe.summary.txt
```

作用分工：

- `*.raw.txt`
  - 单次工具的原始全量输出
- `*.structured.json`
  - 非 AI 的结构化裁剪结果
- `*.summary.txt`
  - 真正回注给主模型的 observation summary
- `node_inputs/*.json`
  - 某个节点实际传给 LLM 的输入载荷
- `node_outputs/*.json`
  - 某个节点写回 state 的核心输出
- `handoff/*.json`
  - 节点之间实际传递的 compact handoff
- `budget/*.json`
  - 本次调用的上下文预算记录


## 6. 一个完整例子

用户问题：

```text
我的集群有什么问题？
```

假设当前场景是 `memhog` OOM。

### 6.1 layer

模型会先调用少量工具，例如：

- `kubectl_get_by_kind_in_cluster(kind="pod")`
- `kubectl_describe(...)`

然后输出：

- `primary_pod = memhog-xxx`
- `pod_status_keyword = CrashLoopBackOff`
- `pod_abnormal_type = OOMKilled`
- `layer = L2`

下游不会收到 describe 原文，只会收到 `layer_handoff`。

### 6.2 evidence

模型接收到的 user prompt 不会重复整份 layer 分析，而是只看到：

- 原始问题
- `layer_handoff`
- archive 可读入口

它必须先输出 `evidence_plan` JSON，然后自己决定调用：

- `kubectl_describe`
- `kubectl_get_yaml`
- `kubectl_logs --previous`
- 必要时再查 events

每次工具返回后：

1. 原文落盘到 `tools/*.raw.txt`
2. 结构化裁剪写入 `tools/*.structured.json`
3. 摘要写入 `tools/*.summary.txt`
4. 回注给主模型的是 summary，不是 raw

### 6.3 rca

RCA 不会再看到一堆 describe/yaml 原文。

它看到的是：

- `primary_pod`
- `pod_status_keyword`
- `pod_abnormal_type`
- 已验证事实
- 缺失证据
- 冲突证据

于是它只需要完成：

- 根因收敛
- 因果链表达
- runbook 归因

### 6.4 conclusion

conclusion 负责把上面 3 步收敛成用户可读报告。

它不需要重新理解一遍完整集群，也不应该再碰工具全文。


## 7. 现在怎么判断“上下文优化是否生效”

看 3 个地方就够了。

### 7.1 日志里的 context budget

如果优化生效：

- `input_tokens` 或 `budget_tokens` 会明显低于旧版本
- 最大头部通常是 `node_system_prompt`、`runbook_catalog`、`user_message`
- 不应该再出现下游节点把 `layer_full_analysis` 当主要输入

### 7.2 `node_inputs/*.json`

如果优化生效：

- `evidence.input.json` 里应该看到 `layer_handoff`
- 不应该看到整份上游工具原文被直接拼进去

### 7.3 `tools/*.summary.txt`

如果优化生效：

- 主模型反复引用的是 summary
- raw 只留给人工排查和 `read_context_archive`


## 8. 当前设计边界

这套设计解决的是：

- 小模型上下文不够
- 工具原文过长
- 节点之间重复搬运同一份大文本
- evidence 漂移到泛化巡检而不是围绕异常 Pod 取证

这套设计没有承诺解决：

- 模型本身推理能力不足
- 所有工具调用都完美去重
- 任意复杂跨服务问题都能只靠 Pod 主线解决

当前主链已经明确偏向“异常 Pod 状态诊断”，不是全场景集群巡检代理。
