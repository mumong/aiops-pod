# 工作流上下文流转说明

> 注意：本文保留了旧链路排查视角，部分内容描述的是 `layer_full_analysis` 膨胀问题的历史行为。当前正式上下文管理设计与实现请优先阅读 [上下文管理设计与实现](/root/huhu/agent/combine-aiops-mcp/robusta/docs/上下文管理设计与实现.md)。

这份文档专门回答一个问题：

在当前工作流里，`/ask` 和 `/query` 的每个节点，到底会把什么上下文塞给大模型？

重点不是抽象设计，而是当前代码里的真实行为。文中会同时说明：

- 入口如何选择工作流
- `WorkflowState` 如何在节点间流转
- 每个节点实际传给 LLM 的 `system prompt`、`question/user_message`、工具和附加上下文
- 哪些地方最容易导致上下文膨胀
- 用一个完整案例演示 `/ask` 链路


## 1. 两条主链路

### `/ask`

`/ask` 固定走完整诊断链路：

`layer -> evidence -> rca -> conclusion`

配置来源见 [app/api/routes.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/api/routes.py:60)。

- `query_mode = "full"`
- `nodes = {layer: true, evidence: true, rca: true, conclusion: true}`


### `/query`

`/query` 固定走轻量查询链路：

`layer(query direct) -> conclusion(render)`

配置来源见 [app/api/routes.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/api/routes.py:157)。

- `query_mode = "direct"`
- `nodes = {layer: true, evidence: false, rca: false, conclusion: true}`


## 2. 状态怎么流转

每次请求先创建一个 `initial_state`，核心字段见 [app/core/workflow/executor.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/executor.py:157) 和 [app/core/workflow/state.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/state.py:16)。

初始状态最重要的输入只有两个：

- `question`
- `run_id`

后面各节点逐步往 `WorkflowState` 里写这些关键字段：

- `layer`, `layers`, `layer_analysis`, `layer_full_analysis`, `key_entities`, `possible_scenarios`
- `evidence_items`, `evidence_analysis`, `evidence_completeness`, `query_result`
- `deterministic_decision`, `root_cause`, `causal_chain`, `rca_analysis`, `primary_runbook_id`
- `conclusion`, `conclusion_formatted`
- `thinking_events`

注意：

- `layer_analysis` 是结构化 JSON 字符串
- `layer_full_analysis` 是更大的文本，包含阶段 1 的工具原始输出
- `evidence_analysis` 和 `rca_analysis` 也都是字符串化后的 JSON
- `thinking_events` 会累计所有节点的中间事件，尤其是 `tool_result`


## 3. 所有 `_call_llm()` 节点共有的上下文拼装

凡是走基类 `WorkflowNode._call_llm()` 的节点，都会在真正调用 LLM 前做统一拼装，逻辑见 [app/core/workflow/nodes/base.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/base.py:108)。

统一会做三件事。

### 3.1 注入 runbook catalog

如果该节点没有禁用 catalog 注入，就会在 `system prompt` 最前面插入整份 runbook 目录，而不是 runbook 正文。

格式大致是：

```text
# Available Runbooks
If one or more runbooks match the issue, use the fetch_runbook tool for each relevant runbook.

- l2-oomkilled.md: ...
- l3-imagepull-failed.md: ...
- private-k8s-health-reference.md: ...
...
```

来源见 [app/core/workflow/nodes/base.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/base.py:131)。

这意味着：

- 注入的是目录，不是正文
- 真正正文只有模型显式调用 `fetch_runbook` 后才会拿到
- catalog 的长度和你当前初始化时加载的 runbook 数量成正比


### 3.2 注入修复权限约束

如果 `AUTO_REMEDIATE=false`，会在 `system prompt` 末尾追加一段“禁止执行修复操作”的规则。

来源见 [app/core/workflow/nodes/base.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/base.py:149)。


### 3.3 传入所有工具

节点拿到的是 `executor.mcp_tools`，也就是：

- 所有 MCP 工具
- 内置 `fetch_runbook`

来源见 [app/core/workflow/executor.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/executor.py:142) 和 [app/core/service.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/service.py:174)。


## 4. 图路由怎么决定

路由逻辑见 [app/core/workflow/graph.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/graph.py:171)。

- `layer == HEALTHY`：直接到 `conclusion`
- `layer == QUERY` 且 `query_mode == direct`：直接到 `conclusion`
- 其他情况：正常进入下游

因此：

- `/ask` 下即使问的是查询句子，也可能先走 `layer -> evidence -> rca -> conclusion`
- `/query` 下只要 `layer` 判成 `QUERY`，就不会经过 `evidence` 和 `rca`


## 5. 各节点真实上下文

下面是最重要的部分。


## 5.1 layer 节点

代码入口见 [app/core/workflow/nodes/layer_classifier.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/layer_classifier.py:246)。

### `/ask` 模式下

`layer` 使用 `LAYER_CLASSIFIER_PROMPT`，来源见 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py:109)。

真实发给模型的上下文由三部分组成：

1. `system prompt`
   - runbook catalog
   - `LAYER_CLASSIFIER_PROMPT`
   - auto-remediate 限制

2. `question`
   - 就是用户原始问题本身
   - 没有额外拼接 layer/evidence/rca 内容

3. `tools`
   - 全量 MCP 工具
   - `fetch_runbook`

所以 `/ask` 的 `layer` 节点，模型看到的上下文并不复杂，主要是：

- 一大段系统规则
- 一整份 runbook 目录
- 原始用户问题
- 全量工具

### `/query` direct 模式下

`layer` 改用 `LAYER_QUERY_DIRECT_PROMPT`，来源见 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py:252)。

有一个非常关键的差异：

- direct query 模式下，`layer.should_inject_runbook_catalog()` 返回 `False`
- 也就是不注入整份 runbook catalog

来源见 [app/core/workflow/nodes/layer_classifier.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/layer_classifier.py:63)。

所以 `/query` 下的 `layer` 实际上下文是：

1. `system prompt`
   - 只有 `LAYER_QUERY_DIRECT_PROMPT`
   - 再加 auto-remediate 限制

2. `question`
   - 用户原始查询

3. `tools`
   - 仍然是全量工具

这里虽然不注入 catalog，但 prompt 本身会要求：

- 涉及 Prometheus 时优先 `fetch_runbook private-k8s-query-promql-reference.md`

也就是：

- `/query` 没有 catalog 噪音
- 但模型仍可以主动去拿指定 runbook


### layer 的输出怎么变成下游上下文

`layer` 最重要的两个输出：

- `layer_analysis`
- `layer_full_analysis`

其中 `layer_full_analysis` 不是简单 JSON，而是：

- LLM 最终文本
- 加上所有成功 `tool_result` 的原始输出

构造逻辑见 [app/core/workflow/nodes/layer_classifier.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/layer_classifier.py:421)。

大致格式：

```text
[LLM 最终输出]

# 工具返回的原始数据（以此为准）
[tool1]
...
[tool2]
...
```

如果太长，会压缩到大约 30000 字符，再传下游，逻辑见 [app/core/workflow/nodes/layer_classifier.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/layer_classifier.py:278) 和 [app/core/workflow/nodes/base.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/base.py:200)。


## 5.2 evidence 节点

代码入口见 [app/core/workflow/nodes/evidence_collector.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/evidence_collector.py:77)。

这是当前最容易膨胀的节点。

### evidence 的 `system prompt` 由什么组成

基础 prompt 是 `EVIDENCE_COLLECTOR_PROMPT`，来源见 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py:328)。

然后代码会继续往 `system prompt` 里追加三块内容，见 [app/core/workflow/nodes/evidence_collector.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/evidence_collector.py:389)。

#### 第一块：格式化后的 evidence prompt 本体

会把下面两个变量填进去：

- `{layer}`
- `{possible_scenarios}`

#### 第二块：上游 layer 完整分析

如果 `layer_full_analysis` 存在，会把它整段拼到 `system prompt` 里：

```text
# 上游问题定位结果（已完成，不要重复分析或重新获取 runbook）
[layer_full_analysis]
```

这块往往很大，因为它可能包含：

- layer 的 JSON
- layer 的工具原始输出
- 压缩后的长上下文

#### 第三块：关键实体

会把 `key_entities` 再拼进去，格式类似：

```text
# 已提取的关键实体
  - Pod: xxx
  - Namespace: xxx
```

#### 第四块：严格重试提示

如果第一轮只拿到了 `evidence_plan` 没有真实 `tool_result`，第二轮会在 `system prompt` 末尾再追加一段“上一轮结果被拒绝”的硬约束，来源见 [app/core/workflow/nodes/evidence_collector.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/evidence_collector.py:407)。

### evidence 的 `question`

非常重要：

`evidence` 传给 `_call_llm()` 的 `question` 仍然只是原始用户问题，没有把 layer 结果拼到 user message 里。

见 [app/core/workflow/nodes/evidence_collector.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/evidence_collector.py:418)。

所以 evidence 的模型输入形态是：

- 巨大的 `system prompt`
- 很短的 `question`

这意味着当前 evidence 非常依赖模型对 `system prompt` 的长期保持能力。


### evidence 最终产出的上下文

执行完后会写回：

- `evidence_items`
- `evidence_analysis`
- `evidence_completeness`
- `query_result`（仅 layer=QUERY 时）

其中 `evidence_analysis` 是一个很肥的 JSON 字符串，内部至少包含：

- `evidence_plan`
- `tool_results`
- `tool_data`
- `llm_analysis`
- `collection_summary`
- `evidence_inventory`
- `missing_reasons`
- `early_stop`

见 [app/core/workflow/nodes/evidence_collector.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/evidence_collector.py:203)。

这也是后面 `rca` 和 `conclusion` 的一个重要膨胀源。


## 5.3 rca 节点

代码入口见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:61)。

### 默认模式：lite

当前默认是 `lite`，不是工具模式。逻辑见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:168)。

这意味着当前大多数情况下，`rca` 不走 `_call_llm()`，而是直接 `call_simple_json()`。

因此默认 `rca`：

- 不注入 runbook catalog
- 不带工具
- 不追加 auto-remediate 限制

### rca 的 `system prompt`

`system prompt` 来自 `ROOT_CAUSE_ANALYZER_PROMPT.format(layer=..., evidence_summary=...)`

来源见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:220) 和 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py:419)。

这里最关键的是：`evidence_summary` 本身已经不是简单摘要，而是又拼了很多上游内容。

### rca 的 `evidence_summary` 包含什么

先来自 `evidence_items` 的摘要：

- 每条证据的 collected 状态
- description
- value

见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:149)。

然后又会把 `layer_full_analysis` 整段再拼进去：

```text
# 问题定位结果（layer 节点输出）
[layer_full_analysis]

# 证据采集结果
[evidence_items summary]
```

见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:86)。

然后再从 `evidence_analysis` 里提取补充数据：

- `llm_analysis`
- `tool_data`

见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:96) 和 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:407)。

所以默认 `rca` 实际看到的是：

1. `system prompt`
   - RCA 规则
   - 直接内嵌的 `evidence_summary`

2. `user_message`
   - 用户问题
   - 同一份 `evidence_summary` 再来一次

见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:225)。

也就是说，默认 `rca` 的一个特点是：

- 不带工具
- 但会双份携带 `evidence_summary`


### rca full 模式

如果手工把 `WORKFLOW_RCA_MODE=full`，它会改走 `_call_llm()`，见 [app/core/workflow/nodes/root_cause_analyzer.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/root_cause_analyzer.py:275)。

那时它会重新具备：

- runbook catalog
- 工具
- auto-remediate 限制

但 prompt 里又明确告诉模型不要重复采集。


## 5.4 conclusion 节点

代码入口见 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:94)。

### `/query` direct 模式

如果：

- `layer == QUERY`
- `query_mode == direct`
- 且 `query_result` 已存在

那么 `conclusion` 不调用 LLM，直接 render。

见 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:128)。

这条路径上下文最干净：

- 没有 runbook catalog
- 没有工具
- 没有第二次 LLM 理解


### `/ask` 下的 conclusion

默认 `/ask` 会调用 `AICall.call_simple()` 生成最终报告，见 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:349)。

它不走 `_call_llm()`，所以默认不会有：

- runbook catalog
- 工具
- auto-remediate 注入

### conclusion 的 `system prompt`

来自 `CONCLUSION_FORMATTER_PROMPT`，见 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py:498)。

如果是 QUERY 兼容总结路径，还会额外拿到 `QUERY_CONCLUSION_INSTRUCTION_ZH` 作为 `instruction` 拼进 user message，见 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py:643) 和 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:214)。

### conclusion 的 `user_message`

这是当前另一个明显的上下文大头。

它会拼入：

1. `question`
2. `layer_analysis`
   - 优先 `layer_full_analysis`
   - 没有才回退 `layer_analysis`
3. `evidence_analysis`
4. `rca_analysis`
5. 从 `evidence_analysis` 再抽一遍 `evidence_stats_section`
6. 从全局 `thinking_events` 再抽一遍 `tool_data_text`
7. 如果存在，再拼 `query_result_section`
8. 最后拼模式级 `instruction`

见 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:237) 和 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:266)。

其中：

- `tool_data_text` 来自所有节点 `thinking_events` 里的成功 `tool_result` 预览，最多 20 条，见 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:930)
- 如果总 token 估算超预算，会优先压缩 `layer_analysis / evidence_analysis / rca_analysis` 三大段，见 [app/core/workflow/nodes/conclusion_formatter.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/conclusion_formatter.py:298)


## 6. 一个完整案例：`现在我的集群有什么问题？不要考虑之前的历史情况`

下面用 `/ask` 来串一次真实上下文流转。


## 6.1 请求进入 `/ask`

用户问题：

```text
现在我的集群有什么问题？不要考虑之前的历史情况
```

工作流配置：

- `query_mode = full`
- 节点链路 = `layer -> evidence -> rca -> conclusion`


## 6.2 layer 节点拿到什么

### system prompt

由三部分组成：

1. runbook catalog
2. `LAYER_CLASSIFIER_PROMPT`
3. 禁止自动修复约束

### question

只有一句：

```text
现在我的集群有什么问题？不要考虑之前的历史情况
```

### tools

全量 MCP 工具 + `fetch_runbook`

### layer 典型行为

模型通常会：

- 先用 `kubectl_get_by_kind_in_cluster` 看 node / pod
- 发现异常 Pod 后 `describe`
- 如果命中特定场景，再 `fetch_runbook`

### layer 输出

假设它最终识别到：

- `layer = L4`
- `key_entities = [Pod, Namespace]`
- `possible_scenarios = [配置缺失, 启动校验失败]`

并生成：

- `layer_analysis`：结构化 JSON 字符串
- `layer_full_analysis`：JSON + 成功工具输出拼接文本


## 6.3 evidence 节点拿到什么

### system prompt

evidence 的 `system prompt` 会非常长，因为它包含：

1. runbook catalog
2. `EVIDENCE_COLLECTOR_PROMPT.format(layer="L4", possible_scenarios="...")`
3. `# 上游问题定位结果`
   - 整段 `layer_full_analysis`
4. `# 已提取的关键实体`
   - Pod / Namespace 等

如果第一轮 plan-only 失败，还会再多一段：

5. `# 上一轮结果被系统拒绝`

### question

仍然只是原始问题：

```text
现在我的集群有什么问题？不要考虑之前的历史情况
```

### tools

还是全量工具

### evidence 典型行为

理想情况下，它应该：

- 先生成 `evidence_plan`
- 再调用例如 `kubectl_get_yaml`、日志工具、事件工具
- 把工具输出转成 `evidence_items`

### evidence 输出

它会写回：

- `evidence_items`
- `evidence_completeness`
- `evidence_analysis`

其中 `evidence_analysis` 里又带：

- 计划
- 工具输出摘要
- tool_data
- collection_summary
- missing_reasons


## 6.4 rca 节点拿到什么

默认 `rca_mode=lite` 时：

- 不再拿 catalog
- 不带工具
- 只做文本分析

### system prompt

`ROOT_CAUSE_ANALYZER_PROMPT`，其中已经直接嵌了 `evidence_summary`

### user_message

又再带一遍：

- 用户问题
- `evidence_summary`

而 `evidence_summary` 本身已经包括：

- `layer_full_analysis`
- `evidence_items`
- 从 `evidence_analysis` 提取的 `llm_analysis`
- 从 `evidence_analysis` 提取的 `tool_data`

所以 `rca` 并不轻。它只是“不带工具”，不是“上下文小”。


## 6.5 conclusion 节点拿到什么

默认 `/ask` 下 `conclusion` 还会把上面几层再汇总一次。

### system prompt

固定的 `CONCLUSION_FORMATTER_PROMPT`

### user_message

按顺序拼入：

1. 用户问题
2. 阶段1分析
   - 通常是 `layer_full_analysis`
3. 阶段2分析
   - `evidence_analysis`
4. 阶段3分析
   - `rca_analysis`
5. evidence 统计补丁
6. thinking_events 提取出的 tool preview
7. 模式指令

所以 conclusion 是最终最大的汇总点。


## 7. 当前最主要的上下文膨胀点

如果只看代码里的真实行为，最大的四个膨胀点是：

### 7.1 runbook catalog 在多个节点重复注入

当前凡是走 `_call_llm()` 的节点，默认都会注入整份 catalog。

这会影响：

- `layer`（ask 模式）
- `evidence`
- `rca` full 模式

不会影响：

- `query direct` 的 layer
- 默认 lite 模式的 rca
- conclusion


### 7.2 `layer_full_analysis` 太重

它会把成功工具的原始输出一起打包传下游。

这意味着同一份工具结果至少会重复出现在：

- `layer_full_analysis`
- `evidence` 的 system prompt
- `rca` 的 evidence_summary
- `conclusion` 的 layer_analysis 段


### 7.3 `evidence_analysis` 是一个“胖 JSON”

里面不只是结论，还有：

- plan
- llm_analysis
- tool_data
- inventory
- missing reasons

这份 JSON 后面又会被：

- `rca` 解析再抽一遍
- `conclusion` 直接整段再吃一遍


### 7.4 conclusion 是最终聚合点

它会把前三个阶段的大块内容重新拼成一个新 user message。

所以即使前面某个节点还能撑住，最后也很可能在 conclusion 膨胀。


## 8. 从 Langfuse 里怎么看这些东西

如果你在 Langfuse 里看每个节点的 LLM 请求，建议按下面方式理解。

### 看 `layer`

重点看：

- `system prompt` 前面是否有整份 runbook catalog
- `question` 是否只有原始用户问题
- 输出后是否附带了真实工具调用


### 看 `evidence`

重点看：

- `system prompt` 里是否已经拼入整段 `layer_full_analysis`
- 是否又有 catalog
- 是否出现“上一轮结果被系统拒绝”的 retry block
- `question` 是否仍然只是原始问题


### 看 `rca`

重点看当前到底是：

- lite
- full

如果是 lite：

- 不应看到工具 schema
- 不应看到 catalog
- 但会看到非常长的 `evidence_summary`


### 看 `conclusion`

重点看：

- `user_message` 是否一次性拼了 layer/evidence/rca 三大段
- 是否又附带了 tool preview
- 是否经过压缩


## 9. 一句话总结

当前链路里：

- `layer` 的输入相对还算干净
- `evidence` 是第一个明显的“system prompt 膨胀点”
- `rca` 默认不带工具，但上下文并不小
- `conclusion` 是最终最大的汇总点

如果你接下来要优化本地模型的稳定性，优先关注的不是“每个节点都一样大”，而是：

1. `evidence` 的 system prompt 是否过重
2. `layer_full_analysis` 是否在下游被重复注入过多次
3. `conclusion` 是否把前面的大块 JSON 又完整吞了一遍
