# 上下文管理设计与实现

本文说明当前 AIOps Copilot 如何管理 LLM 上下文，重点回答：

- 每个节点之间传递什么信息
- 大工具输出如何避免塞爆本地小模型上下文
- `layer_full_analysis` 如何被替换为 `layer_handoff`
- token budget 日志怎么看
- context archive 存在哪里、怎么排查
- 哪些能力已经实现，哪些只是预留设计

当前设计目标很明确：LLM 仍然自主决定调用什么工具，但系统必须控制上下文大小，把全量数据落盘，把模型可见内容压缩成结构化、短而硬的事实摘要。

当前 `/ask` 主链还有一个新的约束：

- 主链只围绕异常 Pod 状态展开
- runtime runbook catalog 只暴露 5 个 Pod 异常主线 runbook
- `fetch_runbook` 还会额外拒绝 `private-k8s-health-reference` 和 `l4-dependency-503`
- `private-k8s-query-promql-reference` 仅保留给 `/query` direct
- 第一个节点先产出 `primary_pod / pod_status_keyword / pod_abnormal_type`
- 然后下游 evidence/rca/conclusion 都围绕这个 handoff 展开


## 1. 背景问题

本地模型从 64K 上下文进一步切到 32B 小模型后，主要风险不是单次工具调用是否成功，而是长上下文下的注意力漂移。

旧链路中有几个典型问题：

- `layer_full_analysis` 会把 layer 阶段的完整分析和工具原始输出继续传给 evidence、RCA、conclusion。
- 同一份工具结果可能重复出现在 `layer_full_analysis`、下游 prompt、`thinking_events`、最终报告上下文里。
- 重型 K8s 工具如 `kubectl_describe`、`kubectl_get_yaml`、`kubectl_get_by_kind_in_cluster` 可能返回很长内容。
- evidence 节点曾经把大量上游内容拼到 system prompt，导致模型容易忘记“必须调用工具”这类硬约束。

当前实现的核心变化：

- 全量原始内容落盘到 context archive。
- 跨节点只传 `layer_handoff`、证据摘要、归档引用。
- 工具 observation 回注给主 agent 前先摘要。
- 节点间业务上下文主要走 user message，而不是继续往 system prompt 里塞大段上游文本。
- 每次 LLM 调用前记录 token budget，方便定位哪个节点上下文过重。


## 2. 总体数据流

### 2.1 `/ask`

```text
用户问题
  -> layer
      -> 调用工具定位问题
      -> 生成 layer_analysis
      -> 生成 layer_handoff
      -> full_analysis 落盘
  -> evidence
      -> 基于 layer_handoff 构造节点专用 user message
      -> LLM 自主调用只读工具采集证据
      -> 工具原始输出落盘，摘要回注模型
      -> 生成 evidence_items / evidence_facts / conflicts / missing
  -> rca
      -> 使用 layer_handoff + bounded evidence context
      -> 生成 root_cause / causal_chain / rca_analysis
  -> conclusion
      -> 使用 compact layer context + evidence/RCA
      -> 输出最终报告
```

### 2.2 `/query`

```text
用户问题
  -> layer(query direct)
      -> 使用 query 专用 prompt
      -> LLM 自主调用 Prometheus/K8s 工具
      -> 直接产出 query_result
  -> conclusion
      -> 渲染结构化查询结果
```

`/query` 不经过 evidence 和 RCA。查询类 PromQL 知识通过 query 专用 prompt 和 query runbook 引导，不再依赖诊断链路里的大段 runbook catalog。


## 3. WorkflowState 传递策略

状态定义见 [app/core/workflow/state.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/state.py)。

当前 `WorkflowState` 仍是 LangGraph 节点间的主数据板，但不再把大文本作为默认下游输入。

### 3.1 仍然传递的结构化字段

- `question`：用户原始问题。
- `run_id`：本次请求 ID，也是 archive 子目录名。
- `layer` / `layers`：主层级和多层级判断。
- `layer_analysis`：layer 的结构化 JSON 字符串。
- `layer_handoff`：给下游使用的结构化交接对象。
- `layer_archive_ref`：layer 全量内容和 handoff 的归档路径。
- `context_archive_ref`：本次 run 的归档根目录。
- `tool_artifact_refs`：工具 raw/structured/summary 文件引用。
- `evidence_items`：证据项列表。
- `evidence_facts`：已验证事实摘要。
- `evidence_conflicts`：冲突或负向证据。
- `missing_evidence`：缺失证据。
- `rca_analysis` / `root_cause` / `causal_chain`：RCA 输出。
- `thinking_events`：节点执行过程中的 AI 消息、工具调用、工具结果事件。

### 3.2 被废弃的大字段

`layer_full_analysis` 保留字段但默认置为 `None`。

原因：它曾经包含 layer 阶段的完整 LLM 输出和所有成功工具原始输出，是下游上下文膨胀的主要来源。当前 full analysis 只写入 archive，默认不再进入 evidence/RCA/conclusion prompt。


## 4. layer_handoff

`layer_handoff` 是当前上下文治理的核心对象，由 layer 节点生成，逻辑见 [app/core/workflow/nodes/layer_classifier.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/layer_classifier.py)。

它的职责不是保存全文，而是告诉下游：

- 上游认为当前问题是什么
- 涉及哪些真实实体
- 已经看到了哪些关键工具信号
- 哪些 runbook 被 fetch 过
- evidence 必须验证什么
- 哪些东西不能漂移
- 如果需要看全文，归档文件在哪里

典型结构：

```json
{
  "diagnosis_scope": "current_state_only",
  "layer": "L3",
  "layers": ["L3"],
  "confidence": 0.9,
  "primary_problem": "多个 Pod 处于 ImagePullBackOff，事件指向镜像仓库访问超时",
  "primary_pod": {
    "name": "imagepull-fail-victim",
    "namespace": "aiops-e2e"
  },
  "abnormal_pods": [
    {
      "name": "imagepull-fail-victim",
      "namespace": "aiops-e2e",
      "status": "ImagePullBackOff"
    }
  ],
  "pod_status_keyword": "ImagePullBackOff",
  "pod_abnormal_type": "ImagePullBackOff",
  "active_entities": [
    {"type": "Pod", "name": "imagepull-fail-victim", "namespace": "aiops-e2e"}
  ],
  "active_signals": [
    {
      "source": "kubectl_events",
      "signal": "Failed to pull image ... i/o timeout",
      "raw_ref": "/tmp/aiops/reports/context_archives/<run_id>/tools/001-layer-kubectl_events.raw.txt",
      "summary_ref": "/tmp/aiops/reports/context_archives/<run_id>/tools/001-layer-kubectl_events.summary.txt"
    }
  ],
  "possible_scenarios": ["镜像仓库网络不可达", "DNS 或防火墙异常"],
  "matched_runbooks": ["l3-imagepull-failed.md"],
  "must_verify": [
    "优先围绕 primary_pod 验证它为什么进入当前 pod_status_keyword / pod_abnormal_type",
    "确认 active_entities 中的对象当前仍存在于指定 namespace",
    "确认 active_signals 仍能被真实工具结果验证",
    "如果工具返回 NotFound、空事件或 namespace 不匹配，记录为冲突/负向证据"
  ],
  "do_not_change": [
    "不要把 primary_pod 替换成其他 Pod，除非真实工具结果证明上游对象不存在或已恢复",
    "不要把上游 namespace、Pod、Service、Node 名称改写成其他对象",
    "不要把历史 event 当成当前故障",
    "不要把计划或工具名当成证据，必须基于 tool_result"
  ],
  "archive_ref": "/tmp/aiops/reports/context_archives/<run_id>/layer/full_analysis.md"
}
```

### 4.1 为什么它比 full_analysis 更适合小模型

- 字段固定，模型不需要从长文本里找实体。
- `primary_pod`、`pod_status_keyword`、`pod_abnormal_type` 直接把 evidence 的取证中心钉住。
- `must_verify` 和 `do_not_change` 明确压住 evidence 的执行边界。
- `active_signals` 是摘要，不是工具全文。
- `archive_ref` 保留人工排查入口，但不会自动拉回 prompt。

### 4.2 Pydantic 结构化合同

四节点工作流中所有关键 JSON 边界都应先经过 Pydantic 校验和归一化，再写入 state 或被下游消费。当前合同定义在 [app/core/workflow/schemas.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/schemas.py)。

已覆盖的主要对象：

- `LayerOutput`：约束 layer LLM 的原始 JSON 输出。它会归一化 `confidence`、`layers`、`primary_pod`、`abnormal_pods`、`key_entities` 和 `possible_scenarios`。
- `LayerHandoff`：约束 layer 到 evidence/RCA/conclusion 的结构化交接。`_build_layer_handoff()` 返回前会执行 `LayerHandoff.model_validate(...).model_dump()`。
- `IssueGroup`：约束多异常组，包含 `status_keywords`、`pod_abnormal_type`、`compatible_layers`、`primary_entities`、`is_primary` 和 `possible_scenarios`。
- `QueryResult`：约束 `/query` direct 和 query evidence normalization 的结果。它兼容旧格式中的字符串 `columns / missing / sources`，并归一化为对象数组。
- `EvidencePlanOutput` / `EvidenceCollectionOutput`：约束 evidence 的计划和最终采集统计。
- `RCAOutput`：约束 RCA 输出；conclusion 消费 RCA 时也会先尝试校验。
- `ContextCompactionSummary`：约束 evidence 运行时上下文压缩结果。

关键原则：

- LLM 可以少写或写得不够统一，但不能直接决定下游合同形状。
- 当前异常列表和多异常组优先来自工具 structured 结果和代码归一化，而不是依赖 LLM 是否把所有异常都写进 `possible_scenarios`。
- `LayerOutput.possible_scenarios` 仍保留为全局场景，但 evidence 应优先看 `LayerHandoff.issue_groups[].possible_scenarios`。
- `issue_groups[].possible_scenarios` 会按 `pod_abnormal_type` 补齐默认诊断方向。例如 `ImagePullFailed` 会包含镜像 tag、认证、仓库网络；`TerminatingStuck` 会包含 finalizer、kubelet 删除流程、volume detach。
- state 中保留 JSON 字符串字段是为了兼容前端和旧归档；节点内部和消费端应优先使用 Pydantic 对象或 Pydantic 校验后的 dict。


## 5. Context Archive

归档实现见 [app/core/context/archive.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/context/archive.py)。

默认路径优先级：

1. 环境变量 `AIOPS_CONTEXT_ARCHIVE_ROOT`
2. `/tmp/aiops/context_archives`
3. `/tmp/aiops/reports/context_archives`

K8s 部署中当前显式配置为：

```yaml
AIOPS_CONTEXT_ARCHIVE_ROOT: /tmp/aiops/reports/context_archives
```

并通过 initContainer 初始化权限：

```text
mkdir -p /tmp/aiops/reports/context_archives && chmod -R 777 /tmp/aiops/reports
```

K8s 部署使用 PVC 挂载 `/tmp/aiops/reports`，PVC 使用默认 StorageClass：

```yaml
persistentVolumeClaim:
  claimName: aiops-reports-pvc
```

PVC 带有 `helm.sh/resource-policy: keep` 注解。执行 `helm uninstall` 或删除 Deployment 时，Pod 会被删除，但 PVC 和其中的 context archive 默认保留。只有显式删除 PVC 或底层 PV 回收策略清理数据时，历史归档才会丢失。

### 5.1 目录结构

## 6. Tool Observation 管理

工具 observation 处理实现见 [app/core/context/observation.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/context/observation.py)，调用入口见 [app/core/aicall/client.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/aicall/client.py)。

核心链路：

```text
LLM 决定调用工具
  -> MCP 工具执行
  -> AICall 收到 ToolMessage
  -> ObservationProcessor 处理
  -> raw / structured / summary 落盘
  -> ToolMessage.content 被替换成 bounded summary
  -> 主 agent 继续基于 summary 推理
```

关键点：不是只压缩日志里的 `thinking_events`，而是把 LangChain agent loop 里回注给模型的 `ToolMessage.content` 也替换成摘要。否则主模型仍会看到原始长输出。

### 6.1 重型工具

当前有专门处理逻辑的重型工具：

- `kubectl_get_by_kind_in_cluster`
- `kubectl_get_by_kind_in_namespace`
- `kubectl_get_yaml`
- `kubectl_describe`
- `kubectl_events`
- `kubernetes_jq_query`
- `kubernetes_tabular_query`

处理策略：

- 表格类输出提取异常行、状态统计、样例行。
- `describe` 提取 Name、Namespace、Node、Status、Reason、Message、State、Last State、Warning events。
- `events` 优先保留 Warning、Failed、BackOff、x509、ImagePullBackOff 等事件。
- `yaml` 不做完整 YAML 解析，依赖正则保留高价值字段，例如 kind、metadata、image、resources、env、volumes、status。
- 空结果会明确标记为负向观察，例如 `no_events_found`，不能当作异常已验证。

### 6.2 中等工具

当前中等工具包括：

- `kubectl_get_by_name`
- `kubectl_find_resource`
- `kubectl_lineage_children`
- `kubectl_lineage_parents`
- `execute_prometheus_instant_query`
- `get_prometheus_target`

如果输出本身不大，会直接保留；如果过大，会走通用摘要和截断保护。

### 6.3 摘要策略配置

工具 observation 摘要策略只由 ConfigMap 中的 `workflow.observation_summary` 控制：

```yaml
workflow:
  observation_summary:
    mode: rule
    max_chars: 3000
```

模式：

- `rule`：默认。先走规则摘要；只有规则摘要超过 `max_chars` 时才调用 LLM 兜底总结。
- `ai`：每一次工具 observation 都强制调用 LLM summarizer，再把 LLM summary 回注给主 Agent。

日志判断方式：

```text
processor=k8s_table       # 规则摘要
processor=k8s_table+llm   # 规则提取后又调用 LLM summarizer
processor=fallback_truncate # processor 异常，截断回退
```

注意：`ai` 模式能获得更统一的自然语言摘要，但会显著增加 LLM 调用次数和延迟。小模型或慢推理服务默认建议保持 `rule`。

`AIOPS_OBSERVATION_SUMMARY_MODE` 和 `AIOPS_OBSERVATION_SUMMARY_MAX_CHARS` 不再作为部署配置入口，避免 Secret 环境变量覆盖 ConfigMap 后导致实际策略不透明。Secret 只保留模型连接、上下文窗口和 tokenizer 这类部署环境配置。

### 6.4 Evidence 运行时上下文压缩

Evidence 节点是最容易上下文膨胀的节点，主要来自两类动态内容：

- `ai_messages`：小模型多轮“思考、计划修正、工具选择解释”会累计进入 agent 历史。
- `tool_observations`：多次 kubectl/Prometheus 工具返回会累计进入下一轮模型输入。

当前实现增加了可配置的运行时压缩，仅默认作用于小上下文模型：

```yaml
workflow:
  context_compaction:
    enabled: true
    nodes:
      - evidence
    max_context_window: 35000
    trigger_ratio: 0.70
    max_compactions_per_call: 1
    summary_max_tokens: 1200
```

触发条件：

- 当前节点在 `nodes` 中，默认只包含 `evidence`。
- 模型上下文窗口 `context_window <= max_context_window`，默认 35000。
- 静态上下文 + 当前动态 `ai_messages/tool_observations` 的估算使用率达到 `trigger_ratio`，默认 70%。

压缩方式：

- 使用 `ContextCompactionSummary` Pydantic schema 做 structured output，不依赖提示词手写 JSON 字段。
- 摘要字段包括过程摘要、证据计划、已完成项、未完成项、关键事实、负向事实、冲突、丢弃噪声和下一步焦点。
- 压缩摘要作为 `context_summary` 事件插入 `thinking_events`。
- 原始 `evidence_plan` AI 消息保留，避免后续计划解析失效。
- 原始 `tool_result` 事件保留；若已有 `raw_ref/structured_ref/summary_ref` 且结果很长，只裁剪 `result` 文本并保留归档引用。
- 已经进入 agent 历史的非 plan 长 AI 消息会被回写为短占位，降低后续轮次继续携带大段中间思考的风险。

兼容边界：

- 压缩不改变证据完整率公式，仍然按 `evidence_plan` 中可计量项的采集完成情况计算。
- 压缩失败时不修改 `thinking_events`，继续使用原始上下文。
- 工具原始输出仍以 `raw_ref/structured_ref/summary_ref` 归档，可用于人工追溯和后续更精细提取。

日志判断方式：

```text
runtime context compacted | node=evidence usage=83% window=32000
```

压缩后的 budget 中会出现 `context_summaries` 组件，同时 `ai_messages` 和部分 `tool_observations` 应明显降低。

### 6.5 Evidence 多异常组与计划解析合同

Evidence 节点现在把 layer 阶段的 Pod 表结构化结果作为采证核心输入，而不是只依赖 `primary_pod`。

layer 会从当前 `kubectl get pods -A` 的 structured 输出中提取：

- `current_abnormal_summary.status_counts`
- `current_abnormal_summary.selected_rows`
- `issue_groups`

正常状态过滤口径：

- `Running`
- `Completed`
- `Succeeded`
- `Ready`
- `Bound`
- `Active`

除上述正常状态外，其他状态都应进入异常摘要，并至少被最小验证。比如同一次扫描得到：

```json
{
  "status_counts": {
    "ImagePullBackOff": 3,
    "ErrImagePull": 1,
    "Terminating": 1,
    "Running": 46
  }
}
```

Evidence 的计划不能只覆盖 ImagePull 主问题，还必须给 `Terminating` 异常组至少安排当前状态和一个关键事件/配置/依赖信号检查。主异常组仍按完整维度采集，非主异常组只做最小验证，避免遗漏但不扩展成全量巡检。

给 Evidence LLM 的 user message 会额外生成一个短区块：

```text
# 当前异常结构化摘要（必须优先审查）
status_counts:
- ImagePullBackOff: 3
- ErrImagePull: 1
- Terminating: 1
issue_groups:
- g1: statuses=ImagePullBackOff, ErrImagePull, type=ImagePullFailed, ...
- g2: statuses=Terminating, type=TerminatingStuck, ...
```

同时，传给 LLM 的 `layer_handoff` 会做精简：

- 保留 `primary_pod / abnormal_pods / issue_groups / current_abnormal_summary / pod_status_keyword / pod_abnormal_type / active_signals / must_verify` 等采证必需字段。
- 递归移除 `archive_ref / raw_ref / summary_ref / structured_ref / input_ref / output_ref` 等归档路径。
- 归档路径仍写入 archive 文件，供人工排障使用，但不作为模型采证上下文。

计划解析合同也更严格：

- 只接受合法 JSON 的 `evidence_plan`。
- `evidence_plan` 会通过 `EvidencePlanOutput` Pydantic schema 校验。
- 不再从自由文本或最终分析里的 `kubectl ...` 命令提取 `cmd_0/cmd_1` 这类伪计划。

这个修改修复了一类统计污染：模型实际执行了工具，但最终消息输出了畸形 JSON 或普通命令列表，旧逻辑会把自由文本命令当成新计划，导致完整度从真实工具执行结果变成 `1/10` 之类的错误值。现在这类畸形输出会被拒绝为无效计划，系统保留早期合法计划，并按真实工具结果匹配。

### 6.6 LLM 兜底摘要

当规则摘要仍然超过预算，或者某些工具没有专用处理器时，会调用本地模型做单条 observation 摘要。

入口是 `AICall._summarize_tool_observation()`，prompt 来源是：

```python
get_workflow_prompt("tool_observation_summarizer")
```

约束：

- 它不是诊断 agent。
- 只压缩单次工具输出。
- 不做根因分析。
- 必须保留资源名、namespace、状态、错误、数值。
- 必须明确标记空结果、命令失败、NotFound。

如果兜底摘要失败，系统会退回到 3000 字符截断，并记录：

```text
[AICall] observation processor 失败，使用截断回退
```

即使进入 fallback，系统也会尽量把 fallback 的 raw / structured / summary 写入 `tools/`，避免出现日志里有工具结果但 archive 里缺文件。


## 7. Token Budget 日志

预算估算实现见 [app/core/context/budget.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/context/budget.py)。

每次 LLM 调用都会记录 context budget。带工具的节点会记录两类快照：

- 调用前：静态输入上下文，例如 runbook catalog、节点 system prompt、user message、工具 schema。
- 调用后：在静态输入基础上追加本轮动态新增上下文，例如 tool observations、AI messages、final output。

典型日志：

```text
[context_budget] node=evidence window=32768 window_source=env:MODEL_CONTEXT_WINDOW token=exact token_sources=tokenizer_json:/models/Qwen3-32B-AWQ/tokenizer.json input_tokens=7404 input_usage=23% reserved_tokens=10096 budget_tokens=17500 budget_usage=53%
[context_budget.top] node=evidence tool_schema=2510(8%) user_message=1249(4%) tool_observations=905(3%)
```

字段含义：

- `node`：当前节点。
- `window`：模型上下文窗口。如果无法准确获取，会显示 `unknown`。
- `window_source`：上下文窗口来源。
- `token`：token 计数精度。`exact` 表示使用已配置 tokenizer 计数；`estimated` 表示仍在用字符启发式估算。
- `token_sources`：token 计数来源，例如 `tokenizer_json:/models/Qwen3-32B-AWQ/tokenizer.json`、`tiktoken:cl100k_base`、`heuristic:chars/3`。
- `input_tokens`：当前已经进入模型上下文的 token。只有 `token=exact` 时输出具体数值；如果无法准确计算，输出 `unknown`。
- `input_usage`：`input_tokens / window`。
- `reserved_tokens`：scratchpad/output 预留预算，不是已消耗 token。
- `budget_tokens`：`input_tokens + reserved_tokens`。用于判断是否可能爆上下文。
- `budget_usage`：`budget_tokens / window`。

如果无法准确计算 token，日志不会输出伪精确 token：

```text
[context_budget] node=evidence window=32768 window_source=env:MODEL_CONTEXT_WINDOW token=estimated token_sources=heuristic:chars/3 input_tokens=unknown input_usage=unknown reserved_tokens=10096 budget_tokens=17500 budget_usage=53%
```

详细组件仍保留在 `budget/<node>.json` 里，日志只打印 top3 输入来源，避免刷屏。

### 7.1 准确 token 计数配置

如果没有配置 tokenizer，系统只能使用 `chars/3` 这类启发式估算。原因是不同模型 tokenizer 不同，Qwen、DeepSeek、OpenAI 的同一段文本 token 数可能不同。

要让 Qwen 本地模型获得准确 token 计数，必须让 aiops 容器能读取和模型服务一致的 `tokenizer.json`：

```yaml
llm:
  tokenizer_json_path: "/models/Qwen3-32B-AWQ/tokenizer.json"
```

或环境变量：

```bash
AIOPS_TOKENIZER_JSON_PATH=/models/Qwen3-32B-AWQ/tokenizer.json
```

如果是 OpenAI/tiktoken 编码，可以配置：

```bash
AIOPS_TIKTOKEN_ENCODING=cl100k_base
```

优先级：

1. `AIOPS_TOKENIZER_JSON_PATH`：使用 HuggingFace `tokenizers` 加载本地 tokenizer，标记为 `exact`。
2. `AIOPS_TIKTOKEN_ENCODING`：使用指定 tiktoken encoding，标记为 `exact`。
3. OpenAI 模型名自动匹配 tiktoken，标记为 `exact`。
4. 回退 `heuristic:chars/3`，标记为 `estimated`。

注意：`exact` 的含义是“对当前配置的 tokenizer 准确”。如果配置的 tokenizer 和模型服务实际 tokenizer 不一致，日志无法自动发现这个问题。

组件数组会写入 budget JSON：

```json
{
  "context_window": 32768,
  "context_window_source": "env:MODEL_CONTEXT_WINDOW",
  "context_window_accuracy": "exact",
  "token_count_accuracy": "exact",
  "token_count_sources": ["tokenizer_json:/models/Qwen3-32B-AWQ/tokenizer.json"],
  "static_context_tokens": 10847,
  "dynamic_context_tokens": 2100,
  "actual_context_tokens": 12947,
  "reserved_tokens": 10096,
  "components": [
    {
      "name": "runbook_catalog",
      "category": "static_input",
      "tokens": 900,
      "total_ratio": 0.0391,
      "window_ratio": 0.0275,
      "preview": "# Available Runbooks..."
    },
    {
      "name": "tool_observations",
      "category": "dynamic_runtime",
      "tokens": 1800,
      "total_ratio": 0.0781,
      "window_ratio": 0.0549
    }
  ]
}
```

组件分类：

- `static_input`：本次节点调用开始前就会进入模型上下文的内容。
- `dynamic_runtime`：本次 agent loop 中动态新增到模型上下文的内容。
- `reserved`：不会直接作为文本发送，但为推理、工具调用和输出保留的预算。

当前静态组件：

- `runbook_catalog`：注入到 system prompt 前面的 runbook 目录。
- `node_system_prompt`：节点自身 prompt。
- `remediation_policy`：自动修复开关追加的约束。
- `language_policy`：中文输出和 think 可见性约束。
- `user_message`：节点级 user prompt。evidence 中包含原始问题和 `layer_handoff`。
- `tool_schema`：当前节点可见工具的 schema。

当前动态组件：

- `tool_observations`：工具返回后回注给模型的 bounded summary 累计。
- `ai_messages`：agent loop 中模型已经产生的完整 AI message 累计。
- `final_output`：本次 LLM 调用最终输出。

日志级别：

- `< 75%`：INFO
- `>= 75%`：WARNING
- `>= 90%`：ERROR

预算快照也会写入：

```text
/tmp/aiops/reports/context_archives/<run_id>/budget/<node>.json
```

### 7.1 上下文窗口获取优先级

上下文窗口获取由 `ModelContextResolver` 负责，优先级如下。

1. `MODEL_CONTEXT_WINDOW`

显式环境变量视为准确值：

```bash
MODEL_CONTEXT_WINDOW=32768
```

K8s 部署中该值来自 `deploy/secrets/core.yaml` 的 `MODEL_CONTEXT_WINDOW`，并由
`deploy/k8s-simple.yaml` 注入到 Pod 环境变量。为避免与 Secret 中的 `LLM_MODEL`
产生双配置冲突，当前部署的 ConfigMap 不再配置 `llm.model` 或 `llm.context_window`。

2. `AIOPS_MODEL_METADATA_FILE`

如果部署环境能挂载模型服务配置，可以提供 JSON 文件：

```bash
AIOPS_MODEL_METADATA_FILE=/app/config/model-metadata.json
```

文件中只要能找到以下字段之一，就视为准确：

- `max_model_len`
- `max_context_length`
- `context_length`
- `max_sequence_length`
- `model_max_length`
- `n_ctx`
- `max_position_embeddings`
- `max_input_tokens`
- `max_total_tokens`

3. OpenAI-compatible metadata endpoint

系统会尝试读取：

- `/v1/models/{model}`
- `/v1/model/info`
- `/v1/models`

如果响应中包含上述上下文字段，则视为准确。

4. 模型名启发式映射

如果拿不到准确 metadata，系统会按模型名做启发式估算，并明确标记为 `accuracy=estimated`：

- `qwen3-next-80b`：65536
- `qwen3-32b`：32768
- `qwen2.5-32b`：32768
- `deepseek-chat`：65536

5. unknown

如果无法识别，会显示：

```text
context_window=unknown source=unavailable accuracy=unknown usage=unknown
```

这种情况下仍会输出各组件 token 估算和 `total_ratio`，但不会输出相对上下文窗口的可靠百分比。


## 8. 节点 Prompt 管理

节点基础 prompt 仍统一维护在 [app/core/prompts.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/prompts.py)。

当前原则：

- system prompt 放节点稳定职责、格式约束、安全边界。
- 节点间流转的业务上下文放 user message。
- evidence 不再把 `layer_full_analysis` 这种大段上游全文拼进 system prompt。
- 每个节点的 user message 要符合节点职责，而不是简单复述原始 question。

### 8.1 evidence user message

构造函数见 [app/core/workflow/nodes/evidence_collector.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/workflow/nodes/evidence_collector.py)。

当前结构：

```text
# 用户原始问题
{question}

# 上游定位结构化结果 layer_handoff
{layer_handoff_json}

# 当前节点职责
你是 evidence 节点。上游已定位为 {layer}，你必须基于 layer_handoff 的 active_entities、active_signals、possible_scenarios 和 must_verify 调用真实只读工具采集证据。

# 强约束
- LLM 必须自己决定并调用工具；计划不是证据。
- 必须保持 namespace、Pod、Service、Node、资源类型不漂移。
- 如果工具结果显示对象不存在、namespace 不匹配、事件为空、命令失败，必须把它视为冲突或负向证据，不能当作成功验证。
- 如果上游定位需要 runbook 补充，可以 fetch 相关 runbook，但不能只 fetch runbook 后结束，必须继续调用真实环境工具。

# 输出
完成必要工具调用后，输出 evidence_plan JSON 和简短证据结论。
```

如果第一轮 evidence 只输出计划但没有任何成功工具调用，系统会发起 strict retry，并把失败原因加入 user message。

### 8.2 evidence prompt 日志

为了排查 evidence 输入是否过长、是否指令漂移，当前会在每次 evidence 执行首次调用时打印一次 user prompt：

```text
📨 [evidence] LLM user prompt | chars=... strict=false
...
```

同一次 evidence 节点内不会每轮重复打印，避免日志爆炸。


## 9. Think Streaming

本地推理模型可能输出 `<think>...</think>`，当前可配置展示策略。实现见 [app/core/service.py](/root/huhu/agent/combine-aiops-mcp/robusta/app/core/service.py) 的 `ThinkStreamFilter`。

配置入口：

```yaml
workflow:
  think_stream:
    mode: full
    max_chars: 1200
```

环境变量覆盖：

```bash
AIOPS_THINK_STREAM_MODE=full|truncated|hidden
AIOPS_THINK_STREAM_MAX_CHARS=1200
```

模式说明：

- `full`：完整展示 `<think>`，当前默认。
- `truncated`：只展示每段 think 的前 `max_chars` 字符。
- `hidden`：隐藏 think 内容。

注意：`WorkflowNode._call_llm()` 的 system prompt 仍要求模型不要输出 `<think>`，但部分本地模型可能不完全遵守。因此服务层提供流式过滤作为兜底展示策略。


## 10. 当前实现与预留设计边界

### 10.1 已实现

- `layer_full_analysis` 默认不再作为大字段传给下游。
- layer 全量分析写入 context archive。
- `layer_handoff` 作为下游默认交接对象。
- evidence user prompt 使用 `layer_handoff`，不再依赖上游全文。
- AICall 中工具 observation 会落盘 raw/structured/summary。
- AICall 会把回注给模型的 ToolMessage 内容替换为 bounded summary。
- context budget 日志和 budget 文件已实现，包含静态输入、动态新增上下文、reserved budget 和组件占比。
- 模型上下文窗口会按 `MODEL_CONTEXT_WINDOW`、metadata file、OpenAI-compatible metadata endpoint、模型名启发式顺序解析，并标记 `exact/estimated/unknown`。
- evidence user prompt 首次调用日志已实现。
- think streaming 支持 `full/truncated/hidden` 三种模式。
- 节点输入、节点输出、节点间 handoff 已归档到 `node_inputs/`、`node_outputs/`、`handoff/`。
- observation summary 支持 `rule/ai` 两种策略，其中 `ai` 会强制每次工具 observation 调用 LLM summarizer。

### 10.2 仍是预留或未完全实现

- 还没有接入持久化 LangGraph checkpointer。当前主要依赖 `WorkflowState` 运行时状态和 context archive 文件排查。
- archive 当前是本地文件系统，不是数据库或对象存储。
- `tool_artifact_refs` 字段已在 state 中预留，但不是所有节点都完整消费；当前主要通过 archive 文件排查。
- evidence 的证据有效性仍主要基于 `thinking_events` 和计划匹配，后续可以进一步使用 structured artifact 做更强判定。
- token 数是粗估，不是模型真实 tokenizer 精确计数。


## 11. 典型案例：问“我的集群有什么问题？”

### 11.1 layer

输入给模型：

- system prompt：layer 职责、输出 JSON 要求、runbook catalog、修复限制、语言约束。
- user message：用户原始问题。
- tools：全量只读/可用工具和 `fetch_runbook`。

模型可能调用：

- `kubectl_get_by_kind_in_cluster(kind="pod")`
- `kubectl_get_by_kind_in_cluster(kind="node")`
- `kubectl_events(...)`
- `fetch_runbook(...)`

工具结果处理：

- 原始输出写入 `tools/*.raw.txt`。
- 表格类输出被压缩为异常行和状态统计。
- events 输出保留 Warning/Failed/BackOff 等关键信号。
- 主模型只看到 summary。

layer 结束后：

- `layer_analysis` 保存结构化 JSON。
- `layer/full_analysis.md` 保存完整分析。
- `layer/handoff.json` 保存下游交接。
- `WorkflowState.layer_full_analysis = None`。

### 11.2 evidence

输入给模型：

- system prompt：evidence 节点职责、JSON 格式、必须调用工具的硬约束。
- user message：原始问题 + `layer_handoff` + evidence 当前任务。

模型必须自己决定并调用工具，例如：

- `kubectl_describe` 验证某个 Pod 当前状态。
- `kubectl_events` 验证事件是否仍存在。
- `kubectl_get_yaml` 验证环境变量、资源限制、镜像、volume。

如果模型只输出 plan 不调用工具：

- 系统拒绝该结果。
- 发起 strict retry。
- strict user message 会明确说明上一轮失败原因。

### 11.3 RCA

RCA 不再读取 layer 全量文本。`layer_handoff` 只作为定位边界和实体锚点，RCA 的主要事实来源是 evidence 节点产出的结构化证据：

- `layer_handoff`
- `evidence_items`
- `evidence_facts`
- `evidence_conflicts`
- `missing_evidence`
- 从 `evidence_analysis` 中提取出的工具摘要

这样 RCA 既不会丢失 layer 定位出的对象和场景，也会充分利用 evidence 更详细的已验证事实、冲突证据和缺失证据。

### 11.4 conclusion

conclusion 优先使用：

- compact `layer_handoff`
- evidence summary
- RCA result
- query_result，如果是 `/query`

如果最终报告上下文超过 `CONCLUSION_TOKEN_BUDGET`，会优先压缩最大的阶段文本。


## 12. 排查 Checklist

### 12.1 怀疑上下文太大

看日志：

```bash
kubectl -n aiops logs deploy/aiops-copilot | grep context_budget
```

重点看：

- 哪个 `node` 的 `usage` 最高。
- `tool_schema` 是否过大。
- `startup_prompt` 是否异常。
- `user` 是否说明某个节点 user message 太长。

### 12.2 怀疑工具输出拉爆上下文

看工具处理日志：

```text
[AICall] tool #3 kubectl_describe | success | raw=3951 summary=1800 processor=k8s_describe
```

重点看：

- `raw` 是否很大。
- `summary` 是否被控制在预算内。
- `processor` 是否是预期处理器。
- 是否出现 `fallback_truncate`。

### 12.3 怀疑 evidence 没按上游实体采集

看首次 evidence user prompt：

```bash
kubectl -n aiops logs deploy/aiops-copilot | grep -A80 "LLM user prompt"
```

重点确认：

- `layer_handoff.active_entities` 是否正确。
- namespace、Pod、Service、Node 是否漂移。
- `must_verify` 是否包含当前要验证的关键事实。
- strict retry 是否被触发。

### 12.4 怀疑 full_analysis 丢了

不是丢了，而是不再传给下游。查看：

```bash
kubectl -n aiops exec deploy/aiops-copilot -- find /tmp/aiops/reports/context_archives/<run_id>/layer -type f -maxdepth 1 -print
```

如果目录不存在，优先检查：

- `AIOPS_CONTEXT_ARCHIVE_ROOT` 是否配置。
- Pod 是否有 `/tmp/aiops/reports` 写权限。
- initContainer 是否成功执行。


## 13. 后续优化方向

优先级从高到低：

1. 接入持久化 LangGraph checkpointer，只保存结构化 state 和 archive refs，不保存 raw 大文本。
2. 让 evidence 证据匹配直接消费 structured artifact，提高“工具成功”和“证据有效”的区分能力。
3. 按节点裁剪工具列表，降低 `tool_schema` token 占用。
4. 给 archive 增加按 `run_id` 查询的 debug API。
5. 对 Prometheus 大结果增加专用结构化处理器，区分 instant vector、matrix、空结果、label 维度异常。
6. 将 context budget 阈值配置化，例如 75% warn、90% hard fail 或自动降级。
