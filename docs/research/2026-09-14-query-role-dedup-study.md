# 查询输出角色约束下的观测去重：具体候选与验证边界

日期：2026-09-14。状态：真实函数反例、保守隔离原型及下一候选步骤已形成；新颖性/创造性尚未成立。不是生产修复或上线建议。

续查决定：第 8 节增加不解析查询的无损字段共享对照，以及已核读的查询感知结果压缩专利。**暂不建议把第 4 节原样提升为主申请方案。** 当前缺的不只是检索确认，还包括证明候选复杂度相对于普通无损表示基线有必要性。

## 1. 小切口

同一个标签在一种查询中可能只是副本来源，在另一种查询中却是用户要求区分的结果维度。工具统一删除标签以减少重复，会把原查询已经分开的结果重新合并。

例如：说明性查询 `count by (namespace, pod, instance) (some_metric{namespace="n",pod="p"})`，其结果含 instance=a 和 instance=b，两者值都为 1。后处理如果删除 instance 并按其余标签去重，两个结果会变成一个。值相等不等于两个输出组相同。

这是一种明确的数据表示错误，不需要模型理解“哪个字段对根因更重要”。查询本身给出了必须区分的维度。

## 2. 当前实现与已验证的反例

MCP `servers/aiops_observability/query/metrics.py`：

- `SCRAPER_LABELS` 包含 job、instance、endpoint、service、prometheus、prometheus_replica。
- `compact_prometheus_result`（约 151 行）无查询参数，先删除这些标签再构建分组键。
- 同组中保留样本数更多的记录；数量相同则保留先遇到的记录，不比较值是否一致。
- 普通的同组舍弃不设置 truncated；counts 可以显示 raw_series_count 与 series_count 不同，但不解释值是否发生分歧。
- 现有 `test_aiops_observability_query_metrics.py:test_deduplicates_scrapers_without_summing` 验证的是不同 job/instance、相同时间和相同值的重复样本。

本轮从当前源码 AST 提取真实 compactor、stats、point_count 及相关常量，在本地构造两条除 instance 外标签相同的瞬时记录。同一时间分别为 134217728 和 268435456 字节。输入顺序调换后，保留值相应变化，truncated 仍为 false。

这证明函数在此输入下具有顺序相关的值选择行为，不是已经证明线上存在这两条样本或诊断错误。尤其不能断言 job/instance 在所有源配置中都不是副本标识。

## 3. 第一性原理与跨域类比

去重实际上是在声明一种等价关系。必须先回答“相对于哪个输出含义等价”，而不是先列一个永远可删除的字段表。

可借鉴编译器/数据库的处理思路：一次转换能否实施，取决于当前表达式要求保留的可观察差别。查询给出的分组标签可作为减量操作的限制，不让后处理重新决定这些组是否应当存在。

这只是明确的跨域建模类比；本轮没有将某篇编译器论文或专利核验为本方案出处，也没有把“保持可观察语义”这个原则称为新发明。

## 4. 完整候选处理链（尚未实现全部）

工作名称：**一种受查询输出角色约束的工具观测减量方法**。

1. 在执行前解析实际查询，记录查询版本、对象约束和时间口径。使用真正的 PromQL AST，不采用靠正则抓到所有 by 字段就假定正确的通用解析。
2. 对支持的操作推导输出维度。例如简单 `by(L)` 输出组依赖 L；`without(L)` 需要结合实际输入标签；重命名、二元匹配和未知函数需要独立的标签传播规则。不支持或无法确定时，标记不可证明，禁用跨标签去重。
3. 连接器另行给出明确配置的副本标签。两种信息来源分开：查询决定哪些结果差别受保护，采集配置提出哪些差别可能属于副本。小模型不得凭名称把 instance/job 自动认证为可删除字段。
4. 由程序计算可删除标签集合：已声明副本标签减去受保护的输出维度。先按剩余完整标签建立候选组，再检查时间/值/类型/序列内容是否相同。无法证明相同的记录不能仅按“样本数更多”或“先返回”消除另一条。
5. 完全相同的样本载荷可以共享存储，保留来源成员清单。不同载荷作为不同变体保留，不自动选择哪一个为真。不同时间的相同值也不是同一次观测的等价副本。
6. 在上下文预算内选择表示时，候选组有多个不同载荷则显示“存在差别”及相应来源；不能只留下一个值并隐藏多变体状态。预算不足时输出有引用的差别摘要或明确遗漏，不称为无损保存所有样本。
7. 如需回读，从减量前的源返回或完整变体归档恢复，并沿同一查询输出约束构建输入。若源返回在 MCP 内已不可恢复，则披露缺失，不把 Agent 的 MCP raw_ref 误认为源端完整原文。
8. 模型负责选择需要展开的差别组或提出补查请求；程序负责匹配和保留差别。没有额外证据时，模型的选择不能把多变体状态升级为单一确定事实。读取失败、版本变化或预算耗尽时保留未确认状态并终止相应补读。

这条链的候选区别在于：**查询中的输出区分要求控制后处理可以实施哪些合并**，而不是让后处理仅依照固定字段名单自行归一化。值分歧保留、预算、回读是支撑步骤，不各自宣称创新。

## 5. 原型覆盖范围

运行：`python3 docs/research/dedup_role_feasibility.py`，8 项检查通过。

| 检查 | 结果 |
|---|---|
| 当前真实函数对不同值保留首条 | 复现 |
| 当前真实函数对 instance 不同但值相同的记录合并 | 复现 |
| 明确传入 instance 为受保护维度后仍保持两个组 | 通过 |
| 明确声明的副本且载荷相同，共享载荷并保留两个来源 | 通过 |
| 同组不同值不被压成单个确定值 | 通过 |
| 同值不同时间保留为不同载荷 | 通过 |
| 没有副本声明时，不自行删去 instance | 通过 |
| 保守原型结果不随输入顺序改变 | 通过 |

保守原型的 protected_labels 和 replica_labels **由测试显式传入**。没有实现 AST 标签传播、真实副本配置解析、预算投影、归档服务或模型选择器；因此不能把它称为完整候选已经验证。

该原型也没有实现 HA 时间序列拼接。精确载荷比较宁愿少合并；字符串值 `1`/`1.0` 在原型中仍会不同，可能保留额外变体。若工程上要规范化数值、NaN、时间或直方图，需要单独定义和验证，不允许模糊容差暗改事实含义。

## 6. 已核验的相邻产品：Thanos

固定版本：[Thanos v0.39.2](https://github.com/thanos-io/thanos/releases/tag/v0.39.2)，GitHub release API 返回发布时间 2025-07-21T06:51:58Z。

本轮核读[query.md](https://github.com/thanos-io/thanos/blob/v0.39.2/docs/components/query.md)去重段落与 [pkg/dedup/iter.go](https://github.com/thanos-io/thanos/blob/v0.39.2/pkg/dedup/iter.go)相关源码摘录：

- 配置一个或多个 replica-label，按这些标签区分 HA 副本；不是泛化为所有 job/instance 都可删除。
- 文档说明 penalty、chain 两种算法，前者通过惩罚窗口避免因微小差别频繁切换副本；chain 有明确使用边界，不能把两者说成适用情形相同。
- 迭代器把同标签集合的副本组合；对部分计数器函数有调整逻辑，避免切换副本造成假计数器重置。可见它也并非完全不考虑查询函数。

因此不能主张“配置副本标签”“多副本不直接相加”“函数相关的去重处理”是新技术。Thanos 的主要任务是生成可查询的 HA 序列；本候选关注工具执行完成后的有限输入减量不得消除原查询输出组。二者处理阶段和目的有区别，但**区别是否足以构成创造性尚未证明**。

本轮没有部署或运行 Thanos，也没有证明其在上述结果后处理问题上失败；不能把自己的 compactor 缺陷归给相邻产品。

## 7. 专利检索与决定

本轮检索了 time series / deduplication / conflict、query / deduplication / labels、time series / replica / deduplication、data lineage / duplicate / query 等组合。部分 FPO 查询失败；成功结果得到的“deduplication pruning anomaly”等条目主要讨论存储系统自身异常，未核读全文，不能拿标题当作直接覆盖证据。

没有新增经原件核读的近邻专利。此前已经核读的字段映射、证据标准化、查询细化、跨字段压缩、依赖感知预算等文献仍构成组合风险；本节不作全新空白领域声明。

本候选比“固定字段保护”多一个明确的控制来源：实际查询 AST 决定本次不可合并的输出差别。但推导查询输出依赖本身属于成熟数据库/编译技术，需要继续检索“查询感知去重/结果压缩/语义保持后处理”的整体链，不能只看云平台标签。

当前选择：保留该候选作下一轮精确对比；不直接形成可申请结论。它给出了真实实现中的具体损失及可执行保守基线，尚未满足总目标中的新颖性证据条件。

未修改 Agent、MCP、测试脚本、部署或权限。所有执行仅为本地研究原型和公开来源读取。

## 8. 更简单的反方基线与新增近邻

### 8.1 不删除逻辑行，仅共享重复字段

对前文候选做了必要性检查：如果我们只是要减少重复字段占用，是否必须先判断哪些输出行可以合并？

在 `dedup_role_feasibility.py` 中增加 `factor_labels`/`restore_labels`：提取所有行共有且相同的标签，只存一次；每条逻辑行保留差异标签、时间、值以及其他载荷。解码按共有标签和逐行残差重建。没有 query AST、副本声明或 LLM。

用相同 JSON 紧凑序列化口径比较，得到：

| 合成行数 | 完整行列表字节数 | 字段共享后字节数 | 解码是否逐行相等 |
|---:|---:|---:|---|
| 1 | 120 | 120（编码更大则保留原文） | 是 |
| 2 | 239 | 222 | 是 |
| 20 | 2391 | 1060 | 是 |

20 行实例保留所有不同 instance，各行值都为 1，没有把“相同值的不同输出组”折成一个。另测试不同值、不同时间、标签缺失、重复行的次数都能恢复。原型共 14 项检查通过。

局限必须明确：

- 字节数不是 token 数，也不是端到端准确率或 MTTR。
- 这是数据编码/解码验证，没有验证模型直接阅读共享格式是否正确。
- 如果送入模型前完全展开，输入节省可能不再存在；若直接交给模型读，则要另做理解准确性测试。
- 所测共同标签很多，不代表任意工具响应都能同比压缩；无共同部分时回退原文。
- 这是普通无损编码对照，不作为新的专利方案。代码使用原始标签字符串比较，不扩展到任意结构对象的语义等价证明。

本次结果不能证明查询感知方案没有任何价值，但证明：在已经展示的“防止误合并且减小表示”条件下，查询解析不是唯一甚至不是必要的实现步骤。候选若要继续，需要提出该基线解决不了的新增技术矛盾，而不是先人为做一次破坏性合并，再复杂修复。

### 8.2 US9218354B2：Query-aware Compression of Join Results

IBM；该申请提交日 2013-02-28，授权公告日 2015-12-22；首页记载公开 US20130179412A1 于 2013-07-11，并记载较早母案。本轮不核定母案优先权有效性或整个同族。

原件：[USPTO PDF](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9218354)。本轮核读 PDF 第 1、16、17、18 页，含权利要求 1—16；没有完整精读全部说明书。

需要准确区分标题和授权权项：该份授权权利要求 1 的主语是用 decoder 解压 join query 结果，不是无限定地覆盖一切查询结果压缩。

其具体关系：

- 接收编码 tuple 及字典条目值/位置。
- 从 join query 确定 join order。
- 按 join order 和条目信息建立嵌套字典层次，嵌套顺序对应 join order。
- 根据编码位置与字典映射重建 tuple，保留与原表标识的关联。
- 权利要求 4、10、15 涉及叶级/中间级字典将片段编码后再形成更短编码；6 涉及列标识。

这与我们“保护分组维度以限制合并”的具体谓词不相同，但它已经把查询结构、结果减量表示、来源位置和可恢复 tuple 连接起来。不能再把“利用查询结构指导压缩和重建”这个上位概念当成未有人提出。

同族线索还有 9529853、9785674，尚未逐项核读；不得推断其权项与本件一致。

### 8.3 US5615361：查询唯一性约束的早期线索

标题 **Exploitation of Uniqueness Properties Using a 1-tuple Condition for the Optimization of SQL Queries**；IBM；1995-02-07 申请，1997-03-25 授权。

本轮查看[官方 PDF](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/5615361)首页与末尾两页，后者实际是 1997-11-25 更正证书的第 4—5 页，**不是已读取完整原始权利要求**。首页摘要明确结合谓词中绑定列与表键识别至多一 tuple 条件，再进行查询变换及 DISTINCT 要求消除。

它是“查询约束控制允许的数据变换”的早期技术线索。由于正文及全部更正尚未核读，本轮不据此作精确权利要求覆盖结论，也不把更正页错误计为新的独立专利。

### 8.4 当前收敛结果

保留已复现的工程问题；将查询角色候选保留为对照，不在尚无额外必要性证据时继续追加模型或字段。

后续方案至少需要同时越过两个基线：

1. 在无需删逻辑记录的情况下先做无损字段共享；
2. 当仍超预算时，已有查询感知压缩与按需恢复机制。

这不是把多个旧操作拼接就宣布否定新颖性；而是要求新的处理关系说明为何不是这些成熟基线的常规选型与组合。研究总目标依然未完成，尚不能提供“已具备新颖性”的最终判断。
