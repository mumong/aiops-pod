# 小模型选择观测后，怎样判断是否漏选：候选必要性与现有技术核查

日期：2026-09-14。仅研究记录；未修改 Agent、MCP、服务、测试任务或权限。

## 1. 本轮决定

保留“模型判断相关性，程序按源记录构建输入”作为可实施工程基线；不将“再加一个模型复核”或“抽查遗漏后控制风险”直接提升为专利核心。

当前需要解决的更具体问题是：**选择器没有展示的观测，依据什么触发补读？** 不能把“模型没有要求补读”当成“没有遗漏关键依据”，也不能把全体记录的低漏选比例等同于一次故障的关键线索未丢失。

这是研究收敛，不是已找到具有创造性的完整方法。前序研究见 [查询角色去重及无损表示对照](2026-09-14-query-role-dedup-study.md)。

## 2. 有限总体抽查的精确反例

设未展示集合有 N 条，其中 r 条是我们事后知道的重要记录；均匀无放回抽取 k 条复核。先给复核器最有利假设：只要抽到重要记录就一定识别。

完全漏掉的概率为 `C(N-r,k) / C(N,k)`，不是模型置信度。使用 Python 标准库 `math.comb` 与 `fractions.Fraction` 精确计算：

| N | r | k | 未抽到任何重要记录的概率 |
|---:|---:|---:|---:|
| 1000 | 1 | 32 | 96.800000% |
| 1000 | 5 | 32 | 84.963575% |
| 1000 | 10 | 32 | 72.127906% |

只有一条重要记录时，要达到 95% 的抽中概率，需要抽取 950 条。实际模型还会误判，因此抽中并不等于识别成功。

这个反例只否定无信息条件下的小规模均匀抽查能够保证稀有线索恢复；不否定带有有效特征的检索、分层采样或全量低成本扫描。若主张后者有效，必须说明特征从何而来，不能假定已经知道重要记录在哪一层。

可复算：

```python
from fractions import Fraction
from math import comb
assert Fraction(comb(999, 32), comb(1000, 32)) == Fraction(968, 1000)
assert Fraction(comb(999, 950), comb(1000, 950)) == Fraction(5, 100)
```

本轮执行上述断言及三组计算通过。不是线上运行、模型实验或诊断准确率测量。

## 3. 跨领域方法：统计风险控制已有可执行实现

### 3.1 Conformal Risk Control

核读作者[官方仓库 README](https://github.com/aangelopoulos/conformal-risk)与 `core/get_lhat.py` 全部内容。作者引用论文为 Angelopoulos、Bates、Fisch、Lei、Schuster，arXiv:2208.02814，2022。

核心不是让模型自己报告可信度，而是：具有参考答案的校准样本 → 不同选择阈值对应的损失表 → 计算校准损失及有限样本修正 → 选择满足风险条件的阈值。README 用多标签集合的漏选比例举例；源码说明它针对单调风险控制 marginal risk。

源码定位：[get_lhat.py 固定提交](https://github.com/aangelopoulos/conformal-risk/blob/e0fb22dd60b4c7f3269f27386a5869a31ca777af/core/get_lhat.py)。GitHub API 返回该文件最近提交日期 2022-07-28。未运行其图像、问答实验，也未逐项复核原论文全部定理。

对本项目的边界：需要能够计算损失的校准依据，并满足相应统计前提；不能拿模型自评分冒充参考标签。统计保证不是对任意一次特定 Pod 诊断的遗漏清零证明。

### 3.2 C-RAG：已将校准、检索配置与生成风险连接

Mintong Kang 等，*C-RAG: Certified Generation Risks for Retrieval-Augmented Language Models*，ICML 2024，PMLR 235:22963–23000。

- [正式条目及摘要](https://proceedings.mlr.press/v235/kang24a.html)
- [论文 PDF](https://raw.githubusercontent.com/mlresearch/v235/main/assets/kang24a/kang24a.pdf)
- 本轮核读摘要和 PDF 第 2–5 页，包含 §3、§4、§5 的开头；没有核完附录证明或 §6 分布偏移的全部条件。

§4 的配置包含检索示例数、生成数量及相似性阈值；依据带参考文本的校准集合评估生成风险，计算风险界或可接受配置集合。它不是一个仅靠“再问模型是否足够”的机制。

§5 的部分理论使用单层自注意力、示例近似为单 token 等分析设定；不能将其证明直接套用于当前运维 Agent。论文还明确讨论长尾参考类别需要更大的知识库样本。它另有分布偏移扩展，不能笼统说这项工作完全不处理分布变化。

对照结论：**模型/检索选择＋校准风险＋配置控制已有完整研究链。** 换成运维数据、小参数模型或 token 预算，不自动产生创造性。本文没有认定该论文与任何拟议权利要求逐项相同。

## 4. 对混合方案的实际约束

可实施的基线流程如下，均不作为已证实的新点：

1. 固定本次已取得集合 D 的版本、对象与窗口，保存源记录和可定位引用。
2. 程序先做无损共享和明确的重复处理；小模型根据问题对记录或类别排序。
3. 程序在预算内构建 S，保存选择清单与未展示记录入口；不将模型改写当作源字段。
4. 后续补读分开处理：模型提出相关性需求；支持明确谓词的程序检查可执行精确取数。无法表达或验证的语义条件不能冒充已检查。
5. 若使用抽样/校准，只报告其实际损失定义、适用总体、样本及前提；不得输出“本次没有漏掉根因”这样的越界保证。
6. 达到预算或时间上限后，披露仍未覆盖的范围，而不是以没有补读请求作为完整性验收。

关键限制：即使某个明确谓词已在 D 中全量检查，也只验证该谓词在已取得集合中的结果，不证明候选根因集合完整，不证明数据源完整，更不证明因果关系。

## 5. 下一候选的准入条件

需要找到可观察、可计算的机制，让未展示记录实际影响补读决策，并证明其相对“普通检索＋保留原文＋可选校准”的额外作用。不能靠以下三种方式补足论证：

- 让另一个模型重复相同判断，却称其为独立保证；
- 用总体低错误率掩盖单次稀有关键记录的遗漏；
- 假定事先存在完备的根因特征表，再声称解决开放诊断的漏选。

本轮排除了一个看起来合理但不充分的扩展，并补上直接近邻研究。仍未形成可建议定稿的创新性结论；下一步不是继续堆模型，而是寻找上述普通基线尚未解决的可实施处理差别。

## 6. 续查：反例反馈和分组细化也需要更简单的对照

### 6.1 回到当前函数，而非假定线上已经误诊

新增 [witness_retention_feasibility.py](witness_retention_feasibility.py)，从当前 `app/core/context/observability_projection.py` AST 提取真实 `_selection_bucket`、`_diverse_order` 及所需函数，未导入业务模块、调用服务或模型。

源码 SHA256：`aabd00a24db5e2a6ac12215ea972e22de7c069f1d7494ab902ea80dd8ef1f9a2`。

合成 100 条同 UID、同 `/ready` 路径、同窗口、同级别的日志。首尾为 503，中间第 51 条为 200。日志消息中的数值经模板化后属于同一分组；真实排序函数的前两条为首尾，未包含中间反例。

这只证明所测日志形态与排序前缀的性质。**不是完整字符/token 预算执行，不是线上模型误判，不是当前程序声明这 100 条状态相同。** `pattern_count` 是模式成员数，不应被解释成全部成员每个字段都相同。Tracing 的分组显式包含响应码，此反例不能推广为所有三维数据都用相同分组逻辑。

### 6.2 对照结果

检查条件显式给定为“所提供范围内的记录均为 503”。未使用模型从自然语言抽取条件；范围检查、等值比较和三值结果由隔离脚本实现。

| 处理 | 两条记录预算 | 一条记录预算 |
|---|---|---|
| 当前排序前缀 | 所测输入仅含两个 503，无法展示反例 | 同样未展示反例 |
| 按条件真假分组，各保留代表 | 展示 503 与 200 | 无法同时满足两个代表，返回预算不足 |
| 固定保留已找到的 200 反例，再补普通记录 | 展示反例，可反驳全称断言 | 单条反例仍可反驳全称断言 |

8 项检查通过：包括当前分组/顺序复现、两种基线、单条预算、不同 UID/路径/窗口隔离、缺失字段/空集合未知、失效 ID 不补造、重复构建仍保留反例且源集合不变。

“在提供记录中成立”只指输入集合，不等于源系统全窗口完整；“被反驳”只针对该有限全称条件，不意味着根因已经确认或服务已恢复。记录数量不是 token，未知字段会增加代表类别，不能承诺有限预算能容纳任意多个检查条件。

**必要性结论：**对这个已经具体展示的问题，持久保留反例 ID 的简单基线已经足够，不需要持久修改分组规则。不能先把反例重新丢掉，再用复杂细化机制修复，作为优于正常引用保留的证据。这不证明分组细化在所有任务上无益，但当前没有证明其新增复杂度必要。
