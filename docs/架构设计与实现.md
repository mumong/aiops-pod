# Robusta AIOps 平台架构设计与实现

## 一、系统概述

Robusta 是一个面向 Kubernetes 集群的智能运维诊断平台，通过融合大语言模型推理能力与确定性规则引擎，实现对集群故障的快速定位、根因分析和修复建议生成。系统采用分层架构设计，将执行层、推理层、技能层和配置层进行清晰解耦，在保证诊断准确性的同时，确保系统的可解释性、可审计性和可扩展性。

本平台基于 FastAPI 构建 Web 服务，集成 HolmesGPT 作为 AI Agent 框架，并引入 LangGraph 实现结构化工作流编排。系统支持单集群诊断和多集群联邦查询两种工作模式，能够适应从小规模开发环境到大规模生产集群的不同应用场景。

## 二、核心设计理念

### 2.1 混合推理架构

传统的运维诊断系统往往面临两难选择：纯规则引擎虽然准确但覆盖范围有限，纯 LLM 推理虽然灵活但缺乏可解释性且容易产生幻觉。本系统创新性地采用混合推理架构，将确定性规则引擎与大语言模型推理能力有机结合。

在这一架构中，规则引擎负责处理已知的、高置信度的故障场景。通过声明式的规则定义和证据规格，系统能够对 OOMKilled、磁盘满、网络故障等常见问题进行快速准确的判定。规则引擎的输出包含完整的证据链、因果关系和修复步骤，具有极高的可解释性，满足企业级应用对审计和合规的要求。

同时，大语言模型作为补充推理引擎，处理规则库未覆盖的场景、进行复杂的关联分析、生成自然语言报告。LLM 能够理解用户的自然语言查询意图，灵活调用工具获取集群信息，并将结构化数据转化为易于理解的诊断报告。两者通过证据门控机制进行协调：当规则引擎检测到关键证据缺失时，会自动降低置信度并生成补采建议，引导 LLM 进行进一步的信息收集。

### 2.2 分层诊断模型

系统基于 Kubernetes 技术栈的天然分层特性，建立了五层诊断模型（L0-L4），为故障定位提供了清晰的分析框架。

**L0 基础设施层**关注物理资源和操作系统层面的问题，如磁盘空间耗尽、内存压力、CPU 过载等。这一层的故障往往是上层问题的根本原因，需要优先排查。

**L1 集群与节点层**聚焦于 Kubernetes 集群本身的健康状态，包括节点就绪状态、Kubelet 服务、证书有效性、网络插件等。该层问题会直接影响 Pod 的调度和运行。

**L2 工作负载层**关注 Pod、Deployment、StatefulSet 等工作负载对象的状态，包括 Pod 驱逐、容器崩溃、资源限制超限等问题。这是最常见的故障发生层。

**L3 服务与网络层**涉及 Service、Ingress、NetworkPolicy 等网络相关对象，以及 DNS 解析、服务发现、负载均衡等功能。网络问题往往表现为应用层错误，需要逐层排查。

**L4 应用层**关注业务应用本身的逻辑问题，如依赖服务不可用、配置错误、业务逻辑异常等。这一层的诊断需要结合应用日志和业务知识。

此外，系统还定义了 **QUERY 查询层**，用于处理纯数据查询请求，不触发诊断流程，直接返回集群状态信息。

这种分层模型不仅为 AI 提供了结构化的推理框架，也便于运维人员理解故障的层次关系和影响范围。在实际诊断过程中，系统会首先判定问题所属层级，然后针对性地采集该层的关键证据，避免盲目的全量信息收集。

### 2.3 证据驱动的诊断流程

传统的故障诊断往往依赖经验和直觉，缺乏系统性和可重复性。本系统引入证据驱动的诊断方法论，将每个故障场景分解为一系列可验证的证据项，每个证据项都有明确的采集方法、重要性级别和权重。

证据分为三个级别：**关键证据（Critical）**是判定问题的必要条件，缺失会导致诊断置信度大幅下降；**重要证据（Important）**提供有力支撑，但非必需；**可选证据（Optional）**用于补充分析，增强结论的完整性。

在诊断过程中，系统会根据初步判断制定证据采集计划，通过调用 kubectl、Prometheus 等工具获取实际数据。证据提取器使用关键词匹配和正则表达式从工具输出中提取结构化信息，转化为可判定的事实。规则引擎基于已采集的证据进行条件匹配，计算置信度分数。

证据门控机制作为质量保障的最后一道防线，会检查关键证据的完整性。当检测到关键证据缺失时，系统不会直接拒绝输出结论，而是采用软拦截策略：自动降低置信度等级，在报告中明确标注证据缺失情况，并生成针对性的补采命令建议。这种设计既保证了诊断的严谨性，又避免了过于僵化的流程阻塞。

### 2.4 配置外置与知识沉淀

系统的运维知识和诊断规则被统一外置到配置层进行管理，实现了代码逻辑与业务知识的分离。这种设计带来了多方面的优势。

首先，规则库采用声明式定义，每条规则包含场景描述、适用层级、判定条件、置信度基准、修复步骤等完整信息。新增或修改规则无需修改代码，只需更新规则配置文件即可。证据规格同样采用声明式定义，明确了每个场景需要哪些证据、如何检测、如何提取值。

其次，Runbook 知识库以 Markdown 文档形式存储，包含故障场景的详细描述、诊断流程、判定标准、修复方案和预防措施。AI 可以通过语义匹配检索相关 Runbook，将沉淀的运维经验融入诊断过程。知识库支持热更新，通过 ConfigMap 挂载到容器中，无需重启服务即可生效。

再次，系统提示词统一管理在配置文件中，包括默认模式的系统提示词、工作流各节点的提示词、联邦查询的路由提示词等。提示词的版本化管理便于进行 A/B 测试和持续优化。

最后，工具集和 MCP 服务器配置也采用声明式定义，支持灵活的启用/禁用控制。这使得系统能够根据不同的集群环境和安全策略，动态调整可用的诊断工具集。

通过配置外置，系统具备了持续演进的能力。运维团队可以根据实际经验不断完善规则库和知识库，而无需深入理解底层代码实现。这种设计也便于在多个集群环境中复用和定制诊断能力。

## 三、系统架构设计

### 3.1 整体架构

系统采用经典的分层架构模式，从下至上依次为执行层、技能与规则层、推理层和接口层。各层职责清晰，通过定义良好的接口进行交互，既保证了模块的独立性，又实现了灵活的组合与扩展。

**执行层**作为系统与真实运行环境之间的桥梁，负责与 Kubernetes 集群及其周边系统进行交互。该层通过统一的 MCP（Model Context Protocol）工具集形式，对 kubectl、Prometheus、Helm 以及安全 Shell 等能力进行封装。执行层的设计原则是仅负责执行具体查询或操作并返回原始结果，不参与任何推理或判断逻辑。所有工具调用都经过严格的权限控制和审计日志记录，确保系统操作的安全性与可追溯性。

执行层支持两类工具集成方式：内置工具集通过 HolmesGPT 的 toolset 机制直接加载，包括 Kubernetes 核心工具、Helm 工具、Prometheus 查询工具等；远程 MCP 服务器通过 SSE（Server-Sent Events）协议进行通信，支持 Elasticsearch 日志查询、自定义诊断脚本等扩展能力。这种设计使得系统能够灵活适配不同的基础设施环境，同时保持核心逻辑的稳定性。

**技能与规则层**是系统的核心创新点，为模型推理提供确定性的判定能力。该层包含规则引擎、证据提取器、证据门控和输出格式化器四个核心组件。规则引擎基于声明式规则定义，对工具返回的原始数据进行结构化分析，识别已知问题场景并计算置信度。证据提取器使用关键词匹配和正则表达式从非结构化文本中提取结构化事实，为规则判定提供输入。证据门控作为质量保障机制，对分析结论进行充分性校验，防止在证据不足的情况下输出不可靠结论。输出格式化器将判定结果转化为结构化的诊断报告，包含问题概览、证据详情、因果链、修复步骤等完整信息。

技能与规则层的设计充分考虑了可扩展性。规则库采用注册表模式，新增场景只需定义规则对象并注册即可，无需修改引擎代码。证据规格同样支持声明式扩展，每个场景可以独立定义所需的证据项。多场景并行评估机制能够同时检测多个异常，并分析场景之间的关联性，识别共享根因或级联故障。

**推理层**负责整体的诊断流程编排和决策生成。该层支持两种工作模式：传统的 HolmesGPT agentic loop 模式和基于 LangGraph 的结构化工作流模式。在 agentic loop 模式下，大语言模型通过多轮工具调用迭代地收集信息、分析问题、生成结论，具有较高的灵活性。在工作流模式下，诊断过程被分解为问题定位、证据采集、根因分析、汇总报告四个明确的阶段，每个阶段由独立的节点执行，具有更好的可控性和可观测性。

推理层与技能层的集成是通过事件映射机制实现的。在工具调用完成后，系统会自动触发技能层的评估逻辑，将确定性判定结果附加到 LLM 的上下文中。这种设计使得 LLM 能够利用规则引擎的高置信度判定，同时保留对规则外场景的处理能力。两者形成互补关系：规则引擎提供准确性和可解释性，LLM 提供灵活性和覆盖范围。

**接口层**基于 FastAPI 构建，提供 RESTful API 和流式输出能力。系统支持文本流和 SSE 两种输出格式，前者适合人类阅读，后者适合前端应用集成。接口层还负责请求参数验证、错误处理、日志记录等横切关注点。通过 CORS 中间件配置，系统能够安全地为前端应用提供服务。

### 3.2 执行层设计

执行层的核心职责是提供安全、可控、可审计的集群操作能力。该层的设计遵循最小权限原则和职责单一原则，确保每个工具只执行明确定义的操作，不承担任何业务逻辑。

**工具集架构**采用分类管理的方式，将工具按功能域划分为多个工具集。Kubernetes 核心工具集提供 Pod、Node、Service、Deployment 等资源的只读查询能力，通过 kubectl 命令行工具实现。Helm 工具集支持 Release 列表查询、Chart 值获取等操作，便于诊断应用部署问题。Prometheus 工具集封装了 PromQL 查询接口，支持指标数据的时序分析。Bash 工具集提供受限的 Shell 命令执行能力，用于执行自定义诊断脚本，但默认处于禁用状态，需要通过环境变量显式启用。

**MCP 协议集成**是执行层的重要扩展机制。MCP 是一种标准化的工具调用协议，定义了工具的描述格式、参数规范和结果返回格式。系统通过 MCP 客户端连接到远程 MCP 服务器，动态加载工具定义。MCP 服务器可以用任何语言实现，只需遵循协议规范即可。这种设计使得系统能够轻松集成第三方诊断工具，如 Elasticsearch 日志查询、自定义监控系统、配置管理数据库等。

MCP 服务器支持两种通信模式：stdio 模式通过标准输入输出与子进程通信，适合本地工具；SSE 模式通过 HTTP 长连接接收服务器推送的事件，适合远程服务。系统优先使用 SSE 模式，因为它更适合分布式部署和容器化环境。

**权限控制与安全**是执行层设计的重点。系统通过 Kubernetes RBAC 机制限制 ServiceAccount 的权限范围。默认配置下，系统仅具有集群资源的只读权限，能够查询 Pod、Node、Service 等对象的状态，但不能进行修改或删除操作。对于需要修复能力的场景，可以通过 RBAC 配置授予特定资源的 patch 或 delete 权限，如 Deployment 的滚动重启、Pod 的强制删除等。

Bash 工具的安全控制更为严格。默认情况下，Bash 工具处于禁用状态。即使启用，也会维护一个命令白名单，只允许执行预定义的安全命令。对于需要执行任意命令的场景，必须设置 `BASH_TOOL_UNSAFE_ALLOW_ALL` 环境变量，并在审计日志中记录所有命令执行。

**审计与可追溯性**通过多层日志机制实现。每次工具调用都会记录调用时间、工具名称、参数、执行结果和耗时。对于失败的调用，会记录详细的错误信息和堆栈跟踪。这些日志不仅用于问题排查，也是合规审计的重要依据。在流式输出模式下，工具调用信息会实时推送给客户端，便于用户了解诊断进度。

### 3.3 技能与规则层设计

技能与规则层是本系统在模型推理之外引入的独立分析能力，旨在提升诊断结果的稳定性、可控性和可解释性。该层不依赖大语言模型的推理能力，而是通过确定性的算法和规则对数据进行分析和判定。

**规则引擎（RulesEngine）**是技能层的核心组件，采用声明式规则定义和条件匹配机制。每条规则描述了一个已知的故障场景，包含场景标识、适用层级、判定条件、基础置信度、修复步骤和根因模板等完整信息。规则引擎的工作流程分为四个阶段：首先通过关键词匹配检测当前场景，然后从工具输出中提取证据，接着进行规则条件匹配，最后计算置信度并生成判定结果。

规则条件支持多种操作符，包括存在性检查、数值比较、字符串包含和正则匹配等。多个条件可以通过 AND 或 OR 逻辑组合，满足不同场景的判定需求。例如，OOMKilled 场景的判定条件是检测到 "OOMKilled" 标记或退出代码为 137，两者满足其一即可匹配（OR 逻辑）。而磁盘满场景需要同时满足磁盘使用率超过阈值和存在 ENOSPC 错误信息（AND 逻辑）。

**置信度计算算法**是规则引擎的关键机制。系统为每条规则设定一个基础置信度分数（通常为 0.85-0.95），然后根据证据的采集情况进行扣减。每个缺失的证据会按其权重扣减分数，如果缺失的是关键证据，还会额外扣减 0.1 分作为惩罚。最终分数被映射为三个等级：0.8 以上为高置信度，0.5 至 0.8 为中置信度，0.5 以下为低置信度。这种机制确保了只有在充分证据支撑下，系统才会输出高置信度的判定结果。

**证据提取器（EvidenceExtractor）**负责从非结构化的工具输出中提取结构化信息。每个故障场景都有对应的证据规格定义，明确了需要采集的证据项及其提取方法。证据提取采用三层机制：首先通过关键词匹配判断证据是否存在，然后通过正则表达式提取具体数值（如退出代码、资源使用率、时间戳等），最后将提取结果构建为标准化的事实对象。事实对象包含键名、值、来源和信度等属性，为规则判定提供统一的数据接口。

证据规格的声明式设计使得新增场景的开发成本极低。运维人员只需定义该场景需要哪些证据、如何检测和提取，就可以让系统自动完成证据采集和分析，无需编写任何业务逻辑代码。

**证据门控（EvidenceGate）**是诊断质量保障的最后防线。该组件检查判定结果中关键证据的完整性，当发现关键证据缺失时，执行软拦截操作。所谓软拦截，是指不阻止输出结论，但会自动降低置信度等级，在报告中醒目标注证据缺失情况，并根据问题类别智能生成补采命令建议。

例如，当 OOMKilled 判定中缺少容器内存限制信息时，证据门控会将置信度从"高"降级为"低"，并建议执行 `kubectl describe pod <pod-name>` 命令获取资源限制详情。这种设计既保证了诊断的严谨性，又为用户提供了明确的行动指引。

**多场景并行评估器（MultiScenarioEvaluator）**扩展了规则引擎的能力，支持同时检测多个异常场景。传统的单场景检测在发现第一个匹配后就会停止，可能遗漏其他关联问题。多场景评估器对所有已注册的规则进行全量扫描，识别所有匹配的场景，并分析场景之间的关联关系。

关联分析识别三种关系类型：共享根因（多个问题源于同一个底层原因，如磁盘满导致多个 Pod 被驱逐）、级联故障（一个问题引发另一个问题，如 DNS 故障导致应用返回 503）和独立问题（多个不相关的问题同时存在）。这种分析有助于运维人员理解故障的全貌，避免"头痛医头"式的处理方式。

**输出格式化器（DecisionFormatter）**将判定结果转化为多种格式的输出。完整的 Markdown 报告包含问题概览表格、深度分析维度表格、详细证据表（区分已采集和缺失）、因果链可视化（ASCII 图）、时序分析、匹配规则详情、修复方案与验证步骤、下一步建议、数据来源列表和置信度说明等丰富内容。此外还支持简报模式（单行摘要，适合概览）和 JSON 摘要模式（结构化数据，适合 API 响应）。

### 3.4 推理层设计

推理层是系统的智能决策中心，负责理解用户意图、编排诊断流程、协调各层组件并生成最终的诊断报告。该层支持两种工作模式，适应不同的使用场景和精度要求。

**HolmesGPT 传统模式**采用 agentic loop（Agent 循环）的方式运行。在这种模式下，大语言模型接收用户问题和系统提示词后，进入迭代循环。每轮迭代中，LLM 分析当前信息，决定调用哪些工具获取更多数据，然后根据工具返回的结果进行推理，直到收集到足够的信息生成最终结论。这种模式的优势在于灵活性高，LLM 可以根据实际情况动态调整诊断策略，适合处理未知或复杂的故障场景。

系统提示词经过精心设计，为 LLM 提供了完整的诊断框架。提示词定义了两条处理路径：路径 A 用于直接回答简单查询（如"列出所有 Pod"），路径 B 用于进行深入的故障诊断。对于诊断场景，提示词引导 LLM 按照"收集信息 → 分层定位 → 分析根因 → 生成建议"的流程进行推理。同时，提示词中也包含了安全约束，禁止 LLM 执行可能影响集群稳定性的命令。

在传统模式下，技能层的集成通过事件映射机制实现。当 LLM 调用工具并获得结果后，系统会自动调用规则引擎对工具输出进行确定性分析。如果规则引擎检测到已知场景并生成了判定结果，该结果会被格式化为 Markdown 报告并附加到 LLM 的上下文中。这样，LLM 在后续推理中可以参考规则引擎的判定，生成更加准确和结构化的最终答案。

**LangGraph 工作流模式**将诊断过程分解为四个明确的阶段，每个阶段由独立的工作流节点执行。与传统模式相比，工作流模式具有更好的可控性、可观测性和可调试性。

**问题定位节点**负责理解用户意图并确定问题所属层级。该节点接收用户的自然语言问题，通过专门设计的提示词引导 LLM 进行意图分析。分析结果包括问题类型（QUERY 查询或 L0-L4 诊断）、定位置信度、关键实体（如 Pod 名称、命名空间、节点名等）和可能的场景列表。这些信息被结构化保存到工作流状态中，供后续节点使用。

**证据采集节点**根据问题定位结果制定证据采集计划并执行。对于查询类请求，该节点直接调用相应工具获取数据并返回。对于诊断类请求，该节点会根据问题层级和可能场景，规划需要采集的证据项，按照关键证据优先的原则依次调用工具获取数据。采集完成后，将证据项列表和完整度评估保存到工作流状态中。

**根因分析节点**是技能层与推理层深度融合的关键节点。该节点首先调用规则引擎对已采集的证据进行确定性分析，获得规则层面的判定结果。然后应用证据门控进行质量校验，必要时降低置信度。最后，LLM 基于规则引擎的判定结果和原始证据，进行补充分析和因果链构建。对于规则库覆盖的场景，LLM 主要起验证和补充作用；对于规则库未覆盖的场景，LLM 独立进行推理分析。

**汇总报告节点**整合前三个节点的全部分析结果，生成最终的诊断报告。该节点调用输出格式化器将判定结果转化为完整的 Markdown 报告，同时由 LLM 生成自然语言的汇总评论。最终报告包含性能统计信息，如 MTTR（平均修复时间）、根因置信度、证据完整率、工具调用详情等。

四个节点按照线性顺序执行，每个节点的输出通过 WorkflowState 传递给下一个节点。这种设计使得每个节点可以独立开发、测试和优化，同时保证了数据在节点间的完整传递。工作流状态包含了诊断过程的全部中间结果，便于调试和回溯。

### 3.5 联邦查询设计

联邦查询模块使系统能够管理和诊断多个 Kubernetes 集群，是企业级多集群运维的核心能力。该模块支持两种查询模式，分别适用于不同的使用场景。

**并发聚合模式（v1）**采用简单直接的方式处理多集群查询。主集群的 FederationCoordinator 同时向所有已注册的子集群发送查询请求，等待所有结果返回后，由 LLM 进行汇总分析和报告生成。这种模式的优势在于实现简单、延迟可控（总耗时等于最慢的子集群响应时间），适合对所有集群进行统一的状态巡检或对比分析。

**Agent-to-Agent 智能路由模式（v2）**采用更加智能的方式处理多集群查询。主集群的 FederationAgent 是一个具有工具调用能力的 LLM Agent，它通过两个工具与子集群交互：`list_clusters` 获取所有可用集群的列表和描述信息，`query_cluster` 向指定集群发送查询请求。

在 v2 模式下，LLM 首先分析用户问题的意图，判断需要查询哪些集群。如果用户明确指定了目标集群（如"查看 cluster-24 的 CPU 使用率"），LLM 会直接路由到指定集群。如果用户提出了全局性问题（如"哪个集群的负载最高"），LLM 会依次查询所有相关集群。这种设计使得系统能够智能地减少不必要的跨集群查询，降低延迟和资源消耗。

联邦查询的通信采用 HTTP 协议，主集群通过 httpx 异步客户端向子集群的 `/ask` 端点发送请求。子集群运行完整的诊断流程（包括工具调用、规则判定、报告生成），将结果返回给主集群。主集群负责汇总多个子集群的结果，生成跨集群的统一诊断报告。

为了提高并发效率，多个子集群查询使用 `asyncio.gather` 在单个事件循环中并发执行，共享一个 httpx 连接池。这种设计确保了总延迟等于最慢的单个子集群响应时间，而非所有子集群响应时间之和。

子集群的注册和管理通过配置文件进行。每个子集群配置包含名称、查询端点 URL、描述信息和启用/禁用标志。通过灵活的配置管理，运维团队可以动态地添加、移除或禁用子集群，无需修改代码或重启服务。

### 3.6 配置层设计

配置层作为系统的知识管理中枢，统一管理所有运维知识、诊断规则、系统提示词和运行参数。该层的设计目标是实现"知识即配置"，使得系统能够通过配置变更来适应新场景、新规则和新集群环境，而不需要修改代码和模型。

**Runbook 知识库**是配置层的核心组成部分。每个 Runbook 是一份结构化的运维手册，以 Markdown 文件形式存储，包含场景识别条件、关键证据清单、标准诊断流程、判定规则、修复方案和预防措施等完整信息。Runbook 的索引文件（catalog.json）定义了每个 Runbook 的唯一标识、名称、描述和文件路径，AI 通过语义匹配机制检索相关 Runbook。

知识库的加载采用优先级合并机制。系统内置的基础 Runbook 提供默认的诊断知识，用户自定义的 Runbook 可以通过配置目录或 Kubernetes ConfigMap 进行挂载。自定义 Runbook 与内置 Runbook 自动合并，同名条目以自定义版本优先。这种设计使得企业可以在不修改系统代码的情况下，添加针对自身业务的诊断知识。

**规则配置**采用声明式定义方式。每条规则是一个结构化的数据对象，包含规则标识、名称、适用层级、场景描述、问题类别、判定条件列表、条件组合逻辑、基础置信度、修复步骤列表、根因模板和因果链模板等完整信息。证据规格同样采用声明式定义，明确了每个场景需要采集的证据项，包括证据标识、描述、重要性级别、权重、检测关键词、提取正则表达式和值类型等。

**配置加载机制**支持多种来源和优先级策略。系统首先检测运行环境（Kubernetes 集群内或本地开发），根据环境自动选择配置文件路径。配置文件支持环境变量替换语法（`${VAR}` 和 `${VAR:-default}`），便于在不同环境中复用相同的配置模板。对于 LLM 相关配置（API Key、模型名称、API 端点），采用环境变量优先、配置文件次之、默认值兜底的优先级策略。

**多 LLM 提供商支持**是配置层的重要特性。系统通过 LiteLLM 统一接口支持 DeepSeek、Claude、GLM 智谱、OpenAI 等多种 LLM 提供商。切换提供商只需修改 LLM_MODEL 和 LLM_API_BASE 环境变量，无需修改任何代码。这种设计降低了对单一 LLM 提供商的依赖，也便于在不同提供商之间进行效果对比和成本优化。

## 四、关键模块实现

### 4.1 服务编排器（HolmesService）

HolmesService 是系统的核心编排组件，采用全局单例模式实现。它负责管理系统的初始化流程、配置加载、AI 实例创建以及查询执行。

初始化流程遵循严格的顺序依赖关系。首先检测运行环境并加载配置文件，然后进行环境变量替换，创建 AI 实例（包括工具集加载和 MCP 连接），最后初始化 Runbook 管理器和联邦查询模块。整个初始化过程受到线程锁保护，确保在多线程环境中只执行一次。初始化支持超时控制，当超过指定时间后，系统会在后台继续初始化，同时允许健康检查端点返回初始化中的状态。

查询执行支持同步和流式两种模式。同步模式等待完整结果返回后一次性响应，适合简单查询和 API 集成场景。流式模式通过 Python 生成器逐步产出事件，支持文本流和 SSE 两种格式。工作流模式的集成通过 `USE_WORKFLOW` 环境变量控制，当启用时，查询请求会被路由到 LangGraph 工作流执行器。

### 4.2 事件系统

事件系统是流式输出的基础架构，定义了一套标准化的事件协议。每个事件包含类型标识、唯一 ID（基于 SHA1 哈希）、运行 ID（16 字符 UUID）、序列号和毫秒级时间戳，以及类型相关的负载数据。

事件映射层负责将 HolmesGPT 的内部事件转换为系统定义的标准事件。在转换过程中，系统会执行工具输出预处理（截断超长输出并存储为工件）、AI 消息提取（区分推理过程和最终结论）和确定性决策评估（在工具结果事件中触发技能层分析）。

工件存储系统采用内存 LRU 缓存机制，用于存储被截断的大型工具输出。每个工件有 30 分钟的 TTL（生存时间），缓存最大容量为 200 个条目。当工具输出超过 1200 字符时，系统会存储完整输出到工件存储，在事件中只包含预览和工件引用 ID。客户端可以通过 `/artifacts/{id}` 端点获取完整的工具输出。

### 4.3 流式输出

流式输出是系统用户体验的重要组成部分。文本流格式采用了精心设计的可视化方案，使用 emoji 图标和分隔线来区分不同类型的信息，包括工具调用开始和完成、AI 推理过程、迭代统计和最终答案等。这种设计使得用户可以在终端中直观地跟踪诊断进度。

SSE 流格式遵循 HTTP Server-Sent Events 标准，每个事件包含事件类型和 JSON 格式的数据负载。定义的事件类型包括 `run_start`（查询开始）、`tool_start`（工具调用开始）、`tool_result`（工具结果）、`ai_message`（AI 消息）、`iteration_end`（迭代结束）、`final`（最终答案）和 `run_end`（查询结束）。前端应用可以解析这些事件，构建实时更新的诊断界面。

### 4.4 Kubernetes 部署架构

系统为 Kubernetes 环境提供了完整的部署方案，包括 Deployment、Service、RBAC、ConfigMap 和 Secret 等资源。

容器镜像基于 Python 3.12 slim 构建，额外安装了 kubectl v1.29.0、Helm 3.14.0 以及网络诊断工具（net-tools、dnsutils、netcat 等），为 AI 提供完整的集群诊断工具链。镜像采用非 root 用户运行，遵循最小权限原则。

RBAC 配置定义了精细化的权限控制。默认的 ClusterRole 授予了对集群资源的只读权限，覆盖 Pod、Node、Service、Deployment、Event 等核心对象。对于需要修复能力的场景，ClusterRole 还包含了对 Deployment、DaemonSet、StatefulSet 的 patch 和 delete 权限，以及对 Pod 的 delete 权限和对 ConfigMap 的 patch 权限。

配置管理采用 ConfigMap 和 Secret 分离的策略。ConfigMap 存储非敏感配置，包括工具集配置、MCP 服务器配置、联邦查询配置和 Runbook 知识库。Secret 存储敏感配置，包括 LLM API Key、工作流开关和安全相关参数。两者都支持热更新，修改后通过 Pod 重启即可生效。

Service 类型为 NodePort，默认端口 30800，便于在集群外部访问。对于生产环境，建议通过 Ingress 或 LoadBalancer 对外暴露服务。

## 五、技术选型与实现优势

### 5.1 技术栈选择

**FastAPI** 作为 Web 框架的选择基于其对异步编程的原生支持、自动 API 文档生成和高性能特性。FastAPI 的异步能力使得系统能够高效处理并发请求和流式输出，同时其 Pydantic 集成提供了强类型的请求参数验证。

**HolmesGPT** 作为 AI Agent 框架的选择基于其专为运维场景设计的工具集生态。HolmesGPT 内置了 Kubernetes、Helm、Prometheus 等运维工具的集成，提供了成熟的工具调用循环和流式事件机制。通过封装层的设计，系统在利用 HolmesGPT 核心能力的同时，保持了架构的灵活性和可替换性。

**LangGraph** 作为工作流编排引擎的选择基于其对有向图工作流的原生支持。LangGraph 提供了声明式的图定义 API、状态管理和流式执行能力，使得系统能够将复杂的诊断流程分解为可管理的节点序列。其与 LangSmith 的集成也为工作流的可观测性和调试提供了便利。

**LiteLLM** 作为 LLM 统一接口的选择基于其对多提供商的透明支持。通过 LiteLLM，系统可以用统一的 API 调用 DeepSeek、Claude、GPT-4、GLM 等不同提供商的模型，切换提供商只需修改模型标识符，无需修改调用代码。

### 5.2 实现优势总结

**确定性与灵活性的平衡**。规则引擎提供了高置信度的确定性判定，LLM 提供了对未知场景的灵活处理能力。两者通过证据门控和事件映射机制有机结合，既保证了已知场景的诊断准确性（>95%），又保留了对新场景的适应能力。

**可解释性与可审计性**。每个诊断结论都有完整的证据链支撑，包括证据来源、采集方法、判定规则和置信度计算过程。因果链可视化使得诊断逻辑一目了然。所有工具调用和推理过程都有详细的日志记录，满足企业级应用的审计要求。

**渐进式演进能力**。通过配置外置的设计，系统可以在不修改代码的情况下不断积累运维知识和诊断规则。新增故障场景只需定义规则和证据规格，新增运维知识只需编写 Runbook 文档。这种设计降低了系统维护和演进的技术门槛。

**多模式适配**。系统同时支持简单查询和深度诊断、文本流和结构化输出、单集群和多集群管理等多种使用模式。通过环境变量和配置参数的灵活控制，同一套代码可以适应开发、测试和生产等不同环境的需求。

**性能与用户体验**。流式输出使得用户可以实时跟踪诊断进度，而不是等待漫长的处理过程。联邦查询的并发执行机制确保了多集群查询的延迟可控。工件存储和缓存机制优化了大数据量场景下的内存使用和传输效率。
