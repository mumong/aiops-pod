# 流式输出设计

本文说明 AIOps Copilot 当前的流式输出设计：AICall + LangGraph 事件流和 token 级输出。

重点回答几个问题：

- 当前 token 级输出是怎么实现的。
- text 与 SSE 两种输出格式的差异。
- 客户端断开、取消和 heartbeat 的处理。
- 当前实现仍有哪些边界。

> 历史沿革（一句话版）：早期 HolmesGPT 单节点一次性返回 → 服务层按行/阶段流式 →
> 当前 AICall agent stream 的 `ai_token/tool_start/tool_result/node_complete` 事件级实时渲染。

## 1. 整体链路：AICall + LangGraph 事件和 token 级输出

当前实现已经从 HolmesGPT 内部调用迁移到自研 `AICall`，底层使用 LangChain / LangGraph 的 agent stream。

核心链路：

```text
FastAPI StreamingResponse
  -> HolmesService.execute_query_stream()
  -> HolmesService._workflow_to_text()
  -> WorkflowExecutor.execute_stream()
  -> 后台线程运行 LangGraph workflow.stream()
  -> 节点通过 event_queue 推送 node_lifecycle / thinking
  -> AICall.call() 通过 agent.astream() 接收 updates + messages
  -> 服务层把事件渲染为 text 或 SSE
```

关键实现文件：

- `app/api/routes.py`
  - `_stream_response()` 创建 `StreamingResponse`。
  - 客户端断开时通过 `cancel_event` 通知后台停止。
- `app/core/service.py`
  - `execute_query_stream()` 是服务层流式入口。
  - `_workflow_to_text()` 把 workflow event 渲染成终端友好的文本。
  - `ThinkStreamFilter` 处理 `<think>` 展示策略。
- `app/core/workflow/executor.py`
  - `execute_stream()` 运行 LangGraph workflow。
  - 后台线程执行 `workflow.stream(initial_state)`。
  - 主线程消费 `event_queue`，实时 yield 事件。
- `app/core/workflow/nodes/base.py`
  - 节点调用 `AICall.call(..., stream_queue=self._event_queue)`。
- `app/core/aicall/client.py`
  - `ChatOpenAI(streaming=True, stream_usage=True)` 开启模型流。
  - `agent.astream(..., stream_mode=["updates", "messages"])` 同时接收工具事件和 token 消息。

### 4.1 事件级输出

LangGraph 工作流本身会产生节点级事件：

```text
node_start
node_complete
heartbeat
final
```

节点内部的 AICall 会产生 thinking 事件：

```text
tool_start
tool_result
ai_message
ai_token
iteration_end
```

这些事件都进入同一个 `event_queue`，由 `WorkflowExecutor.execute_stream()` 统一向上游 API 输出。

### 4.2 Token 级输出

当前 token 级输出来自 `AICall.call()` 中的 LangGraph agent stream。

关键逻辑是：

```python
async for chunk in agent.astream(
    input_messages,
    config=config,
    stream_mode=["updates", "messages"],
    version="v2",
):
    if chunk_type == "messages":
        token_msg, metadata = chunk_data[0], chunk_data[1]
        if token_msg.content and metadata["langgraph_node"] != "tools":
            push_event(stream_queue, "ai_token", node_id, content=token_msg.content)
```

含义：

- `updates` 模式负责拿工具调用、工具结果、AI message 等结构化更新。
- `messages` 模式负责拿模型增量 message chunk，也就是 token/chunk 级内容。
- 来自 `tools` 节点的 message 不作为模型 token 输出，避免把工具返回内容当成模型生成 token。
- 每个 token chunk 会变成 `thinking` 事件，类型是 `ai_token`。
- `service._workflow_to_text()` 收到 `ai_token` 后，不再等整段 message，而是直接写到响应流。

终端渲染大致是：

```text
   💭 [证据链采集] 好的，我需要先确认这个 Pod 当前是否还存在...
```

当连续 token 到达时，服务层不会每个 token 都加一行前缀，而是在本段 token 流开始时输出一次：

```text
   💭 [节点名] 
```

之后直接追加 token，直到下一个非 token 事件到来再换行。

### 4.3 `<think>` 输出处理

本地推理模型可能输出 `<think>...</think>`。当前服务层提供 `ThinkStreamFilter`，支持三种模式：

```yaml
workflow:
  think_stream:
    mode: full
    max_chars: 1200
```

模式：

- `full`：完整展示 `<think>` 内容。
- `truncated`：只展示每段 think 的前 `max_chars` 字符。
- `hidden`：隐藏 think 内容。

环境变量也可以覆盖：

```bash
AIOPS_THINK_STREAM_MODE=full|truncated|hidden
AIOPS_THINK_STREAM_MAX_CHARS=1200
```

注意：最终报告节点会剥离 `<think>`，避免在正式报告中暴露模型内部推理文本。

## 2. 当前流式输出的实际边界

当前已经实现了 token 级输出，但不是所有节点都完全 token streaming。

### 5.1 已支持 token 级输出的部分

主要是走 `AICall.call()` 的 agent/tool 节点，例如：

- layer 节点。
- evidence 节点。
- rca full 模式时的 RCA 节点。

这些节点使用 LangGraph agent loop，能从 `agent.astream(..., stream_mode=["messages"])` 拿到 token chunk。

### 5.2 仍是整段返回的部分

部分简单 LLM 调用仍使用 `call_simple()` / `call_simple_json()`，它们当前主要是 invoke 风格：

- RCA lite 模式。
- conclusion 汇总总结。
- 部分工具 observation LLM summarizer。

因此最终大报告通常还是在 conclusion 节点完成后整段输出，而不是逐 token 输出。

这不是 HTTP 流式层的问题，而是该节点当前选择了简单调用路径，目的是降低复杂度、避免工具重复调用，并保证最终报告结构稳定。

### 5.3 为什么用户仍会感觉“现在是 token 级”

因为在 layer/evidence 这些耗时和工具交互最多的节点里，模型的 `<think>`、计划、工具前后分析已经可以按 token/chunk 输出。用户能看到模型正在想什么、下一步要调用什么工具、工具结果回来后模型如何继续推理。

但严格说，当前系统是：

```text
工作流事件级流式 + agent 节点 token 级流式 + conclusion 整段输出
```

不是“所有节点所有输出都 token streaming”。

## 3. text 与 SSE 两种输出格式

接口参数：

```text
format=text  # 默认，适合 curl/终端
format=sse   # 适合前端 EventSource
```

### 6.1 text 模式

`text` 模式由 `HolmesService._workflow_to_text()` 渲染，输出人类可读的终端文本：

```text
📍 [问题定位] 执行中...
💭 [问题定位] 调用工具: kubectl_get_by_kind_in_cluster
✅ [问题定位] 完成 (6.3s)
```

它的目标是让 `curl --no-buffer` 直接可读。

### 6.2 SSE 模式

`sse` 模式使用 `create_sse_message_cn()` 包装：

```text
event: thinking
data: {"node":"evidence","thinking_type":"tool_start","tool_name":"kubectl_describe"}
```

它更适合前端页面消费，因为前端可以按 event 类型渲染不同 UI。

## 4. 客户端断开与取消

当前 `_stream_response()` 会为每个请求创建 `cancel_event`。

当客户端断开，例如 `curl Ctrl+C`，生成器捕获 `GeneratorExit`：

```text
客户端断开 -> cancel_event.set()
```

工作流和 AICall 在循环中检查 `cancel_event`：

```text
WorkflowExecutor.execute_stream()
  -> 检查 cancel_event

AICall.call()
  -> agent.astream 循环中检查 cancel_event
```

这样可以避免客户端断开后后台仍持续跑很久。

## 5. 为什么要保留 heartbeat

即使有 token streaming，也仍然需要 heartbeat。

原因：

- 工具调用期间没有模型 token。
- 某些 MCP 工具执行时间较长。
- 某些模型调用可能长时间没有 chunk。
- 网络代理或客户端可能因为长时间无输出断开。

因此 `WorkflowExecutor` 在队列一段时间没有新事件、且节点仍在执行时，会输出：

```text
⏳ [证据链采集] 仍在处理，等待工具或模型返回...
```

这类 heartbeat 不是模型输出，而是服务层可观测性事件。

## 6. 与上下文管理的关系

流式输出和上下文管理是两件事，但现在它们共享同一套 `thinking_events` 和工具 observation 处理链路。

工具结果返回后会发生：

```text
工具 raw 输出
  -> ObservationProcessor
  -> raw/structured/summary 落盘
  -> ToolMessage.content 替换为 summary
  -> thinking event 记录 raw_ref/summary_ref/structured_ref
  -> 流式输出展示 result_preview
```

所以现在用户在终端看到的是工具摘要，而不是完整 raw。

完整 raw 在 context archive 中：

```text
/tmp/aiops/reports/context_archives/<run_id>/tools/*.raw.txt
```

这能同时解决两个问题：

- 流式输出不被大段 YAML/Events 淹没。
- 模型上下文不会被工具 raw 撑爆。

## 7. 当前架构总结

当前流式架构可以概括为：

```text
FastAPI StreamingResponse
  -> generator
  -> HolmesService.execute_query_stream
  -> WorkflowExecutor.execute_stream
  -> event_queue
  -> LangGraph workflow.stream
  -> WorkflowNode._call_llm
  -> AICall.call
  -> agent.astream(updates + messages)
  -> ai_token / tool_start / tool_result / node_complete
  -> text 或 SSE 渲染
```

这个架构相比 HolmesGPT 早期模式的关键变化是：

- 模型调用层由项目自己控制。
- 工具 loop 的事件由项目自己采集。
- 节点生命周期由 workflow executor 统一管理。
- token chunk 可以直接进入事件队列。
- 工具 raw、摘要、引用和上下文预算可以和流式事件打通。

## 8. 后续可优化方向

如果后续需要“真正全链路 token 级输出”，主要还需要补这些点：

- 将 `call_simple()` 改成支持 streaming invoke，用于 RCA lite 和 conclusion。
- conclusion 节点边生成边输出，而不是完整报告完成后再输出。
- SSE 模式中区分 `ai_token`、`final_token`、`think_token`，方便前端分别渲染。
- 对 token 级输出增加批量 flush，避免极小 token 导致前端刷新过于频繁。
- 在 `hidden` 模式下不只是隐藏 `<think>`，也可以把隐藏片段计入日志统计，便于排查模型是否仍在输出内部推理。

当前实现已经满足运维诊断的核心目标：长任务可见、工具调用可见、节点边界清晰、agent 节点支持 token/chunk 级实时输出。
