# Robusta AIOps 平台整体流程说明

## 一、概述

本文档详细阐述 Robusta AIOps 平台从用户请求接入到最终报告生成的完整处理流程。系统支持三种核心工作流程：单集群传统模式诊断、单集群工作流模式诊断和多集群联邦查询。每种流程在请求处理、信息采集、分析推理和结果输出等环节都有各自的特点和适用场景。通过对各流程的深入说明，帮助读者理解系统如何将用户的自然语言查询转化为结构化的运维诊断报告。

## 二、系统启动与初始化流程

### 2.1 应用启动

系统采用 FastAPI 框架构建，通过 Uvicorn ASGI 服务器启动。应用启动时，首先创建 FastAPI 实例并注册路由和中间件，然后进入生命周期管理阶段。

生命周期管理器在应用启动时执行一系列初始化操作。首先检查是否需要自动启动本地 MCP 服务器（通过 `MCP_AUTO_START_LOCAL` 环境变量控制），如果需要，则解析配置文件中的 MCP 服务器定义，筛选出标记为自动启动且指向本地地址的服务器，通过子进程方式启动它们并等待其就绪。

随后，系统初始化 HolmesService 单例实例。HolmesService 的初始化是一个多步骤的过程，包括环境检测、配置加载、AI 实例创建和资源准备。整个初始化过程受到线程锁保护，确保在多线程环境下只执行一次。初始化支持超时控制：如果设置了 `HOLMES_INIT_TIMEOUT_SECONDS` 环境变量，当初始化超过指定时间后，系统会在后台继续完成初始化，同时让应用开始接受请求。健康检查端点会如实反映初始化状态（initializing/healthy/unhealthy）。

初始化完成后，系统会通过自检模块输出加载资源的摘要信息，包括已加载的工具集数量、MCP 连接状态、Runbook 数量和联邦集群配置等。这些信息有助于运维人员快速确认系统状态。

### 2.2 配置加载流程

配置加载是初始化过程中的关键步骤，采用多层优先级策略确保灵活性和安全性。

首先，系统检测运行环境。通过检查 Kubernetes ServiceAccount Token 文件和 `KUBERNETES_SERVICE_HOST` 环境变量来判断是否运行在 Kubernetes 集群内。根据环境自动选择配置文件：集群内使用 `config/config.k8s.yaml`，本地开发使用 `config/config.yaml`。如果设置了 `CONFIG_FILE` 环境变量，则使用指定的配置文件路径，覆盖自动检测逻辑。

然后，系统加载 YAML 配置文件并执行环境变量替换。配置文件中可以使用 `${VAR}` 语法引用环境变量，支持 `${VAR:-default}` 语法设置默认值。环境变量替换在所有配置项（包括嵌套的字典和列表）中递归执行。

LLM 相关配置采用专门的优先级策略。API Key 的优先级顺序为：`LLM_API_KEY` 环境变量 > 配置文件 `llm.api_key` > `DEEPSEEK_API_KEY` 环境变量 > `OPENAI_API_KEY` 环境变量。模型名称的优先级为：`LLM_MODEL` 环境变量 > 配置文件 `llm.model` > 默认值 `deepseek/deepseek-chat`。这种设计使得在 Kubernetes Secret 中管理敏感信息变得简单安全。

配置加载完成后，系统会清理配置文件中的非 Holmes 字段（如 `stream_output`、`federation`、`llm` 等自定义扩展），将清理后的配置写入临时文件，通过 HolmesGPT 的标准配置加载接口读取。这种适配层设计使得系统可以在标准 Holmes 配置之外扩展自定义配置项。

### 2.3 Runbook 知识库加载

Runbook 管理器在初始化时加载知识库。首先加载自定义的 Runbook 目录（`knowledge_base/runbooks/`），读取索引文件（`catalog.json`）中的 Runbook 定义，验证每个引用的 Markdown 文件是否存在。然后将自定义 Runbook 与 HolmesGPT 内置的 Runbook 进行合并，生成完整的知识库目录。

知识库加载完成后，系统会配置 Runbook 的搜索路径，确保 AI 在诊断过程中可以通过 `fetch_runbook` 工具检索相关知识。在 Kubernetes 环境中，Runbook 可以通过 ConfigMap 挂载到指定目录，实现知识库的动态更新。

## 三、请求处理流程

### 3.1 请求接入与参数解析

所有用户请求通过 HTTP API 接入系统。主要的查询端点为 `/ask`，同时支持 GET 和 POST 方法。GET 请求通过查询参数 `q` 传递问题文本，POST 请求通过 JSON 请求体传递。此外，系统提供了 `/q/{question}` 路径参数形式的快捷端点。

请求参数包括：`q`（问题文本，必填）、`stream`（是否启用流式输出）、`format`（输出格式，text 或 sse）、`max_steps`（最大工具调用迭代次数）。系统会对问题文本进行双重编码修复，处理某些客户端将 UTF-8 文本进行了两次 URL 编码的情况，确保中文等非 ASCII 字符被正确解析。

根据请求参数和全局配置，系统选择同步响应或流式响应模式。如果启用了流式输出（通过请求参数或全局配置），系统返回 `StreamingResponse`，内容类型根据输出格式设置为 `text/plain` 或 `text/event-stream`。否则返回 `PlainTextResponse`，等待完整结果后一次性响应。

### 3.2 模式路由

请求接入后，系统根据 `USE_WORKFLOW` 环境变量选择执行模式。这是一个全局开关，决定了整个系统的诊断策略。

当 `USE_WORKFLOW=false`（默认值）时，系统使用 HolmesGPT 传统模式。在这种模式下，大语言模型通过迭代式的工具调用循环自主进行诊断。LLM 具有较大的自由度，可以根据实际情况灵活调整诊断策略、选择工具和组织输出。

当 `USE_WORKFLOW=true` 时，系统使用 LangGraph 工作流模式。在这种模式下，诊断过程被分解为四个明确的阶段，每个阶段由独立的工作流节点执行。工作流模式具有更好的结构化和可控性，输出格式更加规范。

两种模式使用不同的提示词体系：传统模式使用单一的 `SYSTEM_PROMPT`，工作流模式为每个节点使用专门的提示词（`LAYER_CLASSIFIER_PROMPT`、`EVIDENCE_COLLECTOR_PROMPT`、`ROOT_CAUSE_ANALYZER_PROMPT`、`CONCLUSION_FORMATTER_PROMPT`）。

## 四、传统模式诊断流程

### 4.1 消息构建

进入传统模式后，系统首先构建初始消息序列。消息序列包含系统提示词和用户问题两部分。

系统提示词为 LLM 定义了角色（K8s-SRE Agent）、工作范围、安全约束和输出格式要求。提示词中包含了 Kubernetes 五层诊断模型的详细说明，引导 LLM 按照层级结构进行故障定位。同时，提示词定义了两条处理路径：路径 A 用于直接数据查询（如"列出所有 Pod"），路径 B 用于故障诊断分析。每条路径都有对应的输出模板，确保输出格式的一致性。

如果已加载 Runbook 知识库，系统会将 Runbook 目录信息（包含每个 Runbook 的名称和描述）附加到系统提示词中，告知 LLM 可用的运维知识库。LLM 可以在诊断过程中调用 `fetch_runbook` 工具检索相关知识。

### 4.2 LLM 迭代循环

消息构建完成后，系统将消息序列传递给 HolmesGPT 的 AI 实例，开始迭代式的工具调用循环。这是传统模式的核心执行逻辑。

在每轮迭代中，LLM 分析当前上下文中的所有信息（包括系统提示词、用户问题、之前的工具调用结果等），决定下一步行动。如果 LLM 认为需要更多信息，它会生成一个或多个工具调用请求。系统执行这些工具调用，将结果追加到消息序列中，然后进入下一轮迭代。如果 LLM 认为已经收集到足够的信息，它会生成最终的分析报告，迭代循环结束。

迭代次数受到 `max_steps` 参数的限制（默认为 20），防止无限循环。在实际运行中，大多数诊断任务在 3-8 轮迭代内完成。每轮迭代的耗时主要取决于 LLM 推理时间和工具执行时间，通常在 2-10 秒之间。

### 4.3 工具调用与结果处理

LLM 在迭代过程中可以调用系统加载的所有工具。工具调用的选择完全由 LLM 根据工具的名称和描述进行语义匹配。例如，当 LLM 需要查看 Pod 状态时，它会调用 `kubectl_get` 工具；当需要查看 Pod 日志时，它会调用 `kubectl_logs` 工具；当需要检索运维知识时，它会调用 `fetch_runbook` 工具。

工具执行完成后，系统对结果进行预处理。对于超过 1200 字符的长输出，系统会截取前 500 字符作为预览，将完整输出存储到工件存储中，并在结果中附加工件引用 ID。这种设计避免了大量工具输出占用 LLM 的上下文窗口，同时保留了访问完整数据的能力。

### 4.4 确定性决策集成

在传统模式中，技能层的集成通过事件映射机制实现。每当工具调用完成并返回结果时，系统会自动调用规则引擎对累积的工具输出进行确定性分析。

规则引擎首先进行场景检测，通过关键词匹配识别当前问题可能属于哪个已知场景（如 OOMKilled、磁盘满等）。然后从工具输出中提取结构化证据，进行规则条件匹配并计算置信度。如果规则引擎成功检测到已知场景并生成了判定结果，输出格式化器会将结果转化为 Markdown 报告。

这份 Markdown 报告会被附加到 LLM 的上下文中，作为"确定性分析参考"提供给 LLM。LLM 在生成最终答案时可以参考这些信息，从而生成更加准确和结构化的诊断报告。需要注意的是，确定性决策是一种软集成：它不会替代 LLM 的推理过程，而是为 LLM 提供高置信度的参考信息。LLM 可以选择采纳、补充或在必要时质疑规则引擎的判定。

### 4.5 最终答案选择

LLM 迭代循环结束后，系统需要从多个候选答案中选择最终输出。候选答案可能来自两个来源：HolmesGPT 框架的标准输出和 LLM 最后一轮迭代的直接输出。

最终答案选择算法考虑多个因素。如果存在需要人工审批的操作（如删除资源等破坏性操作），优先使用框架输出，因为它包含了审批提示信息。如果框架输出包含 DSML（领域特定标记语言）而 LLM 直接输出不包含，优先使用 LLM 输出以避免格式混乱。如果 LLM 直接输出具有结构化的报告格式（包含标题和分析内容），优先使用它。如果框架输出过短（少于 200 字符）且 LLM 有更详细的输出，优先使用 LLM 输出。

这种选择机制确保了最终输出既包含规则引擎的结构化判定，又保留了 LLM 的丰富分析和自然语言表达能力。

### 4.6 流式输出处理

在流式模式下，上述整个流程的中间结果会实时推送给客户端。文本流格式使用清晰的视觉标记来区分不同类型的信息。

查询开始时输出标题行，包含问题文本和初始化耗时。每次工具调用开始时输出工具名称和参数，工具完成时输出状态标记（成功/失败）、耗时和结果预览。LLM 的推理过程以对话气泡形式输出。每轮迭代结束时输出统计信息（Token 消耗、累计耗时）。最终答案以醒目的分隔线框起。

SSE 流格式则将每个阶段的信息封装为标准的 Server-Sent Event，包含事件类型和 JSON 格式的数据负载。前端应用可以通过事件类型进行分类处理，构建实时更新的诊断界面。

## 五、工作流模式诊断流程

### 5.1 工作流初始化

当 `USE_WORKFLOW=true` 时，系统使用 LangGraph 工作流模式执行诊断。工作流执行器首先构建诊断工作流图，定义四个节点和它们之间的连接关系。

工作流使用 LangGraph 的 `StateGraph` API 构建，以 `WorkflowState` 类型字典作为共享状态。四个节点按线性顺序连接：问题定位（layer）→ 证据采集（evidence）→ 根因分析（rca）→ 汇总报告（conclusion）。起始节点设置为问题定位节点，结束节点设置为汇总报告节点。

工作流状态是一个类型化字典，包含了诊断过程中所有需要在节点间传递的数据。初始状态只包含用户问题和运行 ID，每个节点执行后会向状态中添加新的字段（如层级判定、证据列表、确定性决策等）。后续节点可以读取前序节点的输出，实现数据的链式传递。

### 5.2 节点一：问题定位

问题定位是诊断流程的第一步，其目标是理解用户意图并确定问题所属的技术层级。该节点使用专门设计的 `LAYER_CLASSIFIER_PROMPT` 提示词引导 LLM 进行分析。

提示词要求 LLM 从以下维度分析用户问题：问题类型（查询还是诊断）、如果是诊断则属于哪个层级（L0-L4）、判定的置信度和推理过程、问题涉及的关键实体（如 Pod 名称、命名空间、节点名、服务名等）、可能的故障场景（如 OOMKilled、磁盘满、网络不通等）。

LLM 的分析结果以 JSON 格式输出，包含层级判定（layer）、置信度（confidence）、推理说明（reasoning）、关键实体列表（key_entities）和可能场景列表（possible_scenarios）。系统解析 JSON 输出并更新工作流状态。

这一步骤的设计意义在于为后续的证据采集提供方向性指引。通过预先确定问题层级，系统可以有针对性地采集该层相关的证据，避免盲目的全量信息收集。同时，可能场景的识别为规则引擎的快速匹配提供了候选范围。

对于查询类请求（layer=QUERY），后续节点会调整处理策略：证据采集节点直接执行查询并返回数据，根因分析节点仅整理数据而不构建因果链，汇总报告节点使用查询模板而非诊断模板。这种路径分化确保了简单查询不被过度处理。

### 5.3 节点二：证据采集

证据采集节点根据问题定位结果，制定并执行证据采集计划。该节点的行为因问题类型而异。

对于查询类请求（QUERY 层），证据采集节点的行为与传统模式的工具调用类似。LLM 根据用户问题选择合适的工具（如 `kubectl get pods`、`helm list` 等），执行查询并收集结果。这一阶段的输出直接包含用户所需的数据，不进行诊断分析。

对于诊断类请求（L0-L4），证据采集节点的工作更加精细化。节点使用 `EVIDENCE_COLLECTOR_PROMPT` 提示词引导 LLM 制定分层的证据采集计划。提示词中包含了每个层级应采集的典型证据项列表，以及证据的优先级分类（关键/重要/可选）。

LLM 根据问题定位节点识别的层级和可能场景，选择需要采集的证据项，制定工具调用序列，然后依次执行。例如，对于 L2 层的 OOMKilled 问题，LLM 可能会依次执行以下工具调用：`kubectl describe pod` 获取 Pod 详细信息和终止原因、`kubectl logs --previous` 获取崩溃前的日志、`kubectl get pod -o yaml` 获取资源限制配置、`kubectl top pod` 获取实时资源使用情况。

证据采集完成后，节点将采集到的证据项列表和证据完整度评估保存到工作流状态中。证据完整度是一个百分比值，反映了预期证据中实际成功采集的比例。

### 5.4 节点三：根因分析

根因分析节点是整个工作流中最核心的环节，它融合了确定性规则判定和 LLM 推理分析两种能力。

对于查询类请求，根因分析节点的功能简化为数据整理。LLM 对证据采集节点获取的原始数据进行结构化整理，提取关键信息，但不进行因果分析。

对于诊断类请求，根因分析节点执行以下步骤：

首先，节点将所有已采集的证据传递给规则引擎。规则引擎通过关键词匹配检测场景类型，从工具输出中提取结构化事实（如退出代码、资源使用率、错误信息等），然后尝试匹配已注册的规则。如果找到匹配的规则，规则引擎计算置信度分数并生成确定性决策对象。确定性决策包含问题层级、场景描述、置信度等级和分数、已采集证据列表、缺失证据列表、因果链、修复步骤等完整信息。

然后，节点将确定性决策传递给证据门控组件。证据门控检查关键证据的完整性，如果发现有关键级别的证据缺失，会自动降低置信度等级（例如从"高"降为"低"），并在决策的下一步建议中插入补采命令。这种机制确保了只有在充分证据支撑下才会输出高置信度结论。

接下来，LLM 基于规则引擎的判定结果和原始证据进行补充分析。如果规则引擎成功匹配了已知场景，LLM 主要起验证和补充作用：验证规则判定的合理性，补充规则模板中未涵盖的上下文信息，丰富因果链的描述。如果规则引擎未能匹配任何已知场景（可能是规则库尚未覆盖的新故障类型），LLM 独立进行根因推理，构建因果链并评估置信度。

最后，节点支持多场景并行评估。当系统检测到工具输出中可能同时存在多个异常时（例如磁盘满和 OOMKilled 同时发生），多场景评估器会对所有已注册的规则进行全量扫描，识别所有匹配的场景，并分析场景之间的关联关系（共享根因、级联故障或独立问题）。

### 5.5 节点四：汇总报告

汇总报告节点整合前三个节点的全部分析结果，生成面向用户的最终诊断报告。

对于查询类请求，汇总节点使用查询输出模板，直接展示数据结果。模板包含简短的概述和按类别组织的数据表格，不包含诊断分析和修复建议。

对于诊断类请求，汇总节点执行以下流程：

首先，如果存在确定性决策，调用输出格式化器生成 Markdown 格式的诊断报告。完整的 Markdown 报告包含以下部分：**问题概览**以表格形式展示层级、场景、置信度等关键指标；**深度分析**从基础设施、集群、工作负载、服务和应用等维度进行评估；**证据详情**分为已采集证据和缺失证据两个子表；**因果链**以 ASCII 图形可视化因果关系；**时序分析**展示事件的发生顺序；**匹配规则**列出所有被匹配的规则及其条件；**修复方案**提供分步骤的修复指令；**验证步骤**提供修复后的验证命令；**下一步建议**汇总后续行动项；**数据来源**列出所有被调用的工具和获取的数据；**事实提取**展示从数据中提取的结构化事实；**置信度说明**解释置信度计算过程。

然后，LLM 基于所有分析结果生成自然语言的汇总评论，对诊断过程进行整体评价和要点提炼。

最后，节点收集性能统计信息，包括各节点的执行耗时、工具调用次数和详情、Token 消耗、证据完整率和根因置信度等指标。这些信息被附加到报告末尾，为诊断过程的透明度和可审计性提供支撑。

### 5.6 工作流事件流

在工作流模式下，系统通过事件流实时向客户端推送诊断进度。工作流执行器产生的事件包括：

**run_start 事件**在工作流开始时发出，包含问题文本、时间戳和配置信息。

**node_start 事件**在每个节点开始执行时发出，包含节点标识和节点名称。客户端可以据此显示当前正在执行的阶段（如"正在定位问题层级..."、"正在采集证据..."等）。

**node_complete 事件**在每个节点执行完成时发出，包含节点输出的关键数据（如层级判定结果、证据列表概要等）和节点耗时。

**final 事件**包含完整的诊断报告和性能统计。

**run_end 事件**在工作流结束时发出，包含总耗时。

与传统模式的事件流相比，工作流模式的事件流更加结构化，反映了诊断过程的阶段性特征。前端应用可以根据节点事件构建进度指示器，展示当前处于诊断流程的哪个阶段。

## 六、联邦查询流程

### 6.1 并发聚合模式（v1）

并发聚合模式通过 `/federation/ask` 端点触发，适用于需要同时查询所有子集群的场景。

请求到达后，系统获取 FederationCoordinator 单例实例。FederationCoordinator 在初始化时从配置文件中加载子集群注册表，每个子集群配置包含名称、查询端点 URL、描述和启用状态。

查询执行时，FederationCoordinator 使用 `asyncio.gather` 同时向所有启用的子集群发送查询请求。每个子集群的查询通过 SubAgentClient 执行：创建 httpx 异步客户端，向子集群的 `/ask` 端点发送 POST 请求，等待完整响应。子集群运行独立的诊断流程（传统模式或工作流模式），返回诊断结果。

所有子集群响应收集完毕后（或超时后），FederationAggregator 对结果进行汇总。汇总过程包括：收集所有成功响应的诊断报告、记录失败的子集群和错误信息、将所有报告和失败信息提交给 LLM 进行综合分析。LLM 使用 `FEDERATION_SYNTHESIS_PROMPT` 提示词生成跨集群的汇总报告，识别共同问题模式、集群间差异和需要关注的异常。

同时，FederationAggregator 会将每个子集群的完整报告保存到本地 `reports/` 目录，便于后续查阅。保存的报告文件以时间戳和集群名称命名，通过 `/reports` 和 `/reports/{filename}` 端点可以检索历史报告。

### 6.2 Agent-to-Agent 智能路由模式（v2）

智能路由模式通过 `/federation/ask/v2` 端点触发，采用更加智能的方式处理多集群查询。

FederationAgent 是一个具有工具调用能力的 LLM Agent。它使用 `FEDERATION_AGENT_PROMPT` 提示词，该提示词定义了多集群查询的决策逻辑：如何分析用户意图、如何选择目标集群、如何处理模糊查询、如何合并多集群结果等。

FederationAgent 的工具箱包含两个工具。`list_clusters` 工具返回所有已注册且启用的子集群信息，包括集群名称、描述和状态。`query_cluster` 工具向指定集群发送查询请求并返回诊断结果。

查询执行过程是一个多步骤的迭代循环。LLM 首先分析用户问题，判断需要查询哪些集群。如果用户明确指定了目标集群（如"查看 cluster-24 的 CPU 使用率"），LLM 会直接调用 `query_cluster` 查询该集群。如果用户提出了全局性问题（如"哪个集群的 Pod 异常最多"），LLM 会先调用 `list_clusters` 获取集群列表，然后逐个或批量调用 `query_cluster` 查询相关集群。

为了优化性能，当 LLM 在同一轮迭代中生成多个 `query_cluster` 调用时，系统会使用 `asyncio.gather` 并发执行这些调用。所有子集群查询共享同一个 httpx 连接池，避免了连接创建的开销。

子集群的响应通常是一份完整的诊断报告，可能包含大量详细信息。系统会提取报告中的核心结论部分（如问题摘要、根因判定、修复建议等）返回给 LLM，避免过长的原始报告占用上下文窗口。完整的子集群报告会保存到 `reports/` 目录供后续查阅。

当 LLM 收集到足够的子集群信息后，它会生成最终的汇总报告。与 v1 模式不同，v2 模式的最终报告生成采用流式输出，用户可以实时看到报告内容逐字出现。这种设计改善了长时间查询场景下的用户体验。

### 6.3 两种模式的对比与选择

并发聚合模式（v1）的优势在于实现简单、行为确定。它总是查询所有集群，结果完整度高，适合需要全面了解所有集群状态的场景，如日常巡检、全局状态概览等。但其缺点是无法根据问题内容智能选择目标集群，当集群数量较多时可能产生不必要的查询开销。

智能路由模式（v2）的优势在于灵活高效。LLM 能够理解用户意图，仅查询相关集群，减少不必要的网络请求。它支持渐进式查询（先查一个集群，根据结果决定是否查询更多），适合针对性的问题诊断和跨集群对比分析。但其缺点是 LLM 的路由决策可能不总是准确，需要额外的工具调用开销。

在实际使用中，建议根据场景选择合适的模式：全局巡检使用 v1 模式确保覆盖所有集群，针对性诊断使用 v2 模式提高效率。

## 七、Runbook 知识库集成流程

### 7.1 Runbook 的角色与价值

Runbook 知识库在诊断流程中扮演着运维经验沉淀和知识共享的角色。每个 Runbook 是一份针对特定故障场景的标准操作手册，包含场景识别条件、关键证据清单、标准诊断流程、判定规则和阈值、修复方案及注意事项、预防措施等内容。

Runbook 的价值在于将团队的运维经验从个人知识转化为组织知识，并通过 AI 系统进行规模化应用。当新工程师面对一个不熟悉的故障场景时，系统可以自动检索相关 Runbook，按照标准化的流程进行诊断，确保诊断质量不因人员经验差异而波动。

### 7.2 Runbook 检索与使用流程

在诊断过程中，LLM 可以通过 `fetch_runbook` 工具检索相关的 Runbook。检索过程基于语义匹配：LLM 根据当前问题描述和已收集的信息，生成检索关键词，系统在 Runbook 目录中查找描述最匹配的条目，返回对应的 Runbook 内容。

LLM 获取 Runbook 后，会参考其中的诊断流程和判定标准进行分析。Runbook 中定义的证据清单指导 LLM 采集关键信息，判定规则帮助 LLM 进行准确的问题判定，修复方案则直接纳入最终报告的建议中。

需要强调的是，Runbook 是 LLM 推理的参考资料，而非强制执行的脚本。LLM 会根据实际情况灵活应用 Runbook 中的知识：可能完全遵循 Runbook 的诊断流程，也可能只采用其中的部分建议，或者在 Runbook 不适用的情况下依靠自身推理能力。这种灵活性使得 Runbook 系统既提供了标准化指导，又不限制系统处理新问题的能力。

### 7.3 Runbook 与规则引擎的关系

Runbook 知识库和规则引擎是两个互补的知识管理机制。规则引擎面向机器，使用结构化的条件和逻辑进行确定性判定；Runbook 面向 LLM，使用自然语言描述诊断流程和修复方案。

在实际诊断中，两者协同工作。规则引擎快速识别已知场景并给出高置信度判定，Runbook 提供该场景的详细诊断流程和修复指南。当规则引擎的置信度不足时，LLM 可以参考 Runbook 中的诊断步骤进行深入排查。当 Runbook 中提到的某些判定条件可以用规则自动化时，规则引擎承担自动化判定的角色，减少 LLM 的推理负担。

这种分工使得系统在效率（规则引擎的快速判定）和深度（Runbook 的详细知识）之间取得了良好的平衡。

## 八、输出与报告生成流程

### 8.1 输出格式体系

系统支持多种输出格式，适应不同的消费场景。

**文本流格式**面向终端用户和命令行工具。使用 emoji 图标、分隔线和缩进来组织信息层次，使得诊断过程和结果在终端中一目了然。工具调用过程实时展示，最终答案以醒目的框线突出显示。

**SSE 事件流格式**面向前端应用和 API 集成。每个阶段的信息封装为标准的 Server-Sent Event，包含事件类型标识和 JSON 数据负载。前端应用可以根据事件类型进行差异化渲染：`tool_start` 事件显示工具调用进度条，`ai_message` 事件显示 AI 推理过程，`final` 事件渲染完整的诊断报告。

**同步响应格式**面向简单集成场景。等待完整结果后一次性返回纯文本响应，适合脚本调用和自动化流程。

### 8.2 Markdown 诊断报告结构

完整的诊断报告采用多层次的 Markdown 结构，每个部分都有明确的信息传达目标。

**问题概览**以紧凑的表格形式展示关键指标，使读者在几秒钟内了解问题的严重程度和诊断状态。表格包含层级、场景、置信度（含评分和等级）、证据完整度、是否有关键证据缺失等字段。

**深度分析**从多个技术维度对问题进行评估，以分析维度表格的形式呈现。每个维度（基础设施、集群、工作负载、服务、应用）都有相应的分析结论，帮助读者理解问题的影响范围。

**证据详情**是报告中最重要的支撑部分。已采集证据以表格形式列出，包含证据名称、级别标记、具体值和来源。缺失证据同样列出，标注其重要性级别和影响。这种透明的证据展示增强了报告的可信度。

**因果链可视化**使用 ASCII 艺术绘制因果关系图，展示从触发条件到最终影响的逻辑链条。例如，"容器内存超限 → OOMKiller 触发 → 容器被终止 → Pod CrashLoopBackOff"。这种可视化帮助读者快速理解问题的根本原因和传导路径。

**修复方案与验证步骤**提供分步骤的操作指令，每个步骤都有清晰的说明和可执行的命令。验证步骤帮助用户确认修复是否成功。这种实操导向的输出减少了从诊断到修复的转化时间。

**数据来源**按工具分组列出所有被调用的数据采集操作，增强报告的可追溯性。读者可以了解每条结论背后的数据基础。

**置信度说明**解释置信度分数的计算过程，包括基础分、扣减项和最终等级，使读者理解系统对自身判定的确定程度。

### 8.3 性能统计

诊断报告末尾附加性能统计信息，包括平均修复时间（MTTR）估算、各阶段耗时分解、工具调用次数和详情、Token 消耗统计、证据完整率和根因置信度等指标。

这些统计信息具有多重价值：帮助用户评估诊断过程的效率，为系统优化提供数据支撑，为 SLA 报告提供参考指标。在多次诊断的历史对比中，性能统计数据可以揭示系统性能的变化趋势。

## 九、流程优势分析

### 9.1 分阶段处理的优势

将诊断流程分解为问题定位、证据采集、根因分析和汇总报告四个阶段，带来了多方面的优势。

在可控性方面，每个阶段有明确的输入和输出规范，异常可以在阶段边界被检测和处理。如果某个阶段失败，系统可以记录错误并在后续阶段进行补偿处理，而不是整个诊断过程失败。

在可观测性方面，每个阶段产生独立的事件和输出，便于监控和调试。运维人员可以清楚地看到诊断进行到了哪个阶段、该阶段产生了什么结果、是否存在异常。

在可优化性方面，各阶段可以独立进行性能优化和提示词调优。例如，可以针对证据采集阶段引入并行工具调用来减少延迟，可以针对根因分析阶段优化规则引擎的匹配算法，而不影响其他阶段。

### 9.2 混合推理的优势

确定性规则引擎与 LLM 推理的混合使用，在准确性、可解释性和灵活性之间取得了良好的平衡。

规则引擎对已知场景的判定准确率超过 95%，且每个判定都有完整的证据链支撑。这种确定性判定为诊断报告提供了坚实的基础，避免了 LLM 可能产生的幻觉问题。

LLM 则弥补了规则引擎覆盖范围有限的不足。对于规则库未涵盖的新场景，LLM 可以利用其广泛的知识进行推理分析。同时，LLM 能够将结构化的判定结果转化为自然语言描述，生成易于理解的诊断报告。

### 9.3 流式输出的优势

流式输出是改善用户体验的关键设计。在传统的同步模式下，用户需要等待整个诊断过程完成（通常 10-30 秒）才能看到结果，期间没有任何反馈。流式输出改变了这种体验：用户在请求发出后的数百毫秒内就能看到第一条输出，然后实时跟踪工具调用、AI 推理和结论生成的全过程。

这种透明性不仅改善了等待体验，还增强了用户对系统的信任。用户可以看到系统正在调用哪些工具、获取了什么数据、AI 如何推理，从而理解最终结论的依据。

### 9.4 联邦查询的优势

联邦查询使系统具备了跨集群的统一视角。在多集群环境中，问题往往不是孤立的：一个集群的基础设施故障可能影响其上运行的多个应用，一个全局性的配置变更可能同时影响多个集群。

通过联邦查询，运维人员可以用一条命令同时诊断多个集群，对比各集群的状态差异，发现跨集群的共同问题模式。智能路由模式进一步提高了效率，LLM 能够理解查询意图并选择相关集群，避免不必要的网络开销。

### 9.5 配置化知识管理的优势

将运维知识（Runbook）和诊断规则外置到配置文件中管理，使系统具备了持续演进的能力。

新增故障场景的成本极低：定义证据规格和规则对象，编写 Runbook 文档，更新 ConfigMap 即可。整个过程不涉及代码修改、镜像构建和服务重启，大幅降低了知识沉淀的门槛。

知识的版本化管理也变得简单。通过 Git 管理 Runbook 和规则文件，可以追踪每次变更的内容和原因，支持回滚和分支管理。多个团队可以并行贡献知识，通过 Pull Request 进行审核后合入主分支。

配置化设计还便于在不同集群环境中复用和定制诊断能力。共享的基础规则库适用于所有集群，特定集群的专有知识通过自定义 Runbook 叠加。这种分层复用机制避免了重复建设，同时保留了定制化的灵活性。
