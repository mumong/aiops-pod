# 修复规划与执行审阅边界

## 约定（2026-10-12）

- 修复节点负责生成方案；目标、变更及参数有依据时，输出具体命令、风险和恢复条件。
- 外部清理状态、业务影响等未知事项必须披露，不得伪称安全；待批准本身不应阻止生成可审阅方案。
- 构造命令必需的镜像、Secret 值、业务配置等未知时仍需补查或询问，不以占位符补齐动作。
- Runbook 说明操作依据，不定义执行权限；历史手册中的资源白名单不是当前策略。
- 实际命令由执行器按 review/auto 配置处理。生产当前保持 review；规划及反馈不等于批准。
- 继续复用原有方案卡片、按组反馈、版本失效及命令审阅接口，不增加故障专用分支。

## 当前配置

`workflow.remediation.denied_executables: [rm]`

`workflow.remediation.allowed_exec_commands: []`

空的容器命令白名单表示不启用额外命令名限制；显式黑名单优先。管理员仍可重新配置两项。
保留 kubectl 入口、当前集群身份、请求归属、目标范围及审批校验。
复杂 shell、动态展开和宿主机 shell 不属于现有执行协议支持范围。

这不是任意代码防绕过沙箱：检查支持语法中的显式命令名，不能保证脚本、解释器、镜像入口或其他程序不会间接删除数据。
只禁 rm 也不意味着禁止所有删除操作。此为本次明确选择的最小策略，不应宣传为完整安全保障。

## 验证

- remediation、修复节点及 runtime policy 单元测试：182 项通过。
- rm 直接调用、绝对路径、常见包装、简单 shell 内调用，在预演/执行/验证阶段均拦截；review/auto 均覆盖。
- patch、apply、非黑名单容器命令不被旧白名单拒绝；人工批准前 runner 不调用，拒绝后不执行。
- 真实模型用诊断副本规划和定向反馈，不批准真实资源变更；原用户诊断及方案不覆盖。
- 验证命令须与恢复条件的退出语义一致；不把预期对象消失导致的裸 get 非零状态当作恢复失败。

历史空方案不会在升级后自动重写。用户需要通过该方案的修改入口重新生成，审批仍针对新版本。
