### 根因结论
**结论**：根据现有证据，**集群核心问题是 Elasticsearch 服务不可用，导致依赖它的 Kibana 无法启动**。然而，由于**关键证据严重缺失**（Elasticsearch 日志、存储状态），无法确定导致 Elasticsearch 不可用的根本原因。初始怀疑的“NFS存储容量不足”已被证据 #7 和 #8 反驳。

**置信度**：低 (30%)
- ✅ **确认现象**：Kibana 连接 Elasticsearch 超时（证据 #3）。
- ❌ **反驳假设**：系统磁盘空间充足，未满（证据 #7, #8）。
- ❌ **缺失关键证据**：Elasticsearch 自身状态、存储卷状态、错误日志均未采集。
- ⚠️ **可能方向**：问题更可能在于 Elasticsearch 应用层（L4）配置、存储卷挂载（L0）或服务发现（L3），而非单纯的磁盘空间问题。

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 诊断 Elasticsearch Pod 状态**
```bash
# 查看 Elasticsearch Pod 详细状态和事件
kubectl describe pod elasticsearch-master-0 -n xnet
# 查看 Elasticsearch Pod 日志
kubectl logs elasticsearch-master-0 -n xnet --previous 2>/dev/null || kubectl logs elasticsearch-master-0 -n xnet
```
*目的*：获取 Pod 启动失败原因、容器退出码、OOM、镜像拉取错误等关键信息。

**2. [关键] 检查 Elasticsearch 存储卷**
```bash
# 查找 Elasticsearch 使用的 PVC
kubectl get pvc -n xnet | grep -i elasticsearch
# 假设 PVC 名为 `elasticsearch-data-elasticsearch-master-0`，查看其详情
kubectl describe pvc elasticsearch-data-elasticsearch-master-0 -n xnet
# 查看对应的 PV
kubectl describe pv <pv-name-from-pvc-status>
```
*目的*：确认 PVC 是否 Bound，容量是否足够，PV 是否正常。

**3. [验证] 检查 Elasticsearch 服务与端点**
```bash
# 检查 Service
kubectl get svc elasticsearch-master-headless -n xnet -o yaml
# 检查 Endpoints
kubectl get endpoints elasticsearch-master-headless -n xnet
# 尝试从集群内网络访问 Elasticsearch API
kubectl run curl-test --image=curlimages/curl:latest -it --rm --restart=Never -- sh -c 'curl -v https://elasticsearch-master-headless.xnet.svc.cluster.local:9200/_cluster/health'
```
*目的*：验证服务发现和网络连通性。

### 后续优化
1.  **完善监控**：对 Elasticsearch 集群健康状态、存储卷使用率设置告警。
2.  **资源评估**：检查 Elasticsearch Pod 的资源请求和限制是否合理。
3.  **初始化顺序**：确保 Elasticsearch 完全就绪后，再启动 Kibana（使用 initContainer 或 helm hooks）。
