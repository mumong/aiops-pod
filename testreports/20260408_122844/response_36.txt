## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 定位故障 Pod 并查看详情**
```bash
# 1. 查找所有处于 ImagePullBackOff 状态的 Pod
kubectl get pods --all-namespaces --field-selector=status.phase!=Running

# 2. 针对找到的 Pod，查看详细事件（以 aiops-e2e 命名空间为例）
kubectl describe pod <故障Pod名称> -n <命名空间>
```
*目的*：获取具体的错误信息（如 `Failed to pull image "xxx": rpc error: code = Unknown desc = ...`），这是诊断的关键。

**2. [关键] 根据错误信息采取对应措施**
- **如果是认证错误（401/403）**：检查并创建正确的 `imagePullSecrets`。
    ```bash
    # 在 Pod 所在命名空间创建 docker-registry secret
    kubectl create secret docker-registry <secret-name> \
      --docker-server=<registry-server> \
      --docker-username=<username> \
      --docker-password=<password> \
      -n <namespace>
    ```
- **如果是网络超时**：从节点测试到镜像仓库的网络连通性。
    ```bash
    # 登录到节点执行（需要节点访问权限）
    ping <镜像仓库地址>
    curl -v https://<镜像仓库地址>/v2/
    ```
- **如果是镜像不存在（404）**：确认镜像名称、标签及仓库路径是否正确。

### 后续优化
1.  **配置网络策略**：如果使用 Calico 等网络插件，检查是否有 NetworkPolicy 阻断了到镜像仓库的流量。
2.  **检查仓库可用性**：确认私有镜像仓库服务是否健康，是否有限流策略。
3.  **节点磁盘空间**：检查节点磁盘是否已满，可能导致镜像拉取后解压失败。
    ```bash
    kubectl describe node <节点名> | grep -A 10 -B 10 “DiskPressure”
    ```
