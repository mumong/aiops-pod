### 根因结论
**结论**：根据证据 #1、#3、#4，问题的根本原因是**配置冲突**。
1.  **节点侧**：`node2` 被标记了 `test-unschedulable=true:NoSchedule` 污点（证据 #3），此污点会阻止新的 Pod 调度上来。
2.  **工作负载侧**：Pod `l1-test-nginx-6c69dc7c76-sxwsp` 通过 `nodeSelector` 强制要求调度到 `node2`（证据 #4）。
3.  **冲突结果**：调度器无法找到同时满足这两个条件的节点，因此报告 `0/3 nodes are available`（证据 #1），导致 Pod 永远处于 `Pending` 状态。

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 方案A：为 Pod 添加对应的污点容忍 (Toleration)**
如果业务确实需要运行在 `node2` 上，且该污点是计划内的（如节点维护），则为 Pod 添加容忍。
```bash
# 编辑 Pod 所属的 Deployment 或直接编辑 Pod
kubectl patch deployment -n aiops-e2e l1-test-nginx -p '{"spec":{"template":{"spec":{"tolerations":[{"key":"test-unschedulable","operator":"Equal","value":"true","effect":"NoSchedule"}]}}}}'
```
*依据*：使 Pod 能够容忍 `node2` 的污点，从而被调度。

**2. [优先] 方案B：移除节点 `node2` 的污点**
如果 `node2` 不应被标记为不可调度，则移除污点。
```bash
kubectl taint nodes node2 test-unschedulable=true:NoSchedule-
```
*依据*：恢复 `node2` 的正常调度能力。

**3. [可选] 方案C：修改 Pod 的节点选择器**
如果 Pod 不一定非要运行在 `node2` 上，则修改其节点选择器，允许调度到其他节点（如 `node1`）。
```bash
# 编辑 Deployment，将 nodeSelector 修改为其他节点标签或直接删除
kubectl patch deployment -n aiops-e2e l1-test-nginx -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/hostname":"node1"}}}}}'
```
*依据*：让 Pod 的调度需求与节点能力匹配。
