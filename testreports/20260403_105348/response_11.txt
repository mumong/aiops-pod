## 🎯 根因分析
### 因果链
```
┌─────────────────────────────────────────────────────────────────┐
│ 根本原因                                                        │
│ 容器内存限制（memory limit）设置过低（如 50Mi 或 200Mi）         │
│ 无法满足 memhog 应用实际内存需求（内存压力测试应用）             │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 传导机制                                                        │
│ 容器内存使用超过 limit → Kubelet 触发 cgroup OOM Killer          │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 直接原因                                                        │
│ 容器被强制终止，退出码 137（Linux OOM Killer 标准信号）          │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 用户可见现象                                                    │
│ Pod 状态为 CrashLoopBackOff，重启 9 次，无前次日志               │
└─────────────────────────────────────────────────────────────────┘
```

### 根因结论
**结论**：根据证据 #1（CrashLoopBackOff + 9 次重启）、证据 #2（Exit Code 137）和证据 #3（集群中大量容器 memory limit ≤200Mi），  
问题的根本原因是**`memhog` Pod 的内存限制（极可能为 50Mi 或 200Mi）远低于其实际运行所需内存**，导致容器被内核 OOM Killer 强制终止并持续重启。

**置信度**：高 (95%)  
- ✅ Exit Code 137 是 OOMKilled 的唯一标准信号（Linux 内核定义）  
- ✅ Pod 名称 `memhog` 明确为内存压力测试应用，预期高内存使用  
- ✅ 集群中多个容器配置极低内存 limit，`memhog` 极可能继承相同低值  
- ⚠️ 缺失 `kubectl describe pod` 输出，但 Exit Code 137 已足够独立确认 OOM  
- ⚠️ 无 Prometheus 内存使用数据，但非必要——OOMKilled 本身已是决定性证据

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 为 memhog Deployment 增加内存限制（推荐 512Mi）**
```bash
kubectl set resources deployment/memhog -n aiops-e2e --limits=memory=512Mi --requests=memory=256Mi
```
*依据*：当前限制极可能为 50Mi~200Mi，`memhog` 为内存测试应用，建议至少翻倍至 512Mi，观察是否稳定运行。

**2. [可选] 查看当前容器日志（确认启动行为）**
```bash
kubectl logs memhog-578d9b5ffd-fj5gs -n aiops-e2e -c memhog --tail=50
```
*目的*：确认是否为内存泄漏或异常分配（如未释放的缓存、大数组等）

**3. [可选] 验证资源更新后 Pod 是否重建**
```bash
kubectl rollout status deployment/memhog -n aiops-e2e
```
等待输出 `deployment "memhog" successfully rolled out`

### 后续优化
1. **统一资源策略**：检查所有 Deployment 的 `resources.limits`，避免使用 `50Mi`、`100Mi` 等极低值，尤其对非轻量级应用
2. **启用资源监控**：部署 `metrics-server` 后使用 `kubectl top pods -n aiops-e2e` 实时查看内存使用
3. **配置 HPA**：基于内存使用率自动扩缩容
   ```bash
