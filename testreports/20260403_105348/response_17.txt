- **证据 #1 + #2 + #5 印证**：`CrashLoopBackOff` + `Exit Code 137` + `Reason: OOMKilled` → **确定为 OOM 导致的容器反复崩溃**

### 因果链
```
┌─────────────────────────────────────────────────────────────────┐
│ 根本原因                                                        │

                              ↓

                              ↓

```

### 根因结论
**结论**：根据证据 #2（Exit Code 137）、证据 #5（Reason: OOMKilled）和证据 #3（多个容器 memory limit 为 40Mi~200Mi），  
问题的根本原因是**多个容器的内存限制配置过低，远低于应用实际运行需求**，导致容器被 Linux OOM Killer 强制终止，进而触发 Kubernetes 无限重启循环。

**置信度**：高 (95%)  
- ✅ Exit Code 137 是 OOM 的唯一标准信号（Linux 内核定义）  
- ✅ `kubectl describe` 明确记录 `Reason: OOMKilled`  
- ✅ 内存 limit 配置数据中多个值为 40Mi、50Mi、200Mi，明显不合理  
- ⚠️ 缺少 Prometheus 数据，无法确认是否为内存泄漏（但配置过低是直接可修复主因）

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 为 memhog Pod 所属 Deployment 增加内存限制（推荐 512Mi）**

*目的*：识别是否存在系统性配置错误，批量修复。

*目的*：确认应用是否在启动阶段即崩溃（如加载大模型、初始化缓存），辅助判断是否需进一步优化。
