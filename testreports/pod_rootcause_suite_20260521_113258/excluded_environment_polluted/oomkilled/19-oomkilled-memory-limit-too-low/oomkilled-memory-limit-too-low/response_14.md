> 我的集群有什么问题

**关键实体**：
| 类型 | 值 |
|------|-----|
| **主要问题 (49个Pod)** | 镜像拉取失败 (`ImagePullBackOff` / `ErrImagePull`) |
| **次要问题 (3个Pod)** | `CrashLoopBackOff` (OOMKilled), `ContainerCreating`, `Failed/StartError` |
| **受影响命名空间** | `default`, `mcp`, `aiops-e2e` |
| **受影响节点** | `node2` (10.2.0.50) - 所有 25 个 `ErrImagePull` Pod |
| **根因** | **集群节点到 `docker.io` 的出站网络连通性故障** |

## 🕵️ 证据链

### 已采集证据

| # | 证据类型 | 来源命令 | 原始数据 | 分析结论 |
|---|----------|----------|----------|----------|
| 1 | Pod 列表 & 状态 | `kubectl_get_by_kind_in_cluster` | `Running=59, abnormal=52. 24 ImagePullBackOff, 25 ErrImagePull` | 集群中有 52 个异常 Pod，其中 49 个因镜像拉取问题处于待定( Pending )状态。 |
| 2 | Pod 列表 & 状态 | `kubernetes_tabular_query` | `Running=60, Pending=50, Failed=2` | 大面积 Pod 待定( Pending )，确认问题规模。 |
| 3 | 镜像拉取错误详情 | `kubectl_describe` (Pod: `registry-check-node2` on `node2`) | `Events: Failed ... dial tcp i/o timeout to multiple registry-1.docker.io IPs (108.160.169.54, 103.200.31.172, ...)` | **核心证据**：明确指向 `node2` 无法连接到 Docker Hub 注册表。 |
| 4 | 镜像拉取错误详情 | `kubectl_describe` (Pod: `dns-resolve-test` on `node2`) | `Events: Failed ... dial tcp i/o timeout to multiple endpoints (168.143.171.189, 103.200.31.172, ...)` | 确认 `node2` 上所有拉取 `busybox` 镜像的尝试均因 TCP 连接超时而失败。 |
| 5 | 镜像拉取错误详情 | `kubectl_describe` (Pod: `node-debugger-node2-cfk7z` on `node2`) | `78 pull attempts over 8h, all failed with i/o timeout on port 443` | 证明网络问题已持续超过 8 小时，且为持续性故障。 |
| 6 | 镜像来源检查 | `kubectl_get_yaml` (Pod: `dns-resolve-test`) | `imagePullSecrets: <none>` | 排除了因镜像拉取凭证( Secret )错误导致拉取失败的根因。 |
| 7 | Pod 启动失败 | `kubectl_describe` (Pod: `rc-oomkilled-memory-limit...` on `node1`) | `Reason: OOMKilled, Exit Code: 137` | 确认 OOM 问题，但仅影响了 1 个 Pod，为独立次要问题。 |
| 8 | Pod 启动失败 | `run_bash_command` (获取该 OOM Pod 的日志) | `unable to retrieve container logs` | 日志无法获取，但 OOM 的事实已通过 Exit Code 确认。 |
| 9 | Pod 启动失败 | `kubectl_describe` (Pod: `node-debugger-node1-nx8gb` on `node1`) | `Message: failed to create containerd task: failed to create shim task: OCI run...` | 确认 `node1` 上存在一个不同的容器启动失败问题。(镜像已拉取，启动失败) |

### 证据关联分析
-   **证据 #1, #2 + #3, #4, #5 印证**：大规模 Pod 待定( Pending )的根本原因是镜像拉取失败，而拉取失败的直接原因是集群节点（尤其是 `node2`）到 Docker Hub 的 **TCP 连接超时**。
-   **证据链**：容器运行时(kubelet) 尝试拉取 `busybox:1.36.1` → DNS 解析成功 → 向 registry-1.docker.io:443 发起 TCP 连接 → 连接建立失败 (dial tcp i/o timeout) → kubelet 报错 `ErrImagePull` → 重试多次后降级为 `ImagePullBackOff` → Pod 处于 `Pending` 状态。
-   **证据 #6** 排除了镜像拉取凭证的常见问题。

### 缺失证据（如有）

| 证据 | 级别 | 影响 |
|------|------|------|
| `node2` 上其他 `ErrImagePull` Pod 的 `kubectl_describe` 详情 | medium | 未采集属于同一异常组的 `node-debugger` Pod 详情，但其兄弟 Pod 的详情已确认，不影响根因。 |
| `node-debugger-node1-nx8gb` 的 `kubectl_describe` 详情 | medium | 未采集该 `StartError` Pod 的完整事件，但其启动错误（OCI runtime failure）已确认与网络问题无关。 |

## 🎯 根因分析

### 因果链
```
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 根本原因                                                                         │
│ 集群节点（node1/node2）到 Docker Hub (registry-1.docker.io) 的出站网络连通性故障 │
│ (防火墙规则/NAT网关/代理等导致TCP 443端口连接超时)                               │
└──────────────────────────────────────────────────────────────────────────────────┘
                                       ↓
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 传导机制                                                                         │
│ kubelet 尝试拉取 busybox:1.36.1 → DNS 解析成功                                  │
│ → 向 registry-1.docker.io:443 发起 HTTPS 请求 → TCP 连接建立持续超时(>8小时)    │
│ → 容器运行时返回 DeadlineExceeded                                                │
└──────────────────────────────────────────────────────────────────────────────────┘
                                       ↓
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 直接原因                                                                         │
│ kubelet无法拉取容器镜像，报告 ErrImagePull                                      │
└──────────────────────────────────────────────────────────────────────────────────┘
                                       ↓
┌──────────────────────────────────────────────────────────────────────────────────┘
                                       ↓
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 用户可见现象                                                                     │
│ 1. 49个Pod处于 ImagePullBackOff/ErrImagePull (Pending)                           │
│    (分布于 default/mcp 命名空间，集中在node2节点)                               │
│ 2. 1个Pod因 OOMKilled 持续重启 (CrashLoopBackOff) - 次要问题                    │
│ 3. 1个Pod容器启动失败 (Failed/StartError) - 次要问题                            │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 根因结论

**结论**：根据证据 #3 (registry-check-node2 的 i/o timeout 事件)、#4 (dns-resolve-test 的超时事件) 和 #5 (node-debugger 8小时的连续失败重试)，
问题的根本原因是**集群节点到 `docker.io` 的 HTTPS 出站网络连通性中断**，导致 49 个使用 `busybox:1.36.1` 镜像的 Pod 无法被拉取而阻塞。

**置信度**：高 (95%)
- ✅ 多个 Pod 的 `kubectl_describe` 事件清晰一致地显示了 `dial tcp i/o timeout` 到多个不同的 registry IP。
- ✅ `kubectl_get_yaml` 排除了镜像拉取凭证的常见根因。
- ✅ `kube-system` 命名空间全部运行正常，排除了集群控制面故障。
- ⚠️ 具体是防火墙规则、NAT 还是代理配置导致的网络隔离，需要进一步在集群外部排查。

## 🛠️ 修复建议

### 立即执行（按优先级排序）

**1. [优先] 排查并修复集群节点到 `docker.io` 的出站网络**

这是解决 49 个异常 Pod 的关键。请集群管理员执行以下操作：

- **检查防火墙规则**：确认节点是否被防火墙阻止访问外部 HTTPS(443) 端口。
- **检查 NAT 网关**：如果节点在私有网络，确认 NAT 网关是否正常工作。
- **检查代理设置**：如果集群使用了 HTTP/HTTPS 代理，请确认 kubelet 和容器运行时的 `HTTP_PROXY`/`HTTPS_PROXY` 配置是否正确。
- **测试连通性**：
  ```bash
  # 在节点 (node2) 上执行，替换为检测到的任何 registry-1.docker.io IP
  curl -v --connect-timeout 10 https://registry-1.docker.io/v2/
  # 或
  wget -q -O- --timeout=10 https://registry-1.docker.io/v2/
  ```
  *目的*：确认节点自身能否访问 Docker Hub。
*依据*：证据 #3, #4, #5 全部指向 TCP 连接超时。

**2. [可选] 切换镜像源 / 使用镜像仓库**

如果无法修复出站网络，考虑为集群配置一个可用的镜像仓库（如 Harbor, Nexus）或将所使用的 `busybox:1.36.1` 镜像搬运到本地可访问的私有仓库，并更新 Pod 的 `image` 字段。

**3. [紧急] 处理 OOMKilled Pod**
*依据*：证据 #7 (Exit Code 137)。
```bash
kubectl set resources deployment <deployment-name> -n <namespace> --limits=memory=512Mi
```
*目的*：增加内存限制，解决 `rc-oomkilled-memory-limit` Pod 的内存不足问题。

**4. [常规] 查看并处理容器启动失败的 Pod**
```bash
kubectl describe pod node-debugger-node1-nx8gb -n mcp
```
*目的*：查看 Pod 启动失败的具体原因（OCI runtime 错误），并检查其基础镜像是否完整。

### 后续优化
1.  **镜像管理**：建立私有镜像仓库，所有业务镜像从私有仓库拉取，避免依赖公网 registry。
2.  **Pod 健康检查**：为所有 Pod 配置合适的 `readinessProbe` 和 `livenessProbe`，让 K8s 能自动处理异常 Pod。
