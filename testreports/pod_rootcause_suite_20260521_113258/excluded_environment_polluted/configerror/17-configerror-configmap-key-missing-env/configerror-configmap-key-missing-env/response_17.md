## 🎯 根因分析
### 因果链
```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│ 根本原因                                                                            │
│ 集群节点（node1, node2）无法访问外部 HTTPS 镜像仓库（docker.io, registry.k8s.io 等） │
│ (TCP连接超时/连接重置)                                                               │
└─────────────────────────────────────────────────────────────────────────────────────┘
                                      ↓
┌─────────────────────────────────────────────────────────────────────────────────────┐
│ 传导机制                                                                            │
│ 节点网络故障 → kubelet 在尝试拉取镜像时连接外部仓库超时 → 反复重试失败 → 触发       │
│ kubelet BackOff 机制。对于 Terminating Pod，网络问题导致容器清理流程卡住。           │
└─────────────────────────────────────────────────────────────────────────────────────┘
                                      ↓
┌─────────────────────────────────────────────────────────────────────────────────────┐
│ 直接原因                                                                            │
│ kubelet 因网络问题无法完成容器镜像拉取 → Pod 进入 ErrImagePull / ImagePullBackOff    │
└─────────────────────────────────────────────────────────────────────────────────────┘
                                      ↓
┌─────────────────────────────────────────────────────────────────────────────────────┐
│ 用户可见现象                                                                        │
│ 约 ~47 个 Pod 处于 ErrImagePull/ImagePullBackOff 状态，约2个 Pod 在 Terminating 卡住 │
│ 所有 Pod 状态为 Pending                                                             │
└─────────────────────────────────────────────────────────────────────────────────────┘
```
### 根因结论
**结论**：根据证据 #2 (`i/o timeout`)、#3 (`DeaflineExceeded`)、#4、#5、#10、#11，集群存在**大规模、跨节点、跨命名空间的镜像拉取失败**。问题的根本原因是**集群节点无法通过 TCP 连接到外部镜像仓库（docker.io, registry.k8s.io）**，导致所有依赖外部镜像的约47个 Pod 无法启动。

**次要结论**：`aiops-e2e/rc-config-configmap-key-missing` 是独立的**配置错误**。其 ConfigMap `rc-app-config` 中缺少必需的`APP_BOOT_MODE` 键。

**置信度**：高 (95%)
- ✅ 跨节点、跨命名空间的多个 Pod 出现一致的 `i/o timeout` 错误
- ✅ `finalizers` 证据排除 Terminating Pod 的常见根因
- ⚠️ 缺少节点级网络配置，无法定位具体网络层故障点

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 排查并修复集群对外网络连接**
这是核心问题，必须先解决。请检查节点上的网络连通性：
```bash
# 在 node1 和 node2 上执行
curl -v --connect-timeout 5 https://registry-1.docker.io/v2/
curl -v --connect-timeout 5 https://registry.k8s.io/v2/
nslookup registry-1.docker.io
```
*依据*：证据 #2, #3 显示连接到 docker.io 和 registry.k8s.io 超时。

**2. [依赖问题1] 排查集群网络出口配置**
在确认网络不可达后，需要检查：
- **是否配置了**：HTTP/HTTPS 代理
- **是否配置了**：防火墙规则/安全组
- **CNI 组件是否异常**（检查 kube-system 下的网络组件状态）

**3. [独立问题] 修复 aiops-e2e 配置错误**
向 `aiops-e2e/rc-app-config` ConfigMap 中补充 `APP_BOOT_MODE` 键：
```bash
kubectl patch configmap rc-app-config -n aiops-e2e --type merge -p '{"data":{"APP_BOOT_MODE":"production"}}'
```
*依据*：证据 #6, #7 表明 ConfigMap 缺少该键，该命令将添加一个默认值。

**4. [待验证] 清理卡住的 Terminating Pod**
在网络问题修复后，这些 Pod 可能会自动清理。如果仍然卡住，可以强制删除：
```bash
kubectl delete pod curl-test -n kube-system --force --grace-period=0
kubectl delete pod curl-test-registry -n default --force --grace-period=0
```
*依据*：证据 #8, #9 显示 `finalizers` 为空，可以安全强制删除。

### 后续优化
1. **配置镜像仓库代理/缓存**：在集群内搭建 Harbor 或 Pull Through Proxy，避免直接访问外部仓库，提高拉取速度和可用性。
2. **监控告警**：配置对 `ErrImagePull` / `ImagePullBackOff` 状态的监控和告警。
3. **应用侧优化**：确保 ConfigMap 和所需 Secret 的所有 key 都被正确定义。
