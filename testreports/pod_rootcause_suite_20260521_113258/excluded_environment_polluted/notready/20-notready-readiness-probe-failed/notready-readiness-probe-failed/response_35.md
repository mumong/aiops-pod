## 🛠️ 修复建议

### 立即执行（按优先级排序）

**1. [最高优先] 排查并修复集群对 `docker.io` 的出站网络连接**

这是解决问题的核心。需要集群管理员检查网关/防火墙/代理/NAT策略。
- **检查防火墙/安全组**：确认是否允许节点向 `104.244.46.208`, `54.152.223.174`, `100.28.191.205` 等IP地址的 `TCP 443` 端口出站。
- **检查代理配置**：如果集群使用了HTTP/HTTPS代理，确认代理配置是否生效且能正确代理到 `docker.io`。检查 kubelet 或 containerd 的代理配置。
- **检查DNS解析**：确保节点能正确解析 `registry-1.docker.io` 的域名。

**2. [优先] 验证修复效果**

修改网络策略后，在集群任意节点或通过DaemonSet Pod执行以下命令验证：
```bash
# 直接在节点上执行（需要节点权限）
curl -o /dev/null -s -w "%{http_code}" https://registry-1.docker.io/v2/

# 或者在一个可调度的Pod内执行（推荐，安全）
kubectl run test-network --image=busybox:1.28 -it --rm --restart=Never -- wget -O- -q https://registry-1.docker.io/v2/
```
*预期结果*：返回 `200 OK` 或执行成功，无超时。

**3. [紧急恢复] 手动删除并重建因网络问题卡住的Pod**

一旦网络恢复，您可以删除这些Pod，由控制器（如Deployment, DaemonSet）自动重建。
```bash
# 查看所有处于 ImagePullBackOff 或 ErrImagePull 的 Pod
kubectl get pods -A | grep -E "ImagePullBackOff|ErrImagePull"

# 批量删除（请根据实际情况过滤命名空间和Pod名）
kubectl delete pod --all -n default
kubectl delete pod --all -n mcp
# ... 其他受影响的命名空间
```

### 后续优化
1. **配置镜像仓库代理/镜像仓库Mirror**：在集群中部署Harbor等私有镜像仓库作为代理或Mirror，将 `docker.io` 的常用镜像缓存到本地。修改 kubelet 或 containerd 配置，优先使用本地镜像仓库。这可以彻底解决对外部仓库的网络依赖和单点故障。
2. **使用稳定性更高的基础镜像**：如果可能，将应用的基础镜像从公共仓库迁移到更稳定或内部托管的镜像源。
3. **监控告警**：对大规模 `ImagePullBackOff` 事件设置告警，以便在类似的网络问题发生时能迅速响应。
