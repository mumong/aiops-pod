**置信度**：高 (95%)
- ✅ 跨节点、跨命名空间、跨镜像仓库的验证
- ✅ 网络层错误 (`i/o timeout`, `connection reset`) 而不是认证或镜像不存在错误
- ✅ `kubectl describe` 和 `Events` 原始数据直接证明确实存在这些错误
- ⚠️ 缺少节点网络配置、防火墙规则和 DNS 配置等关键环境证据，无法定位具体的阻断原因

### 次要问题说明
1.  **Terminating 卡住 (default/curl-test-evict, default/dns-test-dig-verify)**：工具输出明确显示 `finalizers: <none>`，排除该可能。宽限期 (`terminationGracePeriodSeconds: 30`) 已过，可能因Kubelet忙于失败的重试或底层运行时卡住。**此问题被镜像拉取失败的“噪音”掩盖。**

## 🛠️ 修复建议

### [核心] 修复网络问题

**根本方法：检查和修复集群节点的出口网络连接。**

**步骤1：验证节点到外网的连通性**
请在 `node1` 和 `node2` 上分别执行以下命令，这可以直接确认问题所在。

```bash
# 在节点 node1 上执行
ping -c 3 registry-1.docker.io
curl -I https://registry-1.docker.io/v2/
nslookup registry-1.docker.io

# 在节点 node2 上执行
ping -c 3 registry-1.docker.io
curl -I https://registry-1.docker.io/v2/
nslookup registry-1.docker.io
```

*依据*：证据 #3, #4, #5 显示所有连接都失败，需要从节点上的网络层、HTTP层（curl）和DNS层（nslookup）逐层排查。

**步骤2：根据步骤1的结果检查并修复**
- **如果Ping和Curl都失败**：检查节点防火墙（`iptables -L -n -t filter`）、NAT规则（`iptables -L -n -t nat`）以及云平台防火墙/安全组规则，确保 443 端口允许出站。
- **如果Ping失败但Curl成功**：可能是镜像仓库域名解析到多个IP，部分IP被防火墙拦截。可以考虑在DNS或hosts文件中强制使用能访问的IP。
- **如果DNS失败**：检查 `/etc/resolv.conf` 配置和集群内DNS（CoreDNS/kube-dns）的转发策略。

**步骤3：清退并重建所有失败的Pod**
在修复网络问题后，删除所有处于 `Pending` 状态的Pod，让Kubelet重新拉取镜像。

```bash
# 批量删除所有处于 ErrImagePull 和 ImagePullBackOff 状态的 Pod
kubectl delete pods --all-namespaces --field-selector=status.phase=Pending
```

*依据*：网络恢复后，旧的重试状态可能仍停留在BackOff状态，删除后自动重建可以立即重新尝试。

### [次要] 处理其他问题

**1. 处理 Terminating 卡住的 Pod**

```bash
kubectl delete pod dns-test-dig-verify -n default --force --grace-period=0
```
*依据*：工具输出确认 `finalizers: <none>`，在强制删除后不应残留。

重点关注 `Readiness Probe` 的配置，如 `httpGet` 的 `path` 和 `port` 是否正确，以及应用的readiness接口（如 `/healthz`）是否正常返回。
