## 4. 待审阅问题（均未修复）

### F1 — 高：全量结果反复回灌，压缩后仍循环

证据：`310de1265d3240fe`，`runs/.../compactions/`、`node_outputs/evidence.output.json`、`deep.log`。

1. Agent 未选新筛选/字段参数，而是取 67 个 Pod 的完整生命周期响应。
2. 定位阶段压缩一次；证据节点又以相同参数取全量结果。
3. 证据节点共请求同参数 4 次：首次真实执行，后 3 次 `deduplicated=true`，复用首次缓存。
4. 每次缓存回送仍是 **88568 字符**，随后又触发压缩；全流程共观察到 5 次相同参数请求、归档中 5 份已完成的压缩结果（1 次定位、4 次取证）。
5. `evidence-001.after.json` 显示工作消息由 3 条替换为 2 条、估算输入从 58782 降为 12502、近期保留 0 条。说明替换机制生效；大工具对放不进近期预算，所以转入摘要，而后模型再次请求它。
6. 原始 ToolMessage 是合法完整 JSON，`coverage=present`、67 行、无后续页；摘要却写“列表正文曾截断”。这将列表覆盖与“不完整窗口历史”混在一起，是摘要语义错误的直接证据。

因此：缓存只减少了 Kubernetes 执行次数，**没有减少重复向上下文投递大结果，也没有阻止摘要诱发的再查询**。新可选能力的工程计算正确，不代表模型每次会使用它。

建议审阅：通用的采集收据/覆盖元数据独立保留；缓存命中如何引用已有证据而非重复灌入原包；新参数如何被任务驱动选用；缺失“历史”不能靠反复查询同一“当前快照”补齐。**不建议先加步数，也不需要 OOM 特判。**

### F2 — 高：旧表格过滤漏行，旧 describe 摘要又漏掉节点条件

### F7 — 中／新增能力边界：对象字段过滤对模型不够明确

合成数据中存在 `state={running:{...}}`。当前 schema 允许 `where.field=state`、标量 value；传 `state eq "running"` 后返回成功、matched=0、unknown=0。

严格 JSON 比较确实不相等，因此不是计数引擎算错；但此输入并不能表达“当前是 running”，模型容易误用。`state/conditions/resources` 等对象字段与标量字段没有在过滤描述中充分区分。

建议审阅：明确可过滤的标量字段和字段类型，或单独设计通用嵌套字段访问；不静默把不受支持的状态查询包装成有效的业务排除结论。此次自然对话未观察到这个具体误用，是边界探针发现的风险。
