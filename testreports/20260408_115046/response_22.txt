- **证据 #2 + #3 印证**：错误信息显示 DNS 查询发往 `10.96.0.10:53`（CoreDNS 服务 IP），且 CoreDNS Pod 状态正常 → 问题不在 DNS 解析，而在 DNS 查询成功后的 TCP 连接或数据传输阶段。
- **证据链**：应用需拉取外部镜像 → CoreDNS 正常解析 `registry-1.docker.io` → 节点 `node2` 上的 kubelet 尝试与解析出的地址建立连接 → **网络连接超时或被重置** → 镜像拉取失败 → Pod 进入 `ImagePullBackOff` 状态。

### 根因结论
**结论**：根据证据 #2 (Pod事件显示 `i/o timeout` 连接 `registry-1.docker.io`) 和证据 #3 (CoreDNS 运行正常)，问题的根本原因是**集群工作节点（`node2`）无法建立到 Docker Hub 镜像仓库 (`registry-1.docker.io`) 的稳定网络连接**。

**置信度**：高 (85%)
- ✅ 多个 Pod 拉取不同镜像均失败，指向共性问题。
- ✅ 错误信息明确为网络层超时 (`i/o timeout`)。
- ✅ 内部 DNS 服务正常，排除了解析问题。
- ⚠️ 缺少节点级别的直接网络测试证据，无法精确定位是防火墙、路由还是外部网络问题。

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 检查节点网络连通性**
登录到运行故障 Pod 的节点 (`node2`)，执行以下命令测试连通性：
```bash
# 1. 测试DNS解析
nslookup registry-1.docker.io
# 2. 测试到Docker Hub端口的连通性 (HTTPS 443端口)
curl -v --connect-timeout 10 https://registry-1.docker.io/v2/
# 或使用 telnet（如果 curl 不可用）
timeout 5 telnet registry-1.docker.io 443
```
*目的*：确认网络问题是出在节点本身还是集群网络插件。

**2. [关键] 检查并调整网络策略与防火墙**
- **检查 Calico/Flannel 等网络插件日志**：
  ```bash
  kubectl logs -n kube-system -l k8s-app=calico-node --tail=50
  ```
- **检查节点防火墙**（如果使用 `iptables`）：
  ```bash
  sudo iptables -L -n | grep -E “(443|DOCKER)”
  sudo iptables -L -n -t nat | grep -E “(443|DOCKER)”
  ```
- **临时禁用防火墙进行测试（仅限测试环境）**：
  ```bash
  sudo systemctl stop firewalld  # 对于 firewalld
  # 或
  sudo ufw disable               # 对于 ufw
  ```

**3. [可选] 使用可访问的镜像或私有仓库**
如果公网访问短期内无法恢复，可以：
- 将所需镜像推送到集群内可访问的私有镜像仓库。
- 使用 `docker save` 和 `docker load` 手动将镜像导入节点。

### 后续优化
1.  **配置镜像仓库代理或加速器**：在 `kubelet` 或容器运行时（如 Docker）配置国内镜像加速器（如阿里云、腾讯云镜像加速地址）。
2.  **部署私有镜像仓库**：搭建 Harbor 等私有仓库，减少对公网的依赖。
3.  **网络策略审计**：定期审查 `NetworkPolicy`，确保出站到常用镜像仓库的流量不被误拦截。
4.  **节点网络监控**：监控节点的出站网络丢包率和延迟。
