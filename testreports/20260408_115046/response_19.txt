## 🎯 根因分析
### 因果链
```
┌─────────────────────────────────────────────────────────────────┐
│ 根本原因                                                        │
│ 集群节点到外部镜像仓库（Docker Hub）的网络连接被主动中断         │
│ （由 `fault_type=registry_unreachable` 标签指示的故障注入导致）  │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 传导机制                                                        │
│ 1. 故障注入（如TC规则、防火墙规则）生效，中断到特定IP/端口的连接 │
│ 2. Kubelet 尝试从 `registry-1.docker.io` 拉取 nginx:latest 镜像 │
│ 3. TCP 连接在握手或传输过程中被重置 (connection reset by peer)  │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 直接原因                                                        │
│ 拉取镜像 'nginx:latest' 时，与镜像仓库的网络连接被重置           │

└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ 用户可见现象                                                    │
│ Pod `imagepull-fail-victim` 状态为 ImagePullBackOff，无法启动   │
└─────────────────────────────────────────────────────────────────┘
```
### 根因结论
**结论**：根据证据 #1（连接重置错误）和证据 #2（故障注入标签），问题的根本原因是**集群节点到外部 Docker Hub 镜像仓库的网络连接不可达**，这极有可能是一次人为的、针对性的故障注入（`registry_unreachable`）导致。
**置信度**：高 (95%)
- ✅ 证据 #1：Pod 事件明确报告 `connection reset by peer`，是典型的网络连接中断错误。
- ✅ 证据 #2：Pod 标签 `fault_type=registry_unreachable` 直接指明了故障场景。
- ✅ 证据 #3：CoreDNS 正常，排除了内部 DNS 问题。
- ⚠️ 局限性：未进行网络层独立测试（如 `ping`、`telnet`），但现有证据已足够支撑结论。

**2. [验证] 手动测试节点到镜像仓库的网络连通性**

```bash

```
*目的*：独立验证网络连接是否已恢复。
**3. [临时] 使用本地可用镜像或修改 Pod 配置**
如果无法立即恢复网络，可临时使用已存在于节点上的镜像，或改用可访问的私有仓库。

```
