- **证据链**：集群内部 DNS 正常 → 能解析出仓库 IP → 节点尝试建立到该 IP 的 TCP 连接 → 连接被对端或中间网络设备重置 → Kubelet 拉取镜像失败 → Pod 进入 `ImagePullBackOff` 状态。

### 根因结论
**结论**：根据证据 #1 (连接被重置错误) 和证据 #2 (故障类型标签)，问题的根本原因是**集群节点无法建立到外部 Docker Hub 镜像仓库 (`registry-1.docker.io`) 的网络连接**。内部 DNS 服务正常（证据 #3），因此问题定位在 L3 网络层的出站连通性上，可能由节点防火墙、出口网关策略或路由问题导致。

**置信度**：高 (90%)
- ✅ 证据 #1 提供了明确的错误信息 (`connection reset by peer`)。
- ✅ 证据 #2 的 Pod 标签 (`fault_type=registry_unreachable`) 与现象高度吻合。
- ✅ 证据 #3 排除了内部 DNS 故障这一常见原因。
- ⚠️ 缺少从节点直接测试仓库连通性的证据，无法完全排除 Docker Hub 服务端临时问题。

## 🛠️ 修复建议
### 立即执行（按优先级排序）
**1. [优先] 在故障节点上测试网络连通性**
登录到运行该 Pod 的节点 (`node2`)，执行以下命令：
```bash
# 测试到 Docker Hub 的 HTTPS 端口连通性
curl -v https://registry-1.docker.io/v2/ 2>&1 | head -20
# 或使用 telnet 测试 TCP 连接
telnet registry-1.docker.io 443
```
*目的*：确认连接被重置的具体发生点，判断是节点本地问题还是集群出口问题。

**2. [可选] 检查并调整网络策略或防火墙**
检查集群和节点级别的出站规则：
```bash
# 检查集群 NetworkPolicy (如果使用了网络插件如 Calico)
kubectl get networkpolicy -A
# 登录 node2，检查节点防火墙规则 (例如 iptables)
sudo iptables -L -n | grep -i docker.io
sudo iptables -L -n -t nat
```
*依据*：连接重置通常由主动拒绝连接的防火墙或策略导致。

**3. [临时] 使用可访问的镜像或镜像加速器**
如果急需启动 Pod，可以修改 Deployment/Pod 的镜像地址，例如使用国内镜像加速器或已经提前拉取到本地节点的镜像。
```bash
kubectl edit pod/imagepull-fail-victim -n aiops-e2e
# 将 `image:` 字段值改为一个确定可访问的镜像地址
```

### 后续优化
1.  **配置镜像仓库探针**：在集群中部署一个 DaemonSet，定期检测到关键外部镜像仓库的网络连通性，并产生告警。
2.  **使用私有镜像仓库**：搭建内网私有镜像仓库（如 Harbor），避免依赖不稳定的公网服务。
3.  **规范网络出口策略**：明确集群节点的出站访问规则，确保必要的镜像仓库地址（如 `*.docker.io`, `*.gcr.io`）在允许列表中。
