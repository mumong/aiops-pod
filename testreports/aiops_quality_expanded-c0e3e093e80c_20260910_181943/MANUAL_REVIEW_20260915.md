## 评分原则

主因须能区分同一症状下的具体注入机制。同义词、换行、无害措辞不扣分；明确错误的对象、决定性数值、相反机制及实质因果矛盾不通过。非必要的更深层细节未知，不自动否定已经明确的目标机制。

例如：识别启动分配 256Mi 超过 64Mi 并发生 OOM，不要求同一句命中所有关键词；但 CPU 请求 100k 被解释成 100m 并归因其他负载耗尽节点，不能因出现 Insufficient cpu 就通过。

长宽限期内正常等待允许判为正确解释，不强求报告宣布“卡死”。待复议及尚未确认具体根因计 0 分。部分措辞风险保留主因分，详见裁定 JSON 的逐场景说明；该判断不代表报告所有附加陈述都正确。

## 真实问题与原报告例子

### 1. 评分漏判：启动 OOM、环境变量缺失

[c08-startup 第 2 次报告](c08-startup/run-02-d639f68b5daa4608/report.md) 分条写明：限制 64Mi、启动分配 256Mi、超限触发 OOM。核心机制完整，但原规则对同句、顺序的要求导致未命中。本组 20 个原失败项均恢复。

c07-env 的 50 个样本均识别 APP_REQUIRED_CONFIG 缺失导致退出 78；未注入、未定义、未提供、None 等表达不应因词形不同判错。少量“配置文件”“Deployment”泛称仍是措辞风险，并非所有细节均获认可。

c05-plugin 的 39 个有效样本中 38 个识别指定 CNI 插件缺失；第 34 次把单插件缺失扩大成整个目录不存在／不可访问，暂待复议。

### 2. 真实误诊：CPU 数量与调度含义

[c01-cpu 第 21 次报告](c01-cpu/run-21-c77473f1a6a94a5d/report.md) 的证据已显示 CPU Request=100k，但正文将其解释为“100m (100k)、资源门槛极低”，继而确认集群资源全部耗尽，并排除 Pod 请求不合理。

Kubernetes Quantity 中 100k 表示十万 CPU 单位，不是 100m。Insufficient cpu 表明调度请求无法满足，也不能单独证明节点 CPU 实际使用率满载。

本组仅 7 次明确识别请求量级过大。仅复述 Insufficient cpu、未区分不合理请求与其他负载占满节点的，列待复议；这与多根因区分测试的目的有关，不是仅测试能否识别 Pending 症状。

### 3. 真实误诊：137 不等于 OOM，业务成功不等于探针成功

[c10 第 2 次报告](c10/run-02-6bbf477bda514085/report.md) 已列出：
- Container app failed liveness probe；
- HTTP probe failed with statuscode: 500；
- last terminated reason: Error、exit 137。

但结论仍确认内存限制过小导致 OOM，并拿 /work 的 200 响应排除健康检查接口自身失败。这是报告内部的推理错误，不是缺少工具证据即可解释的。

137 通常对应 SIGKILL，但不能独立证明 OOM；/work 和 /health 是不同端点，前者 200 不排除后者 500 或超时。

c10-timeout 原通过项中也有多份实际确认 OOM。本组正确机制应是健康接口约 3 秒响应超过约 1 秒探针超时，触发重启；人工分从 54% 降到 30%。

### 4. Terminating：需要区分机制及是否已经超期

c11-prestop 的配置是 preStop 等待（有 3600 秒 deadline）、总宽限期 3900 秒。c11-grace 则是主进程收到 SIGTERM 后继续等待退出条件，宽限期同为 3900 秒。

因此：
- 两者不能互相替代，也不能用 finalizer 解释没有 finalizer 的场景；
- 尚在宽限期内等待，不等于 kubelet 删除机制失效；
- preStop 或不退出的应用不能据此被描述为阻止最终 SIGKILL、导致永久无法删除。

人工审阅接受正确解释正常等待的报告，因此 c11-grace 从 14% 上调到 64%；同时剔除 c11-prestop 中混淆信号处理或声称超期无法强杀的结论，使其从 56% 下调到 38%。

另外，deletionTimestamp 在优雅删除中可表示预期删除期限，不宜机械当作删除请求起点。当前 Runbook 的“距今未超过宽限期”判断表述存在歧义，值得后续核验；当前文件不等于已经证明当时每次注入的是相同文本。本轮未修改。
