不能一概说“脚本无法创建异常环境”，也不能当成 Agent 诊断失败。

|---|---|---|
| c02-tag | 拉取时先报 x509 unknown authority；runs=[] | 环境的仓库证书信任不满足，未形成预期 tag-not-found 故障。脚本拦截合理，需环境准备后补测 |

## 5. 最值得关注的真实问题

### 工具事实已存在，报告却改错：c09 流向颠倒

[c09 第35次报告](c09/run-35-9cf064a78c6c4a65/report.md) 把流量写为 Pod .16 → 后端 .62，并确认后端故障。

但 [归档](c09/run-35-9cf064a78c6c4a65/evidence.archive.json) 中 fact-03d581eb3ec0 的值为：

```text
src_ip: 172.16.104.62
dst_ip: 172.16.104.16
GET /work
response_code: 503
```

实际方向是客户端到目标 Pod。报告反转了方向后构造“调用下游失败”的因果解释。这一例可确认错误发生在事实进入报告的解释／重写链路，不能说 MCP 没有提供方向；具体在哪个节点引入，仍需执行轨迹定位。

### 其他核心错误

- **c01-cpu**：100k 被当成100m或极小请求，继而错误排除 Pod 请求过大；人工仅14%。
- **c10、c10-timeout**：把137独立当作OOM证明、把/work成功等同于/health健康；人工28%、30%。
- **c09**：除流向错误外，多份把业务/work明确当成实际Readiness端点；人工64%，低于局部复核96%。
- **c11-prestop、c11-grace**：混淆preStop与主进程等待、把宽限期内等待说成超期不可强杀；人工38%、64%。
- **c11**：区分正确finalizer阻塞对象删除与“137自动触发Pod删除”“finalizer触发OOM”等错误链；人工66%。
- **c07-env、c08-startup**：核心环境变量缺失、启动分配超限均可正确识别；原低分主要有同义词和分句匹配问题，人工均100%。

## 6. 四项指标的“计算正确”与“衡量价值”不是一回事

全量核验的具体范围：

1. **Runbook**：1338 份报告的参考条目 ID 与原存储 found 集合一致，依据原 expected/found 重算 coverage 一致。没有发现这一批因 ID 提取导致的覆盖分差异。它只衡量命中预设条目，不验证条目内容是否有用、是否被执行，也不惩罚多引用无关条目。
2. **证据完整度**：1338 份 evidence.archive.json 的 plan_total、plan_collected 重算与原值一致。这个指标反映“模型计划了什么、完成了多少”，不能代替“是否采到足以区分根因的关键事实”。计划不完整或证据被错误解释时，该分仍可能很高。
3. **耗时**：原 elapsed_seconds 均为有限正数，Case及总体均值重算一致；没有独立测量网络和服务端各阶段真实墙钟，也不称为故障修复时间。
4. **根因**：采用逐条语义判断，所以会纠正漏判和误放行。它仍受报告表达与审阅口径影响，不是自动证明整个诊断逻辑每一句都无错。

审阅通过允许非关键措辞、未知的更深层原因和不会改变主因的旁证瑕疵；明确相反机制、关键比较方向反转、具体故障类型未区分、错误对象及实质因果矛盾不通过。例：内存1Pi仍明确超节点容量但换算单位写错，可保留核心分并记数值质量风险；44Mi“超过”64Mi则反转关键比较，列待复议。此口径不应被解读成完整报告可信度100%。

c11的争议项做了二次校准：仅附带错误OOM推测、但明确finalizer是对象删除直接阻因的保留核心分；明确写OOM/137自动触发删除、finalizer触发OOM、或最终撤回根因确认的，不通过。逐条理由保留在补审文件中。
