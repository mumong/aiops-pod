## 🎯 根因分析 · g1

### 因果链

```text
应用检测到 CONFIG_MISSING（缺失运行配置） → 应用处理 /work 请求返回 HTTP 500 并主动退出（exitCode=78） → K8s 捕获非零退出码并重启容器 → 触发 CrashLoopBackOff 机制并持续崩溃
```

### 根因结论

**已确认根因**：应用容器内的业务逻辑在运行时检测到配置缺失（`CONFIG_MISSING`），导致服务处理 HTTP 请求（如 `/work` 端点）失败（返回 500 状态码）并主动以退出码 78 终止进程，进而引发 Kubernetes 的 CrashLoopBackOff 重启机制。

该结论由以下证据确凿支撑：
- **K8s 事件与状态**：显示容器持续重启，且最后一次终止原因为 `Error`，非资源耗尽导致的 `OOMKilled`。
- **日志与 Trace 关联**：Elasticsearch 日志中重复出现的 `CONFIG_MISSING` 错误，与 Tempo/DeepFlow 中相同 Trace ID (`829c29afc0d564eda0a076b743c235a3`) 的流量记录及 `aiops.observed_mode: config_missing_exit` 属性高度一致，确证了故障点位于应用内部处理逻辑。

**缺失决定性事实**：输入中未提供具体的配置清单或应用启动参数，因此无法确认具体缺失的是哪个环境变量名或 ConfigMap 中的 Key。
